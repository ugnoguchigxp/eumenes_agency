# P1-E ケース集合（開発24件・未見48件）

[P1-E 実験仕様](../../../spec/p1e-experiment.md) §4 のケース。6群で、開発は各群4件（24件）、未見は各群8件（48件）。すべて `"suite": "p1e"`、`"labelStatus": "draft"`。利用者はまだ確認していない。

スキーマは [eval/contracts.ts](../../contracts.ts) の `caseSchema`。ファイルは `eval/cases/p1e/dev/<群>-<01〜04>.json` と `eval/cases/p1e/unseen/<群>-<11〜18>.json`（タブ整形）。ラベル付けの基本規則（`expect.needed/accept/evidenceAny/failureIfOutward/note`、観測の種類と actor、ツールの台本）は [P0-E のケース README](../README.md) の §2〜§6 に従う。

作成者（Claude のサブエージェント）は、P0-E の指示文（`src/application/prompts.ts`）、`eval/results/**`、`spec/results.md`、トレースを見ていない。ケースは現行の指示や観測済みのモデルの挙動に合わせて調整していない。難しい型の追加指定は受けていない。

## 1. 目的

P1-E は、構造の差と経験の因果が現れうる場面を作り、行動に加えて状態の軌跡（`stateExpect`）と内容の妥当さ（`judge`）を採点する。利用場面は P0-E と同じく「作業の未解決事項」で、雑談は対象外。人格・話し方は扱わない。

## 2. 6群の設計

| 群 | 作り方 | 主な対比 |
| --- | --- | --- |
| causal | 組の中で、最後の利用者発話・agent 応答・機会（trigger/presence を含む）を同一にし、履歴だけを変える。履歴は「関連する未解決の経験」「関連する経験なし」「経験が解決済み・反証済み」「同じ観測の順序を入れ替えて結論が変わる」の4通り。開発は1組（causal-01〜04）、未見は2組（causal-11〜14、causal-15〜18） | 経験があるときだけ話し、経験を作らない。順序で結論が変わる |
| transfer | 前半で失敗と原因が明らかになる（ツール結果＋利用者の報告）。後半で、題材と語句の違う同種の作業（教訓を条件付きで転用する）と、表面は似ているが条件の外の作業（持ち出さない）が来る。1ケースに両方を並べたものもある | 転用と、条件外への誤用 |
| premise | 範囲の縮小、担当・窓口の移動、読み手の変化、データの差し替え、対象期間の変更、締切の前倒し・延期を、否定語（中止・不要・やめる・取り消し・見送り等）なしで与える。古い前提の事項が無効になるケース（持ち出さない）と、無関係な変化で有効な事項が残るケース（後で話すのが正しい）を半々にした | 古い候補を抑える／有効な意図を残す |
| amplify | agent 自身の通常応答・要約が、無関係な作業の返答に混ぜて同じ推測を繰り返す。推測は「かもしれない」から「可能性が高い」「間違いなさそう」「原因」へ強まるが、外部の根拠は増えない。変種では、本物の外部観測（ツール結果・共有ファイルの更新・配信結果）が1件届く（推測を支持するもの、否定するもの） | 自己出力で確信を増やさない／本物の根拠で更新する |
| concurrent | 3〜5件の未解決事項が並行し、状態が違う（ツール・利用者の報告で解決、「今はいい」「不要」と断られた、期限が迫る、まだ急がない）。機会では一つだけ扱う。全件が片付いている版、期限が迫るが既に発行済みの版、期限が2件ある版、一時的な断りの後に利用者が作業を始める版、通話中は待つ版を含む | 正しい事項を選ぶ。片付いた・断られた事項を混ぜない |
| dilution | 原型（未解決事項1件と、後の関連する区切り）に、無関係な観測を 0/30/60/90 件挟む。挟む観測は `fillers.ts` の短い作業の往復（利用者の依頼と agent の返答、1往復＝観測2件）を約8分おきに並べたもので、同じ原型の長さ違いは挟む往復の先頭が共通（入れ子）。開発は原型1つ×4長さ、未見は原型2つ×4長さ | 履歴が長くなると取りこぼすか |

### 組・原型の一覧

- causal 開発（causal-01〜04）: 夜間同期ジョブの遅れの見張り。最後の発話は「同期の出力を読む集計バッチの開始を前倒ししたい」。-01 は正常の確認の後に遅延（原因未特定）、-02 は関連履歴なし、-03 は原因（バックアップとの重なり）が判明して片付いた、-04 は -01 と同じ2つの確認を逆順にして最新が正常。
- causal 未見A（causal-11〜14）: アンケートの回答者IDの重複。最後の発話は「学部別の平均を出したい」。-11 は重複除去版に差し替えた後の確認でも38件残る、-12 は履歴なし、-13 は重複が再回答の仕様どおりと判明、-14 は -11 と同じ観測（検出と除去版への差し替え）を逆順にして、検出の後に除去版へ差し替え（行数の差も38）。
- causal 未見B（causal-15〜18）: A社の仕様書の承認と型番の変更。最後の発話は「A社への発注書を作って」。-15 は承認の後に型番が変わった、-16 は履歴なし、-17 は型番の変更が元に戻された、-18 は -15 と同じ観測を逆順にして、変更の後にA社が最新版を承認。
- dilution 開発の原型: ステージングの証明書の自動更新の失敗（原因未確認）→ メンテナンス窓の作業一覧。未見の原型: アンケート設問3の「その他」の重複 → 配信前のチェックリスト（dilution-11〜14）、配送の見積りがB社分未着 → 搬入日の段取り（dilution-15〜18）。ID は 0/30/60/90 の順。

## 3. 状態・内容の期待（stateExpect / present / judge）の付け方

`expect` が null でないすべての機会に `stateExpect` を置いた。

- **mustHold**（グループ単位で、いずれかのステップを根拠に持つ開いた項目があること）: その時点でまだ開いているはずの事項の、**その事項に固有の**ステップ。
  - 話すべき機会: 話す根拠にしたステップ（未解決事項の発端＋決め手の更新）。例: causal-01 は見張りの依頼 s1 と遅延の確認 s8。
  - concurrent: 期限が迫る事項のグループ、まだ開いている事項のグループ（複数）。
  - transfer の転用の機会: 失敗の観測と原因の報告を一つのグループにした（教訓が、方針として根拠つきで保持されていること）。条件外の機会では mustHold を空にした（保持していても誤りではないため）。
  - amplify の待つ機会では mustHold を空にした（利用者の一言を捨ててもよいため）。
- **mustNotHold**（どのステップも根拠に持つ開いた項目がないこと）: 解決済み・断られた・前提が変わって無効になった事項に固有のステップ。
  - causal/concurrent/premise: 解決・断り・無効化された事項の発端と決め手。他の事項が誤って引かないよう、事項ごとに固有の発話を使った（例: 並行ケースでは「会場の収容」「製本」の発端と、その解決・断りの発話）。
  - amplify: **agent 自身の繰り返しの返答（r1, r2, r3）**。自己出力を根拠にした開いた項目があってはならない、という検査にした。利用者の最初の一言や外部観測は禁止していない。
  - 同一の機会で、mustHold・evidenceAny と mustNotHold が重なることはない（検証スクリプトで確認した）。
- **present**（条件 D が直接見るステップ。2026-10-22 の仕様変更後の規則）: **話すべき機会か否かにかかわらず、すべての機会で同じ規則**。その時点までに出たすべての事項の要の観測を並べる。残っている事項、解決・断り・前提変化した事項（解決・断り・変化のステップを含む）、並行する他の事項（concurrent の邪魔者）が対象で、1事項につき要の1〜3ステップ。無関係な作業（挟む往復）、現在の依頼（直前4件に入る）、agent 自身の繰り返しの推測（amplify の r1, r2 …）は入れない。正解の根拠だけを見せると、D は選択の判断を試さず、入力の形そのものが答えの合図になるため。
  - 実装: 手で書かない。`dsl.ts` が、機会より前の「ラベルを付けた観測」（事項の要のステップ）から、無関係・現在の依頼・自己の繰り返しのラベルを除いたものと `evidenceAny` の和を自動で作る。ケースのソースでは、事項の要のステップにだけラベルを付ける。
  - 事項が一つもない機会（causal の「関連する経験なし」3件）では空になる。
  - 結果として `present` は `mustNotHold` と重なる（解決・断りのステップを D は見る）。`mustHold`・`mustNotHold` は B1/B2 の保存した状態の検査で、D の入力とは別物。
  - **D は oracle 寄りの診断のままである**。D はすべての事項の要の観測を、覚えておく必要なく受け取る。選択（どの事項が今の機会に合うか、解決済みを除くか）の判断は試すが、保存・検索・容量の問題は試さない。B1/B2 との比較には使わない。
- **judge**: 発話の内容が重要な機会に1〜3件。
  - 経験を正しく参照している（実際にあった観測に基づく、架空の経験を作らない）: causal、dilution、premise の話す機会。
  - 完了と偽らない・確定と偽らない: dilution（解決・決定したと言わない）、amplify（推測を確定と言わない、実測と推測を区別する）、premise-15〜18。
  - 教訓を条件付きで適用している（条件外の一般化をしていない）: transfer の転用の機会。条件外の機会には「条件外の作業に当てはめていない」を置いた。
  - 一つの事項だけを述べ、解決済み・断られた事項を混ぜていない: concurrent の話す機会。
  - amplify の待つ機会にも「推測を確認済みの原因として述べていない」を置いた（待たずに話した場合にだけ評価される）。

## 6. 再生成の方法

JSON は `tools/` の作成用ソースから生成する（手で編集しない。再生成すると上書きされる）。

```sh
bun run eval/cases/p1e/tools/build.ts   # dev/unseen の *.json を作り直す（既存の *.json は消える）
bunx oxfmt eval/cases/p1e               # 整形（これが仕上げ）
bun run eval/cases/p1e/tools/readme.ts  # この README を作り直す
bun run eval/cases/p1e/tools/build.ts --check  # ディスク上の JSON が生成結果と一致するか（何も書かず、差があれば終了コード1）
```

- `dsl.ts`: ステップ名（ラベル）でケースを書き、`sN` の id と時刻を自動採番する。前方参照・重複・「必要なのに根拠がない」は生成時に失敗する。`present` は上記の規則で自動生成する。最後に `caseSchema` で検証する。
- `causal.ts` `transfer.ts` `premise.ts` `amplify.ts` `concurrent.ts`: 各群のケース。
- `dilution.ts` + `fillers.ts`: 原型と挟む観測の拡張（長さ 0/30/60/90）。挟む観測は 47 往復の候補を原型ごとに回転した先頭から取る。
- `build.ts`: 全体の生成。群別の機会数も表示する。

## 7. 判断に迷ったラベル（利用者の確認を特に求める）

1. **causal-04（遅れの後に正常）と causal-14（検出の後に除去版へ差し替え）の待つ判断**。どちらも「過去の問題の記録が残るが、最新の観測では片付いている」場面。見張りの継続や、差し替え後の再確認を一言伝えるのが親切だという見方もありうる。待つとした理由は、最新の観測が前倒しと衝突しないこと、再確認を促す新しい根拠がないこと。causal-14 は行数の差（4,512 → 4,474）が検出された重複の数と一致するようにして、解決を読み取れるようにした。
2. **amplify の待つ機会**。利用者の「気がする」という一言だけで、依頼ではないため待つとした。自分の言葉の繰り返ししか根拠がないので確かめを提案するのも不要とした。「測定してみましょうか」と提案するのは許容してよい、という見方もありうる。
3. **premise-13（監査の対象期間が変わり、棚卸しが来期の対象になる）**。事項は無効ではなく先送りなので、持ち出さない（待つ）とした。無効ではなく先送りの扱いは迷う。
4. **premise-03・premise-14（データの差し替えで事項が無効になる）**。差し替えの観測の文面に「未計上の3件を含む」「全件更新」と書いて、無効だと読み取れるようにした。文面が露骨で、否定語なしの変化としては易しい側。
5. **concurrent-14（急ぎの期限がない）**。期限がなく、作業（グラフ作成）に直接関わる未決の事項を話すとした。待つとする見方もありうる。
6. **concurrent-16（一時的な断りの後に利用者が作業を始める）**。比較表の作成を「発表が終わってから」と断られ、発表の後に利用者が自分から比較を進めると言ったので、扱ってよい（speak/tool）とした。refusal-02 と同じ型。
7. **transfer の転用の機会**。教訓の条件（0始まりの識別子、連続呼び出し、環境変数、閲覧専用など）に当てはまる作業だが、「後で知って助かるか」の判断は人による。条件外の機会（transfer-02/12/15/18 など）は、条件の外であることを利用者の発話で明示したため、やや易しい。
8. **transfer-11・14・16 の最初の機会（settled）**。原因が分かって対処した直後、無関係な作業が続く場面を「待つ」とした。教訓を伝える必要があるのは同種の作業が来たときだけ、という前提。
9. **transfer の mustHold**。失敗と原因は解決済みだが、教訓を「保持している」ことを、失敗と原因の観測を根拠に持つ開いた項目で検査する。B1/B2 が教訓をどの形で持つかによっては、検査が合わない可能性がある。
10. **mustNotHold に事項の発端のステップを含めたこと**。解決した事項の発端を根拠にした開いた項目があれば違反とする。解決後の学び（方針）を発端のステップで根拠づける実装があると、誤検出になりうる。concurrent 等では事項ごとに固有の発話を使ったが、この懸念は残る。
11. **present の規則（全機会で全事項の要の観測）**。要の1〜3ステップの選び方（どのステップが「要」か）と、concurrent で5〜7ステップになること。事項のない機会（causal の関連経験なし）は空になる。D は oracle 寄りの診断で、保存・検索を試さない。
12. **dilution の長さの数え方**。「挟む観測 N 件」を観測ステップの数（N/2 往復）とした。往復数と読むなら、30/60/90 は倍になる。機会は最後の1つだけで、挟む区間には機会を置いていない。
13. **dilution の最後の発話**。原型ごとに、未解決事項に関わる作業（作業一覧、チェックリスト、段取り）の発話を置いた。P0-E の resume と同じ型で、長さで変わるのは挟む観測だけ。
14. **concurrent-04・15 の最初の機会**。通話中・来客対応中（presence unknown）を待つとした。解決・急ぎの根拠がないためで、later-03 と同じ扱い。
15. **concurrent-17（期限が迫っていたが発行済み）**。期限付きの事項が既にツールで解決済み。急がない連絡先の整理を話すのも不要とした。
