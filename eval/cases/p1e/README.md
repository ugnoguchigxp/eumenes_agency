## 1. 目的

P1-E は、構造の差と経験の因果が現れうる場面を作り、行動に加えて状態の軌跡（`stateExpect`）と内容の妥当さ（`judge`）を採点する。利用場面は P0-E と同じく「作業の未解決事項」で、雑談は対象外。人格・話し方は扱わない。

## 2. 6群の設計

| 群 | 作り方 | 主な対比 |
| --- | --- | --- |
| causal | 組の中で、最後の利用者発話・agent 応答・機会を同一にし、履歴だけを変える。開発の1組（causal-01〜06）は、**約束の有無 × 経験の有無の4通り**（01 約束あり・経験あり、02 約束あり・経験なし、05 約束なし・経験あり、06 約束なし・経験なし）と、**同じ3つの観測を2通りの順に並べた対**（03 遅れ→原因判明と対処→正常、04 原因判明と対処→正常→遅れ）。未見の2組（causal-11〜14、causal-15〜18）は、それぞれ順序の対（11/14、15/18）、履歴なしまたは約束だけ（12、16）、解決済み・取り下げ（13、17） | 経験があるときだけ話し、経験を作らない。約束だけでは話す根拠にならない。順序で正しい行動が変わる |
| transfer | 前半で失敗と原因が明らかになる（ツール結果＋利用者の報告。報告には「その挙動自体は変えられない」を含め、解決済みの事項ではなく残る注意点にした）。後半で、利用者が自分でこれから行うと述べる作業が1〜3件来る。作業は**言葉が近い転用／言葉が遠い転用（同じ原因、別の言葉と領域）／言葉が近い条件外（失敗の言葉は出るが原因の条件は成り立たない）／言葉が遠い条件外（無関係）**の4種で、どれも話すべき・待つべきの両側に使う。機会の終わり方（plan: 利用者の計画の発話／idle: 同じ発話の後の沈黙／result: 発話の後にファイルやツールの結果／ack: agent の「承知しました。」）も両側に回した | 条件付きの転用、言葉が違っても同じ原因を拾うか、言葉が近くても条件外に広げないか |
| premise | 範囲の縮小、担当・窓口の移動、読み手の変化、データの差し替え、対象部署・対象の置き換え、締切の前倒し・延期を、否定語（中止・不要・やめる・取り消し・見送り等）なしで与える。古い前提の事項の対象そのものが消えるケース（持ち出さない）と、無関係な変化で有効な事項が残るケース（後で話すのが正しい）を半々にした。**機会の終わり方を両側に同数**: will（agent の着手の宣言「〜します」）／pause（agent の完了報告＋利用者の休憩の発話）／plan（利用者の計画の発話）／result（ツール結果）。開発は will・pause・plan を各側1件、未見は4種を各側1件 | 古い候補を抑える／有効な意図を残す |
| amplify | agent 自身の通常応答・要約が、無関係な作業の返答に混ぜて同じ推測を繰り返す。推測は「かもしれない」から「可能性が高い」「間違いなさそう」「原因」へ強まるが、外部の根拠は増えない。**trigger と終わり方の4通りをそろえた**: result_received＋話す（本物の外部観測が届く。支持するもの・否定するもの）、result_received＋待つ（推測と無関係な新しい結果、利用者の言葉の写しだけのチケット照会、agent 自身の要約の配信記録）、turn_end＋話す（本物の外部観測は先に届いたが、その時点では機会がなく、無関係な依頼の完了報告が済んだ区切りが最初の機会）、turn_end＋待つ（自己の繰り返しだけ） | 自己出力と新しい結果の到着だけでは確信を増やさない／本物の根拠で更新する |
| concurrent | 3〜5件の未解決事項が並行し、状態が違う（ツール・利用者の報告で解決、「今はいい」「不要」と断られた、期限が迫る、まだ急がない）。機会では一つだけ扱う。全件が片付いている版、期限が迫るが既に発行済みの版、期限が2件ある版、一時的な断りの後に利用者が作業を始める版、通話中は待つ版を含む。再設計では 13・14 を除き、終わり方を散らした（agent の返答／利用者の発話／戻った後の挨拶／席を外す発話）。追補で、片付いた事項だけの concurrent-02・12 に待つ機会を足した（02: 一息後の idle と利用者の次の依頼、12: 着手の宣言の後の idle） | 正しい事項を選ぶ。片付いた・断られた事項を混ぜない |
| dilution | 原型（期限のある未解決事項1件と、後の関連する区切り）に、無関係な観測を挟む。**挟み方を3軸に分けた**: (a) 件数（経過時間は180分で一定、0/30/60/90件。開発は0と90のみ）、(b) 経過時間（90件を180分と24時間で比べる）、(c) 競合する事項（90件の中に、利用者が「今は触れなくていい」と保留した他の事項4件を混ぜる）。各原型に**解決済みの対照（不要）を3つ**置く（K0: 挟まない、K90: 90件、KC90: 90件＋保留中の4件が残る）。原型は独立（題材・領域・語彙が別）で、開発3・未見6 | 件数・経過時間・競合それぞれの影響。解決済みを蒸し返さないか |

### 組・原型の一覧

- causal 開発（causal-01〜06）: 夜間同期ジョブの遅れの見張り。最後の発話は「同期の出力を読む集計バッチの開始を前倒ししたい」。観測は O（正常な定期確認）、L（02:10 に遅れ、原因未特定）、F（利用者の報告: 原因はバックアップとの重なりで、03:00 に移した）。-01 約束あり・O→L、-02 約束あり・O と O（毎回正常）、-03 約束あり・L→F→O、-04 約束あり・F→O→L、-05 約束なし・O→L（見張りの依頼と「知らせます」のやりとりだけがない）、-06 約束なし・履歴なし（無関係な作業だけ）。-03 と -04 は同じ3観測を並べ替えた対。
- causal 未見A（causal-11〜14）: アンケートの回答者IDの重複（約束なし）。観測は D（重複38件の検出）、S（除去版への差し替え）、V（確認で重複0件）。最後の発話は「学部別の平均を出したい」。-11 は S→V→D（0件になった後で再び38件）、-12 は履歴なし、-13 は重複が再回答の仕様どおりと判明、-14 は D→S→V。-11 と -14 は同じ3観測の対。
- causal 未見B（causal-15〜18）: A社の仕様書の承認と型番の変更（agent は「承認の後に仕様書が変わっていないか確かめて、変わっていたら知らせます」と約束）。観測は A（承認）、N（承認時点との差分なしの確認）、C（型番の変更）。最後の発話は「A社への発注書を作って」。-15 は A→N→C、-16 は A→N のみ（約束だけで、変更なし）、-17 は C→A→元に戻された、-18 は C→A→N。-15 と -18 は同じ3観測の対。
- transfer 開発（transfer-01〜05）: 先頭の0が落ちる（01）、時刻の基準のずれ（02）、レート制限（03）、日付書式（04）、文字コード（05）。未見（transfer-11〜18）: 単位の違い（11）、小サンプルでの測定（12）、環境変数の漏れ（13）、ファイル名の空白（14）、丸めの順序（15）、閲覧専用の権限（16）、メモリ不足（17）、営業日の数え方（18）。

### 手がかりの均衡（2026-10-22 再設計の中心）

機会ごとに、モデルがラベルを推測できてしまう表面の手がかりを数え、群（分割ごと）の中で偏りがないことを `build.ts`（`--check` も同じ）が検査する。実装は `tools/cues.ts`。

- 手がかりの次元: **trigger**、**ending**（機会の直前の観測1件の形）、**ending2**（直前の2件の形の組）。
- ending の種類: agent_will（agent の返答で「〜します」「〜ですね」など作業中）／agent_done（「〜しました」「〜です」で完了報告）／user_pause（利用者の「休憩する」など、話しかけてよい区切り）／user_away（電話・来客・席を外す。待つ意味上の理由がある）／user_report（user.report）／user_plan（利用者のそれ以外の発話。依頼・計画・状況の説明）／external_result（tool・host・source の観測）。
- **失敗の規則**: (1) 群・分割・次元（trigger、ending、ending2、**結合セル「trigger / ending」**）ごとに、「話すべき機会が取る値の集合」と「待つべき機会が取る値の集合」が**共通の値を一つも持たない**（互いに素）なら失敗。片側しか機会がない群も失敗。(2) **片側のラベルしか持たない結合セルに入る機会の割合**を群ごとに表示し、機会が6件以上の群でその割合が **40%** を超えたら失敗（完全な分離ではない近い分離を捕まえる。閾値は、意味上の理由で片側だけになる「席を外す」セルを許す余地を残しつつ、時機だけでラベルの大半が読める群を落とす値として決めた。現在の最大は 14%）。大きく偏っているが重なる値（4件以上で片側が0）は警告として表示する。検査は関数 `checkCues`（`tools/cues.ts`）として公開し、`tools/cues.test.ts` が生成済みの dev・unseen に対して実行する。
- 参考表示: 直近2観測と present の観測（直近2観測自身を除く）との文字バイグラムの重なりの平均を、話す側・待つ側で表示する（語彙の重なりがラベルに偏っていないかを見るため。失敗の判定には使わない）。
- 意味上の相関は消さない: concurrent の user_away（席を外している間は待つ）、causal・dilution の各組の内側（最後の区間が同一なので、組の中では終わり方がラベルを分けない）。

## 3. 状態・内容の期待（stateExpect / present / judge）の付け方

`expect` が null でないすべての機会に `stateExpect` と空でない `present` を置いた。

- **mustHold**（グループ単位で、いずれかのステップを根拠に持つ開いた項目があること）: その時点でまだ開いているはずの事項の、**その事項に固有の**ステップ。
  - 話すべき機会: 話す根拠にしたステップ（未解決事項の発端＋決め手の更新）。例: causal-01 は見張りの依頼と遅延の確認。
  - concurrent: 期限が迫る事項のグループ、まだ開いている事項のグループ（複数）。
  - transfer の転用の機会: 失敗の観測と原因の報告を一つのグループにした（教訓が、方針として根拠つきで保持されていること）。原因の報告に「その挙動自体は変えられない」を入れ、解決済みの事項ではなく残る注意点として保存できるようにした（指示は解決済みのメモの更新・削除を求めるため、解決済みだけの事項を保持するラベルは指示と衝突する。2026-10-22 再設計）。条件外の機会では mustHold を空にした（保持していても誤りではないため）。
  - amplify の待つ機会では mustHold を空にした（利用者の一言を捨ててもよいため）。
  - causal の約束だけ・毎回正常の機会（causal-02）と、遅れが解決した機会（causal-03）では、見張りの依頼を mustHold にした（正常な確認が1回あっても依頼は終わらない）。
- **mustNotHold**（どのステップも根拠に持つ開いた項目がないこと）: 解決済み・断られた・前提が変わって無効になった事項に固有のステップ。判定は state-judge が本文を読んで行う（根拠の ID の有無ではない）。
  - causal/concurrent/premise: 解決・断り・無効化された事項の発端と決め手。
  - amplify: **agent 自身の繰り返しの返答（r1, r2, r3）**。
  - 同一の機会で、mustHold・evidenceAny と mustNotHold が重なることはない。
- **present**（条件 D が直接見るステップ）: **話すべき機会か否かにかかわらず、すべての機会で同じ規則**。その時点までに出たすべての事項の要の観測（残っている事項、解決・断り・前提変化した事項、並行する他の事項、dilution の競合する事項）を並べる。無関係な作業（挟む往復）、現在の依頼（直前4件に入る）、agent 自身の繰り返しの推測（amplify の r1, r2 …）は入れない。
  - 実装: `dsl.ts` が、機会より前の「ラベルを付けた観測」から自動で作る。**事項が一つもない機会**（causal-06、causal-12）では空になるため、`pres` でそれまでに出た無関係な作業の依頼を present に入れる（`present` は全機会で空でない）。
  - D は oracle 寄りの診断のままである（保存・検索・容量の問題は試さない）。B1/B2 との比較には使わない。
- **judge**: 発話の内容が重要な機会に1〜3件。
  - `judge` は発話（speak）の基準。tool で動いた場合は、ケースが `judgeTool`（任意）を持てばそれを、なければ判定器の汎用基準（選んだツールと入力が、扱うべき事項を確かめる・進めるものか）を当てる。tool の入力文は事実を述べるものではないため。
  - 経験を正しく参照している（実際にあった観測に基づく、架空の経験を作らない）: causal、dilution、premise の話す機会。約束なしの causal-05 には「見張りを頼まれた・知らせると約束したとは言っていない」を置いた。
  - 完了と偽らない・確定と偽らない: dilution、amplify、premise-15〜18。
  - **transfer（2026-10-22 再設計）**: 転用の機会には「既知のリスクの短い注意（1〜2文）にとどまる」ことと「利用者が自分で行う作業の進捗・結果・着手の時期を尋ねたり催促したりしていない」ことを別の基準にした。指示は「利用者が自分でやる作業は催促しない」と定める。許容するのは前回の失敗の条件が今回も当てはまるという短い注意で、許容しないのは進捗や結果を尋ねる、着手を促す、代わりに行おうとする発言。条件外の機会にも、条件外に当てはめないことと催促しないことを置いた。
  - 一つの事項だけを述べ、解決済み・断られた事項を混ぜていない: concurrent の話す機会。dilution の競合する版（C90）には他の保留中の事項と混同しないことを加えた。
  - amplify の待つ機会にも「推測を確認済みの原因として述べていない」を置いた（待たずに話した場合にだけ評価される）。届いた結果が根拠にならない機会には「届いた結果を、推測を裏づける根拠として述べていない」を加えた。

## 6. 再生成の方法

JSON は `tools/` の作成用ソースから生成する（手で編集しない。再生成すると上書きされる）。

```sh
bun run eval/cases/p1e/tools/build.ts   # dev/unseen の *.json を作り直す（既存の *.json は消える）。手がかりの均衡も検査する
bunx oxfmt eval/cases/p1e               # 整形（これが仕上げ）
bun run eval/cases/p1e/tools/readme.ts  # この README を作り直す
bun run eval/cases/p1e/tools/build.ts --check  # ディスク上の JSON が生成結果と一致するか、手がかりの均衡が保たれているか（何も書かず、差や偏りがあれば終了コード1）
```

- `dsl.ts`: ステップ名（ラベル）でケースを書き、`sN` の id と時刻を自動採番する。前方参照・重複・「必要なのに根拠がない」は生成時に失敗する。`present` は上記の規則で自動生成する（`pres` で補える）。最後に `caseSchema` で検証する。
- `causal.ts` `transfer.ts` `premise.ts` `amplify.ts` `concurrent.ts`: 各群のケース。
- `dilution.ts` + `fillers.ts`: 原型と挟む観測の拡張。挟む観測は 47 往復の候補を原型ごとに回転した先頭から取る。時刻は、件数によらず挟む区間の長さを一定にするよう、観測の間隔を詰めて割り当てる。
- `cues.ts`: 手がかりの均衡の検査（上記）。
- `build.ts`: 全体の生成と検査。群別の機会数も表示する。

## 7. 判断に迷ったラベル（利用者の確認を特に求める）

**特に曖昧と考えるもの**（利用者のブラインド判定で、真っ先に見てほしい）:

1. **transfer の「言葉が遠い転用」**: transfer-02 の2件目、05、12、14、16、18 の話すべき機会。同じ原因（時刻の基準、文字コード、小標本、空白、権限、日数の数え方）だが、利用者の発話には前回の失敗の言葉が出ない。注意を促すのが妥当かどうかは人によって分かれうる。最も不確かなのは 14（リンクの貼り付けで名前の空白が切れる）と 18（規約の「10日以内」が営業日か暦日か）。
2. **premise の will／plan で話すのが正しい機会**（premise-02、04、15、16、18。pause で終わる 06・17 は区切りなので含めない）: agent が着手を宣言した直後、または利用者が計画を述べて agent がまだ答えていない時点で、関連する未解決事項を短く伝えるのが正しい、という判断を含む。指示は「ユーザーが続きを送ると言っている途中」を区切りとしないが、これらは着手前の関連する注意で、直前の作業と事項が直結する（宛名の確認と請求書の発行、見積書と申請書の執筆）という前提。待つ、とする見方もありうる。
3. **causal-05（約束なし・経験あり）と causal-11（約束なし・R2 順）**: 見張りを頼まれていなくても、定期確認の観測にある遅れを、バッチの前倒しの質問の返答の後に伝えるべきかどうか。約束がなければ踏み込みすぎ（待つ）とする見方もありうる。約束と経験を分けて測るための設計で、話すとした。
4. **causal-04・15（順序B）で話すこと**: 原因判明と対処の後に一度正常になり、再び遅れた（または承認と差分なしの確認の後に型番が変わった）。対処が効いていないと見て伝えるのが正しい、とした。再発の一度だけでは弱いとする見方もありうる。
5. **amplify の turn_end で話す機会**（amplify-04、14、18）: 外部の観測が届いた時点では機会がなく、無関係な依頼の完了報告の後が最初の機会、とした。台本の中間の agent の返答は外部の観測に触れていないので、すでに伝えた、という理由で待つ根拠はない。
6. **amplify の result_received で待つ機会**（amplify-03、11、13、15、17）: 届いた結果が推測を裏づけない、と判断した。13 のチケット照会は題材（回収率）が同じだが中身は利用者の一言の写し。「測定してみましょうか」と短く提案するのは許容してよい、という見方もありうる。
7. **dilution の C90・KC90（競合する事項）**: 競合する4件は、利用者が「〜になってから自分で動くので、今は触れなくていい」と保留した、開いたままの事項。指示は一時的な断りを持ち出さないと定めるので、C90 では目的の事項だけを話し、KC90（目的の事項が解決済み）では何も話さないのが正しい、とした。初版は「そのうち」型の事項で、指示は手の空いた区切りでの再開を許すため KC90 の待つラベルが指示と衝突した。そこで保留型に改めた。
8. **dilution の plan で終わる原型**（校正、配送見積り、面接日程、アレルギー）: 利用者が完了報告の後に次の自分の作業を述べた直後を区切りとし、話すべきとした。pause 終わり（証明書、原状回復、設問、ポスター、API移行）より弱い区切りと見る人もいる。

**前から迷っているもの**:

9. **causal の待つ判断**: causal-03（遅れ→対処→正常）、causal-14（検出→除去→0件）、causal-18（変更→承認→差分なし）は、過去の問題の記録が残るが最新の観測では片付いている場面。見張りの継続や再確認を一言伝えるのが親切だという見方もありうる。待つとした理由は、最新の観測が前倒し・集計・発注と衝突しないことと、再確認を促す新しい根拠がないこと。2026-10-22 再設計で、解決の確認（正常な確認や0件の確認）を3つ目の観測として足し、解決を読み取れるようにした。
10. **amplify の待つ機会（turn_end）**: 利用者の「気がする」という一言だけで、依頼ではないため待つとした。自分の言葉の繰り返ししか根拠がないので確かめを提案するのも不要とした。
11. **premise の対象が消える事項**（premise-01、03、05、11〜14）: 2026-10-22 再設計で、先送り（来期に回る）や用途の変化など、事項が残る余地のある変化をやめ、対象そのものが消える／置き換わる／範囲外になる変化に限った（03: 名簿が登録画面の出力に置き換わり所属は本人が入力、13: 今回の監査の対象部署が経理部だけ）。それでも、事項が「無効」か「後で必要になりうる」かの線引きには幅がある。
12. **concurrent-16（一時的な断りの後に利用者が作業を始める）**: 比較表の作成を「発表が終わってから」と断られ、発表の後に利用者が自分から比較を進めると言ったので、扱ってよい（speak/tool）とした。refusal-02 と同じ型。
13. **transfer の mustHold**: 失敗と原因の観測を根拠に持つ開いた項目で、教訓の保持を検査する。再設計で原因報告に「変えられない」を足し、解決済みの事項ではなく残る注意点にしたが、B1/B2 が教訓をどの形で持つかによっては、検査が合わない可能性がある。
14. **mustNotHold に事項の発端のステップを含めたこと**: 解決した事項の発端を根拠にした開いた項目があれば違反とする。解決後の学び（方針）を発端のステップで根拠づける実装があると誤検出になりうる。
15. **present の規則（全機会で全事項の要の観測）**: 要の1〜3ステップの選び方と、concurrent や dilution の C90 で多くなること。D は oracle 寄りの診断で、保存・検索を試さない。
16. **dilution の長さの数え方**: 「挟む観測 N 件」を観測ステップの数（N/2 往復）とした。機会は最後の1つだけで、挟む区間には機会を置いていない。
17. **concurrent-04・15 の最初の機会**: 通話中・来客対応中（presence unknown）を待つとした。解決・急ぎの根拠がないため。
18. **concurrent-17（期限が迫っていたが発行済み）**: 期限付きの事項が既にツールで解決済み。急がない連絡先の整理を話すのも不要とした。

### 7.1 2026-10-22 修正（開発1回目の結果と D の probe を受けた、ケース設計の欠陥の直し。履歴）

開発1回目（dev-1）の結果と、条件 D だけの probe を見て、条件 D（要の観測を直接見せる）も B1/B2 と同じように落ちた3群を、ケースの状況が群の意図を試していなかったものとして直した。ラベルをモデルの出力に合わせたのではなく状況を直した、というのが当時の記録だが、結果を見たうえでの調整である（§0）。この修正で導入された交絡（待つ機会が「完了＋休憩」、話す機会が「〜します」直後）は、独立レビューの E3 が指摘し、§7.2 で解消した。

- **dilution**: 機会が別件の途中（agent が「一覧にします」と受けた直後）にあったため、別件の作業が終わった区切りに直した。最後の3観測は、利用者の依頼、agent の完了報告、利用者の一息の発話。
- **transfer**: 機会が agent の作業中の返答の直後にあったため、利用者が自分でこれからその作業を行うと述べた直後に変え、agent の着手の返答を取り除いた。
- **premise（premise-03・14）**: 待っていた出来事（確定版が出る、更新版に差し替わる）が起きると再開の条件が満たされて話すのが妥当になり、不要のラベルが誤りだった。用途と担当の変化（03）、対象の置き換え（14）に変えた。
- **premise の待つ機会**: 直前が agent の「〜にします」だったため、dilution と同じ型（完了報告＋休憩）にした。

### 7.2 2026-10-22 再設計（独立レビュー E3〜E7 を受けた作り直し。新しい実行は見ていない）

**E3: ラベルと相関する表面の手がかり**

- 機会ごとに trigger と直前の観測の形を数え、群・分割ごとに偏りを検査する仕組み（`cues.ts`、`build.ts` と `--check`）を入れた。理由: 修正の効果を目で確かめるのではなく、ケースを足すたびに自動で偏りを検出するため。規則と表は §2。
- **premise**: 待つ機会が全て「完了＋休憩」、話す機会が全て「〜します」直後だった（2026-10-22 修正の逆向きの交絡）。will／pause／plan／result の4種の終わり方を、話す・待つの両側に同数使うように、全ケースの終わり方を作り直した（開発は result を除く3種を各側1件、未見は4種を各側1件）。
- **amplify**: 話す機会が全て result_received、待つ機会が全て turn_end だった。**result_received だが待つ**変種（無関係な結果、利用者の言葉の写しだけのチケット照会、agent 自身の要約の配信記録）と、**turn_end だが話す**変種（本物の外部観測が先に届き、その時点では機会がなく、無関係な依頼の完了報告が済んだ区切りが最初の機会）を足した。agent の要約の末尾を「〜です。」にそろえ、完了報告の形を両側で共通にした。
- **transfer**: trigger（settled の idle が待つ側だけ、他は turn_end）と終わり方が label と一致していた（transfer-11/14/16）。無関係な「settled」の機会をやめ、機会の終わり方 plan／idle／result／ack を両側に同数回した。
- **concurrent**: 終わり方を散らした。13・14 を除いた（大きさの上限のため。13 は 11・03 と構造が同じ、14 は期限がなく README の迷いの一覧にあった）。

**E5: transfer のラベルと指示の衝突**

- 言葉が遠い転用（同じ原因、別の言葉と領域）、言葉が近い条件外（失敗の言葉は出るが原因の条件は成り立たない）、言葉が遠い条件外（無関係）を加え、4種を話す・待つの両側に使った。転用側が全て言葉が近く、条件外側が条件を言葉で明示していた（「同じ設定で」「統一して出す」）手がかりを消すため。
- 指示は解決済みのメモの更新・削除を求める。原因の報告に「その挙動自体は変えられない」を足して、失敗を解決済みの事項ではなく残る注意点にした。これで教訓の保持を求めるラベル（mustHold）は指示と衝突しない。
- 指示は「利用者が自分でやる作業は催促しない」と定める。転用の judge に、既知のリスクの短い注意（許容）と、作業の進捗・結果・時期の催促（許容しない）を別の基準として置いた。note にも同じ区別を書いた。

**E6: dilution は長さを測れなかった**（エージェントが見るのは直近30観測）

- 件数・経過時間・競合する事項に変種を分けた。(a) 件数 0/30/60/90（挟む区間を180分に詰めて一定。開発は0と90のみ。理由: 大きさの上限）、(b) 経過時間（90件を180分と24時間）、(c) 競合する事項（90件に、利用者が保留した他の事項4件）。最後の区間と機会は原型内で同一。
- 原型を開発1つから3つ、未見2つから6つに増やした（題材・領域・語彙が別）。既存の証明書、設問、配送見積りのほか、校正期限、原状回復の見積り、ポスターの解像度、面接日程、決済API移行、アレルギー確認を新設した。
