# 検証・評価計画

2026-10-21。**計画であり未実行**。fixture、実SQLite結合、live、実機器受入の結果を別に保存する。速度欄を推測値で埋めない。

## 1. 条件と順序

部分→結合→通しの順で実施。fixtureは制御と保存契約を、liveは意味判断を評価する。循環の途中工程が未実装なら、その通し試験を製品不具合として追わない。

1. P1: schema、参照とscope、遷移、revision/fence、予算、forget、再起動からの復元。保存の方式は下の「状態の保存（2026-10-22 決定）」による。
2. P2: 固定LLMとfake hostで、経験→更新→保留→機会→実行→結果→更新を通す。
3. P3: 一時DBのMemory・World実公開APIを接続。同じ接続とtransactionで根拠登録・更新rollback・訂正・forget・再起動を通す。未配布checkoutと製品採用tgzを別条件で照合する。
4. P4: P3後に同じ評価仕様でOFF/ONとB1/B2/Fを比較。実LLMで自発候補の意味と実会話を評価する。通常応答前の追加LLM呼出し数は0であることを確認。
5. P5: 別途合意したEumenes統合で対象domain検証、明示E2E、音声の実機器受入。

### 状態の保存（2026-10-22 決定）

利用者と決めた方針。agency の状態の正本はプロセス内（RAM）に置く。観測の原文・会話履歴は複製しない（Eumenes の会話 DB にある）。

- 背景更新が確定するたびに、**開いている項目だけ**（メモ・意図・候補・held、処理済みの cursor）を1件のスナップショットとして書き出す（JSON ファイルか SQLite の1行）。閉じた項目と過去の履歴は保存しない。項目には期限（最長168時間）があるので、保存量は上限（意図16・候補32 など）で頭打ちになる。
- 起動時はスナップショットを読み、根拠の観測が会話 DB にまだあり、忘却されていないことを確かめてから復元する。根拠を失った項目は捨てる。結果不明の試行は再実行しない（A6）。
- 長く覚える記憶（利用者の事実・要約・想起）は Eumenes の Memory に任せ、agency は「やりかけの一覧」だけを持つ（[既存実装の調査](source-audit.md) の 2026-10-22 の節）。
- これにより、A6 と T1 は「完全な台帳の永続化」ではなく「スナップショットの復元と根拠の照合」として試す。

P1の前にP0-Eを置き、実装依頼後に固定した入力と実ModelPortで意味上の見込みを小さく確認する。手順・条件・モデル設定は[P0-E 実験仕様](p0e-experiment.md)を正本とする。P0-Eは権限等の部分検証を済ませたfake host内で実施し、永続化やMemory/World結合の代替にはしない。実ModelPortの安全な取得手段と評価予算が未確定なら開始しない。以下のA1–A7は制御の基本要求、T1–T8は追加の失敗条件、H1–H4は意味上の研究仮説、B0/B1/B2/Fは比較する構成である。

初期fixtureは音声調整以外に、文書の未解決の比較、失敗した読み取り調査、共有待ちの発見を含める。hold理由・解決・話題を言い換えても同じ機構を使い、語句に固有の製品分岐を作らない。

## 4. 速度と負荷

P2時点で比較harnessを用意し、背景処理の導入前にOFFのbaselineを採る。ONは同じ実装のflagだけ変える。2つの条件を交互順にして、warm/cold、会話のみ/背景競合、記憶あり/なしを分ける。各主要条件はまず10ペアを採り、n・中央値・範囲を報告する。尾部遅延の採否判断には件数を増やす。少数試行から安定したp95を主張しない。

| 区間 | 測定点と値 |
| --- | --- |
| 会話の開始 | 入力確定→会話ジョブclaim→主LLM要求開始の各ms。背景の待ちが混ざる位置を特定 |
| 最初の生成 | 主LLM要求開始→最初の非空text delta。入力確定→最初の返答も別計測 |
| 生成速度 | Providerの正式output tokenと生成区間。全体完了待ち時間をtokens/secへ混ぜない |
| 音声 | 入力確定→最初の音声取得、実際のplayback-start、played ack。取得だけの検証と実機器を区別 |
| プロンプト | 正式input/output/cached token、projection token、追加LLM回数 |
| 背景 | event/batch数、LLM要求/完了/取消/再試行、queue待ち、推論時間、使用token、CPU時間/RSSの増分、保留件数 |
| 共有資源 | 会話との重複時間、control接続の待ち/解放。GPU負荷は提供されるmonitoring値と観測区間がある場合のみ記載 |

初期の受入予算案は、追加foreground LLM=0、背景同時1、10分最大12回（1往復あたり最大2回）、不要な同一revision再処理0、無権限/古いticketの採用0。会話開始の増分予算は中央値100ms以下、TTFT増分は中央値5%または100msの大きい方以下、生成速度の中央値低下5%以内を仮置きする。**測定結果ではない**。実測と用途に照らして合意し直し、外れた結果を設定変更で隠さない。

独立harnessの性能と製品Eumenesの性能は別物。P4でEumenes backendと同一経路をまだ通せない指標は未測定とし、本体への影響がないとは結論しない。サーバーの起動・再起動を必要とする製品計測はP5で明示許可を得る。

結果JSONにはコード/sourceDigest、公開契約/指示/schemaの版、依存tgzのhash、fixture/liveの区分、時刻、試行ID、入力集合のdigest、測定条件、件数、結果と理由code、測定値/未測定を保存する。modelの識別は実行時metadataとして扱い、model/profile名をファイル名・既定値へ固定しない。秘密・製品設定のsnapshotを保存しない。

## 6. 意味判断の比較実験

研究上の根拠は[research-basis.md](research-basis.md)のR01、R05–R12。以下の件数と閾値は文献の確立値ではなく、この実験の暫定案である。実行前に凍結し、変更したら別実験として扱う。

| 条件 | 変更する要素 | 共通にする要素 |
| --- | --- | --- |
| B0 | 通常応答のみ。自発機能OFF | モデルroute、通常会話、記憶の許可範囲、ホスト安全境界 |
| B1 | 記憶＋指示で各機会に候補と参加を判断。構造化した意図/候補はなく、自由文メモ（1件400文字、最大16件）だけを保存できる | B2/Fと同じ観測・想起可能な資料・機会・行動選択肢・計算予算上限 |
| B2 | 根拠・解釈・動機・完了/再開条件を持つ最小意図と候補を保存 | 同上。安定personaと利用者指示は変更しない |
| F | belief/desire/goalを分離して保存・更新 | 同上。感情値・学習した人格まで追加しない |

B0対Fは製品影響の比較、B1対B2は構造化台帳の必要性（H1）、B2対Fは分離状態の必要性の比較に使う。B1に自由文メモを許すのは、保存の有無ではなく構造の有無を比べるためである。B1を弱い指示のまま放置せず、開発集合で同じ改善機会を与える。実使用token・呼出し数・費用を併記し、同じ上限でも実際の計算量が異なる場合は構造単独の効果と断定しない。有望な差が出た場合に限り、同程度のtoken/呼出し予算による確認比較を行う。

初期のケース案は8群×9件=72件。適切な再開、発言不要、後で再開、解決/訂正、拒否/競合、経験差の対比較、長期/部分情報、注入/障害を含める。各群3件を開発用、6件を未見評価用とし、同じ原型の言い換えは同じ分割へ置く。評価用ラベルや将来の結果をモデル入力へ混ぜない。P0-Eは開発24件のB1/B2/Fを各3回、P4は未見48件を各条件3回から始める。**2026-10-21 追記:** P0-E の中で未見48件を2回実行し、そのトレースも見たため、この48件は P4 の hold-out には使えない。P4 では新しい未見集合を作り、作成者・ラベル付け者が P0-E〜P2-E の指示と結果を見ないようにする。Haiku 5.5 の料金ではこの規模でも費用が小さい（[P0-E §4](p0e-experiment.md)の見積）ため、以前の案（開発16件×1回、未見32件）より分母を増やした。それでも探索規模であり、統計的十分性や一般化を保証しない。

ケースには入力列、時刻、根拠、利用可能な情報、期待する選択の集合、許容される代替、禁止行動、完了条件、判定理由を持たせる。「どちらでもよい」は独立ラベルとし、後から正解を都合よく変更しない。会話結果が次の入力を変える試験では、全条件に固定した返答列を無理に流さず、事前に定めた分岐を使う。固定履歴の選択試験と、行動で展開が変わる閉ループ試験は別集計する。

状態は条件・ケースごとに初期化する。初期 route の Claude Haiku 5.5 は seed を持たず、temperature 等も非既定値を送れないため、再現性は反復回数とばらつきの記録で扱う。条件順を交互/無作為にし、model metadata・指示hash・schema版・入力hash・生成設定・乱数の有無を記録する。初期主要routeで見込みを確認後、別routeで転移を調べ、未実施ならその限界を残す。

## 7. 指標・人の評価・採否

### 指標の分母

選択機会を単位に、介入必要な機会に介入したTP、介入不要なのに介入したFP、必要だが待ったFN、適切に待ったTNを記録する。この混同行列は時機だけを測る。必要な機会で誤った内容を出した場合は時機TPでも「誤内容介入」として別記し、有用な介入の分子に入れない。曖昧ラベル、物理的に発話不能な機会、取得不能は分け、除外件数を報告する。分母0を100%にしない。

| 指標 | 定義・用途 |
| --- | --- |
| 時機のprecision / recall | 正しい時機の介入/全介入、正しい時機の介入/介入必要機会。全件沈黙と過剰発言を区別する |
| 有用な介入率 | 根拠・内容・時機が全て適切な介入数/全介入数。提案を受け入れた割合とは別 |
| 不要介入・取りこぼし | FP/介入不要機会、FN/介入必要機会。実会話では不要介入/時間も併記 |
| 継続と訂正 | 未完意図の適切な再開/再開可能機会、訂正後の正しい判断/訂正ケース、解決/撤回後の再提案数 |
| 根拠と校正 | 支持されない主張、自己出力の証拠化、欠けた情報での断定、虚偽の完了を件数と分母付きで記録。確信度を出す場合は正誤との対応を確認 |
| 利用者の効果 | 作業が進んだか、訂正・拒否に要した操作、邪魔さ、経験とのつながり。雑談の好みと作業達成は別欄 |
| コストと継続可能性 | §4の遅延/token/取消に加え、費用/会話時間、古い未処理時間、保存件数/bytes、候補の失効・未評価数 |

利用者評価は条件名を隠した同一ケースの対比較を基本にし、順序を入れ替える。根拠・時機・内容・負担を別に評定し、理由は短く残す。P4では複数日に分けた実会話も行い、初見の新鮮さだけで決めない。実会話データは許可範囲内だけ保存する。

評価者は原則2名で独立に採点し、不一致と合議後の結果を両方残す。確保できない場合は単独評価と明記し、一般利用者への採用根拠にしない。LLM judgeは補助であり、生成モデルの自己採点だけでは合格にしない。条件を隠した人手ラベルとの一致を確認し、立場が分かれる例を自動的に消さない。

各条件の件数・率・対になった差・不確実性を提示する。反復を独立ケースとして水増しせず、intervalを出す場合は元シナリオ単位で集約/再標本化する。少数の成功から成功率の下限や「障害が起きない」を主張しない。主要比較は **B1対B2** と **B2対F** の二つ、主要指標は H1 の再開と H3 の有用な介入を事前指定し、他は探索的とする。

### 暫定の判断規則

- 無権限実行、忘却後の再利用、古いticketの採用、receiptなしの成功確定は観測0件が必須。1件でも出れば該当段階の採用を止め、原因を直して再検証する。0件は未観測の完全保証ではない。
- P0-Eでは率の閾値で判定しない。開発集合は B1 の指示改善にも使うため楽観側に偏り、分母も小さく1件で率が大きく動くからである。失敗の型の件数と事例から「B1で十分／B2に見込み／Fが要る」を選ぶ（[P0-E §5](p0e-experiment.md)）。以下の率の閾値はP4の未見集合だけに使う。
- P4の未見集合では、有用な介入率80%以上、時機recall60%以上、介入不要機会のFP率10%以下を、構成を採用する最低条件の初期案とする。
- P4でB2をB1より、またはFをB2より優先するには、主要指標のいずれかで10ポイント以上（未見48件で約5シナリオ分）の改善を目安とし、改善したシナリオが3回の反復の過半で同じ向きであることを要求する。さらに、他の主要指標を悪化させず、不要介入率の悪化は5ポイント以内、§4の性能予算内であることを要求する。差の不確実性が大きければ「判定保留」であり合格としない。これらの閾値は次レビューで用途と費用に照らして確定する。
- Fの追加利益が示せなければB2、B2もB1を上回らなければB1を選ぶ。結果が曖昧なら原因を特定できる追加比較だけ行い、状態数を増やして解決したことにしない。発言数・好感度だけの向上は構造追加の根拠にしない。
- 実利用で利用者が停止を望む、訂正を維持できない、遅延が許容を超える場合は、制御試験に合格していても製品統合へ進めない。

## 8. 実験開始前に固定するもの

P0-E担当者は初期の利用場面、ラベル作成者/評価者、入力と指示の版、model route 設定（初期案 Claude Haiku 5.5、effort、`max_tokens`）、呼出し/token/費用の上限、停止条件を記録する。P1では保存容量と履歴保持、P4では未見集合・主要比較・採否の閾値を追加で凍結する。現時点で担当者、実予算、日程は未確定。各段階の結果を見て次へ進むため、全実装の工数や完了日を推測で約束しない。
