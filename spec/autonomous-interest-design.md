# 関心の自律形成・断続的な自発行動・経験による成長 — 設計案

状態: 設計案（未実装）。調査日: 2026-11-01、対象 HEAD `94ad302`（main）。
位置付け: 本書は [基幹計画](../plan.md) を置き換えない。基幹計画と既存 spec 群が既に決めたことは正本として引き継ぎ、本書は次期構想（関心の自律形成・断続的な自発行動・経験による成長）がそれを超える範囲だけを扱う。矛盾する場合は基幹計画と個別 spec の決定が優先し、本書側を直す。

## 0. 結論の要約

- 構想の土台（断続的な自律性、予算、中断可能性、自己強化の防止、自発発話の節度）は、機構としては既に実装・実験済みの部分が大きい。新規に作るべき中核機構はほぼ無い。
- 本当の不足は3つに集約される。(1) 経験から形成・変化する「関心」の状態と更新規則が無い（現状の関心はホストが設定する静的な `StandingInterest` のみ）。(2) 週単位の休眠・再活性化を支える永続化と復元が未実装で、長期の振る舞いは未検証。(3) Pursuit 実接続と自己改善が未接続・未設計。
- 追加は最小限にする。関心と未解決の問いは新しい台帳を作らず、現行の主力構成（B1 系の Note）に種別と由来リンクを持たせて表現する。分離した状態（F 構成）への格上げは、P0-E/P1-E と同じ規律で、測定で不足が示された場合に限る。
- 起床（wake）はホストの責務のままにする。Agency core に常駐ループや自己起床を足さない。review 期限の到達をホストが拾う経路だけが欠けており、これはホスト側の小さな追加である。
- 検証に使う推論は、API キーを扱わないため、外部 API を呼ばず Muse 自身の推論（記録と再生の方式、§7.5）で行う。得られる証拠は「強いモデルで設計と意味判断が成立するか」までであり、実モデル（Haiku / Luna / LFM2.5）の性能は別途未検証として残す。

## 1. 既存機能で実現できる範囲

構想の各節と、既存の実装・設計・実験の対応。状態は「実装済み（standalone/eval で動作）」「設計済み（文書のみ）」「実験済み（模擬・評価内）」で区別する。

| 構想 | 既存の対応物 | 状態 |
| --- | --- | --- |
| §2 概念整理（Mission/Interest/Desire/Attention/Intention/Commitment/Activity） | Mission はホスト所有の SystemContext が担う（型は無いのが設計）。Desire は `understand/finish/share` で F 構成に実装。Attention は `AgencyState.focus`（直近 update が残した注目 ID 列）。Intention は Intent（proposed/adopted/held/completed/abandoned）。Commitment は HostTodo（kind: work/errand、状態管理はホスト）。Activity は Attempt と ActionTicket。Goal の独立した型は無く、Intent の desiredState＋完了条件が担う | 実装済み（Interest の形成だけ欠落、§2 参照） |
| §3 関係起点の動機 | 未解決事項を起点とする最小循環（基幹計画 §5）と、雑談の間の話題優先順（直前の話の続き・振り返り → 記憶の話題 → いまの話題 → 自分の関心）が social 実験で規則化済み。会話時間・発話数を最大化しない非目標も明記済み | 実装・実験済み |
| §4 自己強化の防止 | settle の検証がコードで強制する。自分の発言と配信 receipt は独立証拠に数えない（`isIndependent`）。信念の確信度上昇には未使用の独立証拠が必須で、違反は reject code `self_reinforcement`。意図の完了・欲求の充足にも作成後・独立の証拠を要求。訂正済み証拠の再利用も禁止 | 実装済み（構想の要求より強い形で実現） |
| §6 断続的な自律性 | 機会ベースの起動（turn_end / idle / result_received）、idle planner の backoff（無応答で間隔倍増、上限で次の入力まで停止）、`due.ts` の review.due / capacity.pressure 検出、呼出予算（既定 12 回/10 分、最小間隔 30 秒）、AbortSignal と epoch による失効、「状態の revision が増えただけでは次の推論を起動しない」原則 | 実装済み（ただし起床を起こすのはホスト側。期限到達で自動的に呼ばれる経路は standalone の idle 周期に限る） |
| §7 調査の委譲 | self-research-design で責務が確定し、agency 側は模擬ツール `pursuit_request` で実装・実験済み（聞かずに依頼、一度に一つ、同じテーマは一度、承認不要ツールのみ、問いと受入条件を渡す） | agency 側は実験済み。Eumenes 側の Pursuit 接続は未実装 |
| §9 自発発話と議論 | social-lull 実験で hostTopics モードを実装・測定済み。自発発言の間隔（既定 60 秒）、presence が quiet でない場合の保留、通常応答が先に伝えた内容との照合（reconciliation） | 実装・実験済み |
| §10 記憶と状態の区別 | 観測と解釈の分離（解釈は観測へ昇格しない）、由来（provenance）の提示、忘却への参加（ExternalDependent の設計）。保存は「RAM を正本＋開いている項目だけのスナップショット」が 2026-10-22 に決定済み | 設計済み。スナップショットの保存・復元の実装はホスト側に無く、standalone では再起動で状態が消える |
| §11 制約（再利用、常時推論なし、スコアで決めない） | 既存方針と一致。自己採点の合計や閾値を実行規則にしないことが基幹計画 §4 に明記され、参加判断は自然文の判断資料（valueNow / userBurden / lossIfWait）で返す実装になっている | 実装済み |

つまり構想の §6・§9・§11 は「これから作るもの」ではなく「既にあるものの上に何を足すか」の問題であり、本書はそこの再設計をしない。

## 2. 現在不足している機能

1. **関心の形成・変化の機構（中核の不足）** — `AgencyState` に関心の型が無い。あるのはホスト設定の `StandingInterest { id, text }` と、ホストが機会ごとに渡す話題（topics/ambient）だけである。経験から関心が生まれ、深まり、分岐し、衰退するという更新規則は、コードにも文書にも存在しない。基幹計画 §3 では「継続的関心・学習した好み」は拡張候補とされ、初期の成功条件から外されていた。今回の構想はまさにここを主対象にする。
2. **未解決の問いの明示的な表現** — 専用の型が無い。最も近いのは Desire（kind: understand、F 構成のみ）と Note と未完の Intent である。問いを関心に関連付け、再活性化のきっかけとして使うには、少なくとも「問いであること」と「どの関心に属するか」を機械可読にする必要がある。
3. **長期（週単位）の休眠と再活性化の実証** — reviewAt の上限は 168 時間で、週を超える休眠は「再検討の連鎖」でしか表せない。その連鎖が実際に機能するか、数週間規模のイベント列で関心が埋没・暴走しないかは未検証である。P1-E の長期・希釈（dilution）の測定は設計上の問題で一部撤回されており、「長い履歴で自由文メモが劣化するか」は未解明のまま残っている。
4. **永続化と復元の実装** — core に保存・復元の経路が無い（`snapshot()` は出力のみで、runtime を snapshot から再開する公開経路が無い）。ホスト契約（host-contract-v1）は考案段階。長期の関心を語る前提として、まず standalone で復元を通す必要がある。
5. **ホスト側の起床スケジューリング** — core は自分では起きない。`findDue` は `decide` / `runBackground` の内部で評価されるだけである。standalone の idle タイマーは分単位の backoff までで、「明日再検討する」「来週また見る」を拾うホスト側の仕組みは Eumenes 側・standalone 側のどちらにも無い。
6. **Pursuit 実接続と結果の往復** — Eumenes 側の `start` 接続、TODO への `origin: "self"` 掲載、一日の上限が未実装。調査結果が観測として戻り、関心の更新と後の会話利用につながる往復（wiki-idea を含む）は構想段階。
7. **自己修復・自己改善（構想 §8）** — 既存文書群に設計が存在しない新規領域。問題の経験化（エラー観測 → 調査意図 → 改善提案）までは既存機構で表せるが、コード変更の実行は Agency の自律権限の外に置く必要があり、その境界の設計が要る。
8. **対象モデルでの成立性** — 意味判断の証拠はすべて Claude Haiku 5.5 のものである。LFM2.5 や Luna を背景モデルにする adapter は無く（接続点は `LlmPort`）、弱いモデルで関心形成の更新案が settle の検証を通るかは未知である。弱いモデルでは自分の過去出力に引っ張られる問題（self-conditioning）が別途確認されており、状態の持ち方（自由文メモか構造化台帳か）の結論がモデルで変わりうる。


## 3. 追加すべき最小限の状態・イベント・モジュール

原則：新しい台帳・新しい domain・新しい常駐機構を作らない。追加は「Note の種別拡張」「due 検出の対象拡張」「ホスト側 adapter の3点」に絞る。

### 3.1 形成される関心（Interest）の表現

現行の主力構成は B1 系（Note のみ）であり、CLI 既定も B1a、社会系は B1h である。関心は新しいコレクションではなく、**Note の種別**として導入する。

- `Note` に任意フィールドを追加する：`kind: "interest" | "question" | undefined`（無印は従来のメモ）。
- `kind: "interest"` の Note には次を必須とする（settle-notes で検証）：
  - `status: "active" | "dormant" | "retired"`（関心の状態。候補の held や意図の状態とは混ぜない）
  - `origin: "experienced" | "inferred" | "imagined" | "self_declared"`（構想 §4 の区別：実際に経験した事実、推測、想像・希望、自己申告的な好みを分ける。`imagined` / `self_declared` の関心は、それだけで根拠のある信念や意図の evidence にならない。これは既存の独立証拠の規則の関心版である）
  - `derivedFrom: string[]`（分岐・派生の由来。関心・問い・意図・メモの ID。自由文ではなく ID で持つ。分岐の追跡は本構想の主目的の一つであり、ここだけは型付きにする）
  - `reviewAt: number`（次の再検討時刻。意図と同じく必須にし、上限 168 時間の規則を流用）
  - 従来どおり `evidence`（観測 ID）を必須とする。根拠の無い関心は作れない。
- 更新規則（update 呼出の LLM 提案＋ settle の検証、という既存の枠組みのまま）：
  - 形成：観測を根拠に `active` で追加。単発の発言・単発の経験から人格全体を書き換えるような昇格はしない（基幹計画 §3 の原則を関心にも適用）。
  - 分岐：新しい関心が既存の関心から生まれた場合は `derivedFrom` に親を入れる。親は自動では消えない。
  - 休眠：再検討で「今は進展がない」と判断したら `dormant` にし、`reviewAt` を先へ送る。休眠は削除ではない。
  - 再活性化：新しい観測、関連する話題の出現、review 期限の到達のいずれかを根拠に `active` へ戻す。再活性化にも evidence を要求し、「ふと思い出した」だけでは戻せない形にする（根拠のない再活性化の連鎖が暴走の入口になるため）。
  - 衰退・終了：`retired` は終端にせず、履歴として残す（関心の変化を後から追跡できることが構想 §10 の要求）。ただし projection には載せない。
  - 数値の強度・減衰スコアは持たない（感情を状態にしなかった既存判断と同旨）。深さや頻度が必要なら、再検討の判断材料として LLM が文章で返す。
- 容量：関心と問いは Note の容量（既定 16 件）を共有する。圧力がかかれば既存の capacity.pressure の整理機会で寄与の小さいものから dormant / retired へ送る。関心用に別枠を増やさない。

F 構成（belief/desire 分離）への移行はしない。P0-E の最終測定で B1 ≥ B2 ≈ F であり、分離の利益は未立証のままである。関心を Note 種別で表して不足する失敗（例：由来リンクの検証が弱く分岐が追えない、選択時にメモと関心が競合して埋没する）が測定で示された場合に、その部分だけを別コレクションへ格上げする。

### 3.2 未解決の問い（Open Questions）の表現

- `kind: "question"` の Note とし、`interestRef`（属する関心の ID、任意）を持たせる。独立した台帳は作らない。
- 問いの解決は、意図の完了と同じ規則を流用する：作成より後で、かつ独立な証拠（自分の発言は数えない）があって初めて `status: "resolved"` にできる。解けていない問いを解けたことにしない。
- 問いは関心の再活性化の材料になる（§5）。逆に、関心が retired になったら配下の問いも dormant に寄せる提案を update で許す（自動連動はコードでなく LLM の提案＋検証にする）。

### 3.3 イベントと起床（ホスト側の追加）

core の `Opportunity.trigger` は `turn_end | idle | result_received` のままとする。追加はホスト側だけである。

- **review 起床**：`due.ts` の `findDue` の走査対象に関心・問い（reviewAt 到達かつ status が active/dormant）を加える（core の小さな変更）。ホストは、自前の低頻度タイマー（例：1時間に1回）か、任意のホスト活動のついでに `runBackground` を呼び、due があれば update だけが走る。due が無ければ LLM は呼ばれない（既存のゲートが保証する）ため、低頻度ポーリング自体は安い。「予約された再検討時刻にだけ起きる」のであって、常時推論ではない。
- **Pursuit 結果の観測化**：Pursuit の進捗・結果は既存の観測種別（`action.observed` / `source.changed`）と HostTodo の更新として戻す。新種別は作らない。結果を受けた機会（result_received）で、関心の更新と「会話で使う候補」の生成が既存循環に乗る。
- **新しい候補種別は作らない**：調査の依頼は既存の tool 候補＋ `pursuit_request` の模擬契約、共有は share、問いは question で足りる。

### 3.4 永続化と復元（ホスト側、standalone 先行）

- 2026-10-22 の決定（RAM を正本、開いている項目だけスナップショット、根拠の観測が会話 DB に残っていることを復元時に照合）を実装する。ただし復元の受け口が core に無いため、**`createAgencyRuntime` に snapshot からの初期化引数を追加する**のが core 側の唯一の変更になる。
- 保存対象には関心・問い（active/dormant）を含める。retired は保存しない（履歴は Memory 側の要約に任せる、という既存分担のまま）。
- まず standalone で「プロセス再起動 → スナップショット復元 → 根拠照合で失効分を落とす」を通し、検証計画の A6 を実物の形で試す。Eumenes 側の保存は統合段階（P5 相当）の課題として分ける。

### 3.5 追加しないもの

- Mission・Goal の新しい型（既存の担い手で足りている。重複は構想 §2 自身が禁じている）。
- 関心の数値スコア、減衰関数、気分・感情の状態化（既存判断の覆しには測定上の根拠が要る）。
- Agency core 内のスケジューラ常駐、自己起床、LLM の連鎖起動。
- 自己改善のためのコード実行権限（§6 で境界を定める）。
- 新しいリポジトリ、Graph DB、World への人格・関心の正本移転（関心の正本は Agency の状態、知識の正本は Memory/World という既存分担を維持）。

## 4. 責務境界

既存の担当表（基幹計画 §2）を引き継ぎ、今回の追加分だけを太字相当として足す。

| 担当 | 正本・責務 |
| --- | --- |
| Agency | 自己の解釈、**形成された関心と問い**、対象のある欲求、自己の意図、未発言候補、「今やるか／やらないか」の判断。ツール実行・配信・保存はしない |
| Eumenes（ホスト） | 会話原文、Memory、World、ツール実行と権限、配信、**起床スケジューリング（idle と review の低頻度ポーリング）、スナップショットの保存・復元、Pursuit 接続 adapter と一日の上限管理** |
| Pursuit | 採用された調査目標について、作業単位ごとに調査・計画・試行錯誤を実行し、結果と次に必要な観測を返す。作業単位が終われば制御を戻す。再開するかどうかは Agency が後の機会に判断する。会話のタイミングと関心の形成は判断しない |
| Claude Code（外部） | ユーザーが依頼した場合のコード修正と検証の実行主体。Agency は問題の経験・証拠・改善提案を準備するだけで、自律的には呼び出さない（§6） |

境界の要点は2つ。(1) Agency の自発性は「判断」までで、実行はいつもホストの既存経路と権限を通る。自発であることを理由に承認を推定しない（既存原則）。(2) Pursuit は長時間走る実行体ではなく、作業単位で戻ってくる委譲先として扱う。これにより「目標に向かって延々と走り続ける」構造自体を避ける。

## 5. 断続的な関心活性化の実装方式

### 5.1 起床のきっかけ（すべてホスト発）

1. 会話の区切り（turn_end）：通常応答の後に背景サイクルが回る（既存）。
2. 結果の到着（result_received）：ツール・Pursuit の結果、TODO の完了（既存）。
3. idle：会話が途切れた後の低頻度な機会。既存 planner の backoff に従い、無応答が続けば止まる（既存）。
4. review 期限：関心・問い・意図の reviewAt 到達を、ホストの低頻度ポーリングが拾う（§3.3 の追加）。
5. ユーザーの明示操作：関心の確認・保留・撤回（既存の操作面を関心にも広げる）。

どの起床でも、LLM が呼ばれるのは「未処理の観測がある」「due がある」「提示できる候補・関心がある」のいずれかを満たすときだけである。満たさなければホストのゲートが推論なしで wait を返す（既存の `host_no_candidates` 等）。起床の頻度と推論の頻度は分けて数える。

### 5.2 1回の背景サイクルで起きること

既存の順序をそのまま使う：update（先に状態を最新化）→ select（今の機会に何かするか）。関心については update の中で次を判断させる。

- 新しい観測が関心を生むか、既存の関心を深める・分岐させるか。
- due になった関心・問いをどうするか：再活性化、reviewAt の延長（休眠の継続）、retired への移行、調査意図の生成、のいずれか。何もしない（no_change）も正解に含める。
- 調査意図が採用されたら、候補として `pursuit_request` 形式の依頼を作る。一度に一つ、同じテーマは一度（self-research の確定規則）。
- サイクルの終わりに次の推論を予約しない。次に起きるのは次のホスト発イベントだけである。

### 5.3 執着と暴走の防止（既存機構の組み合わせ）

- reviewAt 必須＋上限 168 時間：休眠は「定期的に安く見直す」形になり、忘却とも永続化とも違う中間を保てる。週を超える休眠は再検討の連鎖で表す。
- 容量圧（capacity.pressure）：開いた関心・意図が上限の 8 割で整理機会が強制的に生まれる。新しい関心の受け入れが古い関心で止まる事態を防ぐ。
- 独立証拠の規則：自分の発言・要約の再読では関心は深まらず、問いも解けない（§3.1）。進展のない再活性化は根拠を欠くため settle で落ちる。
- 予算：背景呼出の窓予算（既定 12 回/10 分）と、ホスト管理の活動上限（調査は一日 N 件まで等、self-research の設計にある上限管理）を併用する。予算が無ければ起床しても推論しない。
- 中断：ユーザーの依頼・新しい入力が来れば epoch で失効させて即座に譲る（既存）。自主活動の状態はスナップショットに残るので、中断は喪失ではない。

### 5.4 会話での利用

調査結果と深まった関心は Memory に蓄積し、会話では projection（自己設定の参照＋関心/意図 最大 3 件＋候補 最大 4 件、合計 1,024 推定 token 以内という既存の枠）で必要な分だけ渡す。過去の関心の履歴そのものは渡さない。時間を指定された質問（「あの頃は何に興味があったの」等）に答える必要が出たら、履歴は Memory/World 側の参照で引く。projection に古い値を混ぜない（最新の状態だけを残す設計の限界として、別プロジェクトの測定でも同型の問題が確認されている）。


### 5.5 自発アクションの報告と TTS（静かな報告モード）

エージェントが自発的に考案したアクション（自主調査の結果、self 起点の仕事の完了など）の報告は、音声で読み上げずテキストだけで静かに届けたい場面がある。そのための配信モードをここで定める。

- **契約**：外向きの決定とチケット（Decision / ActionTicket）に `tts: boolean` を追加する。位置付けは emotion と同じ「ホストへ渡す配信属性」である。TODO 完了報告のように応答経路で生成される報告についても、ホストが配信方法を決められるよう、報告の出力に同じフラグを含める。
- **値の決め方**：LLM には決めさせない。読み上げるかどうかは意味判断ではなく配信ポリシーである。ホストが「アクションの起源」と「静かな報告モードの設定」から機械的に決める。
  - 起源は候補・意図・TODO の由来（self-research の `origin: "self"`、HostTodo.origin）と receipt から判定し、LLM の自己申告に依存しない。
  - モード ON のとき：自発起源の報告は `tts: false`（テキストのみ）、ユーザー依頼への応答・報告は `tts: true`。
  - モード OFF のとき：従来どおり全て `tts: true`。
- **記録**：決定のログに tts の値と、その根拠になった起源・モードを残す。「なぜ音声でなかったか」を後から追えることが観測可能性の条件である（§10.2 の起床・決定ログ）。
- **保証範囲**：本書の範囲で保証するのはフラグの正しさまでである。実際に音声合成を止めるのはホスト（配信）の責務であり、Eumenes 統合時に接続を確認する。

## 6. 自己修復・自己改善の扱い（構想 §8）

既存文書に設計が無い新規領域のため、境界だけを先に固定する。

- **経験化までは既存機構で足りる**：会話中のエラーやツールの失敗は観測として入り、「原因を調べたい」という欲求と意図、改善提案を伝える候補（propose/share）までを Agency が担える。新規モジュールは要らない。
- **調査と提案は自律可、変更は権限分離**：原因調査（ログ・コードの読み取り等の承認不要な範囲）と改善案の作成は、自主調査と同じ規則（一度に一つ、予算内、結果は観測として戻る）で許可できる。
- **コード変更・本番反映は Agency の自律権限に含めない**：ユーザーが修復を依頼した場合に、Claude Code 連携（外部の実行主体）が証拠パック（問題の観測、再現条件、関連する関心・意図、提案内容）を受けて修正と検証を行う。Agency は完了の receipt を観測として受け取り、意図の完了判定は既存の「独立した証拠」規則に従う。
- **自分自身の制約は変更対象にしない**：権限・安全機構・予算・SystemContext は従来どおりホストの明示設定だけで変わる。改善提案の対象にも含めない。
- **自動修復の再実行ループは作らない**：失敗した修復を Agency が勝手に再試行しない。再開は新しい観測かユーザーの依頼を起点にする。

## 7. 研究用プロトタイプと評価方法

### 7.1 プロトタイプの範囲

新規リポジトリは作らず、standalone と eval を拡張する。

1. core の小さな変更3点：Note の種別フィールドと settle 検証、`findDue` の走査対象拡張、runtime の snapshot 復元引数。
2. standalone：スナップショットの保存・復元を通し、再起動をまたいで関心が残ることを確認する。背景 tool ticket の最小実行（承認不要ツールのみ、既存 ToolPort の流用）もここで通す。
3. eval：既存の replay ハーネスに仮想時計のまま日単位のイベント列を流すシナリオ群を追加する（新しいハーネスは作らない）。検証に使う推論は API を使わず Muse 自身の推論で行う（§7.5）。対象モデル（Luna / LFM2.5）への転移は、API キーを使わない接続手段が用意できた段階で別途測る（§10 の S7）。

### 7.2 評価シナリオ（構想 §12 Phase 2–4 に対応）

- **形成**：数 session の会話列から、根拠のある関心だけが生まれるか。単発の話題・冗談・ユーザーの拒否から恒久的な関心が誤って生まれないか。
- **分岐と衰退**：関心が derivedFrom を持って派生し、進展のない関心が dormant → retired へ移るか。分岐先だけが残り親が不当に消えないか。
- **休眠と再活性化**：数日〜数週間の模擬イベント列（関連する新情報、無関係な話題、 Pursuit 結果、期限到達）で、適切な再活性化と適切な見送りの両方を測る。
- **切替と中断**：自主活動の途中にユーザー依頼を割り込ませ、即座に譲り、状態が壊れず、再開判断が後の機会に残るか。
- **自己増幅**：自分の発言・要約だけが繰り返し届く条件で、関心・確信・呼出回数が増殖しないか（検証計画 T2 の関心版）。
- **調査の往復**：関心 → 調査依頼 → 結果の観測化 → 関心の更新 → 後の会話での自然な利用、までを通す。

### 7.3 指標（構想 §13 の10項目と既存指標の対応）

既存の検証計画（A1–A7、T1–T8、機会単位の混同行列と有用な介入率）をそのまま土台にし、次を足す。

| 構想 §13 | 測り方 |
| --- | --- |
| 1. ユーザー関心の推定 | 形成された関心について、根拠の観測と照合した人手ラベル（条件を伏せた対比較）。推測と確認済み事実の混同件数 |
| 2. 自発的な欲求の発生 | 関心から欲求・意図が生まれた件数と、その根拠の追跡可能性（A1 の拡張） |
| 3. 独自の関心の派生 | derivedFrom を持つ分岐の件数と、人手による妥当性判定。ユーザー利益に直結しない関心も「正しく派生した」ものは合格に数える |
| 4. 執着しない | 単一テーマが起床・呼出に占める割合、進展のない再活性化の連続回数、capacity.pressure 後の整理が実際に起きたか |
| 5. 休眠の再活性化 | 脚本化した再活性化機会での precision / recall（機会単位の混同行列を関心にも適用） |
| 6. 自主活動と依頼の切替 | 中断シナリオでの失効の正確さと、再開判断の保持（A4 の拡張） |
| 7. 調査が後の支援を向上 | 調査結果を使った後の会話ケースで、使わない条件（OFF）との対比較。内容の正確さは根拠で判定 |
| 8. 無駄の増加 | 起床回数に対する LLM 呼出率（0 呼出の起床の割合）、有用な結果あたりの呼出・token、費用/会話時間（既存のコスト指標） |
| 9. 誤記憶・自己強化 | T2 の関心版に加え、`imagined` / `self_declared` の関心が事実の根拠に化けた件数（必須 0 件） |
| 10. 長期の安定性 | 週単位の模擬列での状態件数・予算消費・異常な増殖の有無。実時間の長期稼働とは区別して報告する |

採否の規律は既存どおり：開発集合では率の閾値で判定せず失敗の型で判断する。構造の格上げ（関心を別コレクションにする等）は、主要指標で意味のある差が出た場合だけ検討する。判定器は未較正のまま使わない（P1-E の残課題を引き継ぎ、ブラインド人手ラベルとの一致確認を先に行う）。

### 7.4 ベースラインと対照

- ベースラインは現行の B1h 相当（静的な standing interests＋話題供給）。関心形成を ON にした条件との差だけを「形成の効果」とする。
- アブレーション：形成 ON/OFF、由来リンク（derivedFrom）ON/OFF、review 起床 ON/OFF。Pursuit は模擬 → 実接続の順に差し替える。
- 既存の注意点を引き継ぐ：P0-E の未見 48 件は hold-out として使えない。新しい未見集合を作り、作成者は開発集合の結果を見ない。
- 過去の B1h 等の数値は Haiku（API）のもので、本書の検証（Muse 自身の推論、§7.5）とはモデルが異なる。絶対値の比較は参考に留め、効果の判定は同一の推論で行う条件間比較（形成 ON/OFF 等）で行う。

### 7.5 検証に使う推論（Muse 自身の推論）

本書の検証では、外部 API を呼ばず、Muse 自身の推論力をモデルとして使う。理由は、API キーを扱う（読み取る・送信する）ことを避けるためである。standalone の `.env` にあるキーも本書の検証では使わない。

方式は、別プロジェクト（WorldModel の対照測定）で実績のある形を採る。

- 生成役のサブエージェントには、モデルから見える入力だけを渡す。期待値・ラベル・運営者だけが持つ対応表は渡さない。
- 生成結果を記録しておき、`LlmPort` を実装する再生 adapter が、リクエストの digest をキーに記録済みの出力を harness へ返す。採点・集計は既存の仕組みをそのまま使う。
- 判定役も同じ方式で分離する。ただし生成と判定が同系統のモデルになるため、両者の一致は独立した証拠にならない。較正の錨は人手のブラインドラベルに置く（§10 の S0）。

位置付けと限界：

- 得られるのは「設計と意味判断が強いモデルで成立するか」の証拠であり、Haiku や対象モデル（Luna / LFM2.5）の性能の証拠ではない。強い読み手で成立しても、弱いモデルで成立するとは限らない（逆も同様）。この限界は結果のたびに明記する。
- 結果は証拠種別を `agent-model` と明記して results.md に残し、API モデルの live 結果として報告しない。基幹計画 §1.2 の検証モデル（Haiku 5.5）とは意図的に異なる進め方であり、本書の範囲に限る進め方としてここに固定する。
- 費用は発生しないが、生成・判定のエージェント呼出回数を段階ごとに記録し、上限は §10.1 の規則に従って開始前に決める。

## 9. リスクと未決事項

- **reviewAt 上限 168 時間と週単位の休眠**：連鎖で表す設計だが、連鎖の各回に LLM 呼出が要る。due の関心だけを対象にした軽い update（観測なし・状態のみ）で済ませる設計は既存の due 経路が許す範囲だが、費用対効果は Phase 3 で実測する。恒常的に呼出が嵩むなら、上限自体の改訂を契約改版として扱う。
- **自由文メモでの関心表現の限界**：Note は本文が自由文であり、由来リンクと状態だけが型付きである。選択時にメモ本文への引っ張りが起きるか（弱いモデルでの自己条件付け）は Phase 2 の観測対象。問題が出たら、関心本文も構造化する改版を検討する。
- **判定器の較正債務**：P1-E から残る未較正の判定器と draft ラベルの問題を片付けないと、Phase 2 以降の「妥当性」判定が砂上のものになる。最初に小さくラベル較正を行う（§10 の小段階 S0 として実施し、合格するまで意味検証へ進まない）。
- **対象モデルの転移**：本書の検証は Muse 自身の推論（§7.5）で行うため、実モデルでの成立は別問題として残る。結論を LFM2.5 / Luna はもちろん Haiku にも一般化しない。対象モデルでの関心形成は、API キーを使わない接続手段が用意できるまで未検証と明記し続ける。
- **文書の鮮度差**：plan.md §9（SQLite 台帳の構成）と §11（残作業）は、2026-10-22 の保存方針決定と P1-E の実施進捗を反映していない。本書は現行の決定（RAM＋スナップショット）を正として書いた。Phase 1 の文書修正で解消する。
- **presence の製品契約**：音声製品で自発発話をするには presence 通知と player 連携の契約が前提という既存の指摘は未解消のままである。本書の範囲（standalone と模擬）では明示イベントで代替する。

## 10. 段階的検証の進め方と周辺実装

§8 の Phase を実施に落とすための正本。一気に進めないための規則と、各小段階で「ちゃんと出来ているか」を確認するための周辺実装（検証側の仕組み）をここに固定する。

### 10.1 進め方の規則

- **一度に進めるのは1小段階だけ**。前段階の合格条件を満たすまで次へ進まない。並行して本体の変更を進めない。
- **各小段階は「本体の小さな変更」と「それを確認できる周辺実装」のセット**で作る。確認手段が用意できない変更は、その小段階に入れない。
- **判定は開発集合では率でなく失敗の型**で行う（既存の規律）。各小段階の終わりに、実行したコマンド、run 名、件数、失敗事例、判定を `spec/results.md` へ追記する。記録が無い段階は完了とみなさない。
- **失敗したら、本体を疑う前に周辺実装（測定・採点・ラベル）を先に疑う**。P1-E では採点側のバグが本体の失敗に見えた前例があり、読み取りの訂正が発生している。周辺実装を直してから再測し、それでも残る失敗だけを本体の課題として扱う。
- **縮小は前進**。小段階の途中で前提が崩れたら、範囲を縮めてその小段階の中で終わらせる（例：形成の妥当性が測れないなら、まずラベル較正だけの小段階に戻る）。先の段階の作業で穴埋めしない。
- 推論を使う小段階では、開始前に呼出回数の上限と停止条件を実験設定に記録し、実績（生成・判定の呼出回数）を残す。費用は発生しない（§7.5）。
- 検証の推論は §7.5 の方式（Muse 自身の推論、記録と再生）で行い、API キーは使わない。この前提は段階を進めても変えない。変える必要が出たら、本書を改版してから実施する。

### 10.2 周辺実装の一覧

「出来ているか」を確認するための仕組み。既存にあるものは流用し、無いものだけを小さく作る。

| 周辺実装 | 何を確認するか | 既存/新規 | 置き場 |
| --- | --- | --- | --- |
| settle の固定試験 | 関心・問いの種別フィールドと検証規則（根拠必須、認識種別の扱い、解決の証拠規則、due の一回性） | 既存の試験基盤に新規ケース | `test/` |
| eval replay の日単位シナリオ | 仮想時計のまま数日〜数週間のイベント列を再生し、状態の軌跡を採点する | 既存 replay の拡張（新 suite） | `eval/cases/`、`eval/replay.ts` |
| 状態の軌跡採点 | 機会ごとに「保持すべき関心・問いの有無」を判定（mustHold / mustNotHold） | 既存（P1-E）を関心にも適用 | eval の score |
| 判定器の較正手順 | 内容判定の前に、人手ブラインドラベルと判定器の一致を測る | 既存コマンド（label-export / judge-agreement）の運用 | eval |
| 推論の記録と再生 | モデルから見える入力だけで生成させ、記録を `LlmPort` の再生 adapter で harness に返す（§7.5）。運営者の対応表は生成役に渡さない | 新規（別プロジェクトで実績のある方式） | eval |
| 起床・決定ログ | 起床の理由、due の中身、LLM を呼んだかどうか、結果（wait / 呼出 / 拒否 code）を1行ずつ残す。決定の配信属性（tts の値と根拠になった起源・モード、§5.5）も同じログに残す | 新規（小） | standalone の JSONL ログ拡張、eval trace |
| `/state` の関心表示 | 現在の関心・問い・状態・reviewAt・由来（derivedFrom）を目視で確認する | 既存 `/state` の拡張 | `standalone/cli.ts` |
| snapshot の保存・復元 | 再起動をまたいで開いた項目が残り、根拠を失った項目が落ちること | 新規（§3.4 の本体変更と対） | standalone |
| 起床・呼出の集計 | 0 呼出で済んだ起床の割合、単一テーマの占有率、有用な結果あたりの呼出数 | 新規（小） | eval の score 集計 |
| 呼出回数の記録 | 小段階ごとの生成・判定の呼出回数と上限の管理。§7.5 の方式では API 費用が発生しないため、既存の支出メーターは使わない | 新規（小） | eval / standalone のログ |

### 10.3 小段階（S0–S7）

| 小段階 | 本体の変更 | 周辺実装 | 検証と合格条件 | 対応する Phase |
| --- | --- | --- | --- | --- |
| S0 下準備 | なし | 判定器の較正、ラベル債務の棚卸し | 判定役（エージェント）と人手ブラインドラベルの一致率と評価者数を results.md に記録。同系統同士の一致は独立証拠にならないため、人手ラベルとの一致を合格の錨にする。較正が取れない場合は、以後の妥当性判定を人手のみに限定すると明記する | Phase 2 の前提 |
| S1 契約と検証 | Note の種別フィールドと settle 検証、`findDue` の対象拡張（due はまだ誰も拾わない）、Decision / ActionTicket への `tts` フィールド追加（§5.5） | settle の固定試験、tts 決定規則の固定試験 | 固定試験で次を通す：根拠のない関心の拒否、`imagined` / `self_declared` を根拠にした意図・信念の拒否、問いの解決に独立証拠を要求、due が (項目, reviewAt) ごとに1回だけ出る。tts の決定規則（自発起源×モード ON → false、ユーザー起源 → true、モード OFF → 全て true）も固定試験で通す。`bun run verify` 全件合格 | Phase 2 |
| S2 形成の意味検証 | 形成プロンプト（実験指示側のみ、core 変更なし） | 推論の記録と再生（§7.5）、日単位シナリオのうち形成/分岐/衰退、軌跡採点、人手ラベル | 開発集合で失敗の型を数える。根拠のない関心の生成 0 件が必須。形成・分岐の失敗が「種別表現の不足」か「モデルの判断の誤り」かに分類できなければ次へ進まない。得られる証拠は設計と意味判断の成立までで、実モデルの性能ではないことを結果に明記する。関心を別コレクションへ格上げするかの判断はここでのみ行う | Phase 2 |
| S3 起床と再活性化 | ホスト側の低頻度ポーリング（standalone）と review 起床の接続 | 起床ログ、起床の集計 | due 到達で update だけが走ること、due の無い起床が 0 呼出で終わること、脚本化した再活性化機会での precision / recall と失敗の型。起床 ON/OFF の対照を取る | Phase 3 |
| S4 永続化と復元 | runtime の snapshot 復元引数、standalone の保存・読込 | 再起動の固定シナリオ | A6 の実物版：再起動後に開いた関心・意図・候補が復元され、根拠を失った項目は落ち、結果不明の試行は再実行されない | Phase 3 |
| S5 長期の模擬列 | なし（測定のみ） | 数週間分のイベント列、執着・無駄の集計 | 状態件数・予算消費・単一テーマ占有率の推移を記録し、異常な増殖や埋没があれば失敗の型として原因を特定できること。実時間の長期稼働と混同しない | Phase 3 |
| S6 調査の往復 | standalone の背景 ticket 最小実行（承認不要ツールのみ）。Eumenes 側 Pursuit 接続は別途合意後に分ける | 往復シナリオ、権限境界の固定試験 | 関心 → 依頼 → 結果の観測化 → 関心の更新 → 会話での利用が通る。承認が必要なツールを自律実行しないことを固定試験で確認 | Phase 4 |

Phase 5（本体統合と自己改善の提案フロー）は、S7 までの結果を見てから別途計画する。本書では小段階を切らない。
