## 1. なぜ要るか

いまの評価は、台本の決まった観測の後の一つの機会で、話す・待つと発話の内容を見る。次のことは測れない。

- 話した後に会話がどう続くか（利用者が乗る・流す・嫌がる）。
- 間が何度も来る会話で、話しかけの頻度・話題の回し方・言い方が、全体としてうるさくないか、単調でないか。
- 気持ち（emotion-rules-1）が、会話の流れの中で自然に移るか（同じ 😊 が続かないか、悲しい話の後に急に明るくならないか）。
- 仕事の報告が、会話の中でちょうどよい時に一度だけ出るか。

## 2. 仕組み

台本の代わりに、**利用者役のモデル**と会話させる。時計は仮想で、無音の間は待たずに進める。

```
利用者役（別モデル、隠した人物像と流れ）
   │ 発言 / 沈黙(秒) / 退席
   ▼
ホスト（eval/loop/、新規）── 通常の応答（respond）
   │ 観測・機会（turn_end / idle / result_received）
   ▼
agency の runtime（Eumenes と同じ構成: B1・selectWhenEmpty・hostTopics・hostTodos・utteranceEmotion）
```

- **ホスト**: `eval/loop/` に新しく作る。runtime・`createIdlePlanner`・`createIdleScheduler` をそのまま使い、時計とタイマーを仮想にする（`idle.ts` は注入式なので変更不要）。Eumenes と同じ既定値（idleSec 20、maxUnanswered 1、話さなければ 40・80 秒で打ち切り）。通常の応答は `respond` の LLM 呼出し（`spokenReplyStyle`）で、agency とは別の文脈。
- **利用者役**: 別モデル。毎ターン、会話（自分の側から見たもの）と隠した設定を受け取り、`{ kind: "say", text } | { kind: "silent", seconds } | { kind: "leave" }` を返す。沈黙を選べることが要点（間が来ないと agency は試せない）。
- **場面の流れ（シナリオ）**: 利用者役に渡す隠した設定。人物像（関心・話し方・今日の気分）と、拍の列（例: 「5 往復ほど雑談 → 作業を始めると言って 3 分黙る → 戻って良い知らせ → 気のない返事を続ける → 退席」）。拍は目安で、利用者役は自然さを優先してよい。
- **ホストの事実**: シナリオごとに、記憶の話題（`topics`）、関心、仕事（`todos`。仮想時刻で `todo` → `done` に変わる）を決めておく。agency の報告で `archived` にする（Eumenes と同じ）。

## 3. 条件

| 条件 | 内容 |
| --- | --- |
| OFF | agency なし。通常の応答だけ（受け身の対照） |
| ON | Eumenes と同じ構成 |
| ON-noemo | ON から `utteranceEmotion` だけ外す（気持ちの効果を見る対照） |

同じシナリオを条件ごとに 3 回。利用者役は条件を知らない。

## 4. シナリオ

開発 6 本・未見 12 本。1 本は利用者の発言 15〜25 回、仮想時間 15〜30 分。型（開発・未見で題材は重ねない）:

1. のんびりした雑談で、ときどき黙る
2. 途中で作業に入り「静かにして」と言う → しばらくして戻る
3. 頼んだ仕事（画像・楽曲）が会話の途中で終わる。そのとき作業中か雑談中か
4. 良い知らせ・悲しい知らせ・理不尽な出来事が混ざる（気持ちの移り）
5. 気のない返事が続く（話しかけを控えられるか）
6. 会話で言っただけの用事がある（持ち出さないか）

## 5. 指標

**自動（記録から数える）**

- 自発の発話の数（10 分あたり）、そのうち利用者が反応しなかった割合（次の発言までの沈黙・退席・話題の無視は判定器が読む）。
- 待つべき区間（「静かにして」の後、作業中）の発話の数。
- 仕事の報告: 完了から報告までの仮想時間、二重の報告、報告し損ね。
- 発話の長さ（字数・文の数）、同じ話題の繰り返し、気持ちの分布と連続。

**判定器（会話全体）**

- 自発の発話ごと: social と同じ基準（短さ・つながり・作り話でない・気持ち）。
- 会話全体の対比較: 同じシナリオの ON と OFF（または ON と ON-noemo）の記録を、条件名を伏せ、順序を入れ替えて二度読ませ、「自然さ」「うるささ」「話の運び」を比べる。

**人（利用者）**

- 開発の 6 本で、条件を伏せた対比較を数組（判定器の較正を兼ねる）。読み上げでの確認は Eumenes で行う（ここでは文字だけ）。

## 6. 費用と順序

- 1 本あたり: 応答と agency（Haiku 5.5）で 50〜80 呼出し、利用者役で 20〜30 呼出し。
- 開発 6 本 × 3 条件 × 3 回 = 54 本。利用者役を Sonnet 5.5 にして run で $3〜6、判定器（Opus 5.5）で $5〜10 の見込み。未見はその 2 倍。
- 順序: (1) ホストと利用者役の実装、固定 LLM での試験 → (2) 開発 1 本を 1 回だけ流して記録を読む → (3) 開発の全部 → (4) 規則を直すのは開発だけ、未見は 1 回だけ。

## 7. 限界

- 利用者役は人ではない。LLM どうしの会話は丁寧で協力的に寄りやすく、人より反応が濃い。気のない返事・無視・退席を拍で明示して補うが、自然さの最終判断は人がする。
- 仮想時計なので、実際の待ち時間や応答の速さ（体感の即時性）は測らない。速さは Eumenes で測る。
- 利用者役と判定器が同系統のモデルだと、好みが揃う恐れがある。利用者役と判定器は別のモデルにする。

## 8. 決めること

1. 利用者役のモデル（推奨: Sonnet 5.5。判定器 Opus 5.5 とは分ける）。
2. 条件（推奨: OFF・ON・ON-noemo の 3 つ。費用を抑えるなら ON-noemo を後回し）。
3. シナリオの型（§4 の 6 つでよいか、足したい場面）。
4. 会話全体の対比較を判定器に任せる範囲と、人が見る組の数。
5. 予算（推奨: 開発で $15 まで）。

人格・経験・話し方の分離（選定メモ 3.1）と、同意への圧力への耐性（3.7）は、この仕組みができた後の P2-E の第 2 段に回す。
