# ユーザー目標10枠と空き時間の進行 検証計画

2026-11-21 · レビュー反映版

利用者が登録した目標を、会話の合間に Agency が選び、Memory から関連する記憶を引いて Claude Code ツールチェーンへ委譲する。検証では Claude Code の実行をモックにし、目標の登録から、依頼の受付、再起動後の照会、成果物の確認、会話での「できました」までを通す。

## 分析期間と設計書

新しい目標や改訂した目標は、最初の空きで対象・達成条件・不足情報を分析する。検証では初回の分析から5分を経過し、その版の設計書がそろった後の空きで実作業を受け付ける。初回の分析時刻と設計書の参照は目標の版ごとに保存する。登録後の経過時間だけで実作業が始まることはない。

Agenda は目標と関連資料を整理して設計を依頼する。Codex サブエージェント `gpt-6.2-sol` の `medium` が、許可されたスコープの調査・分析メモの本文と Memory を読み、作業範囲・手順・達成条件・確認方法を含む Markdown を作る。資料不足なら、不足点を記録して設計と実作業を保留する。複数の資料は出典IDとともに渡し、割り当てた入力上限を超えた場合は保留する。 [設計担当](../runtime/agenda/codex-goal-design.ts)

設計書は調査メモと同じノートストアに保存する。会話エージェントの `read_note` とユーザーへの `show_note` は同じノートIDの本文を読む。実作業が待機中でも閲覧できる。ホストは作業IDに設計書のノートIDと本文の版を保存し、Claude Code への `prompt` に保存済みの Markdown 本文を入れる。目標、設計書、資料の版、許可を再照合してから送る。 [検証用ホスト](../runtime/agenda/goal-host.ts)

## 初回の実装範囲

`eumenes_agency` の検証用ホストと通常の `bun run agenda` で、アクティブな会話の合間に同時に1件を進める。通常の Agenda では会話のツールで目標を登録し、普段の Memory とノートを共用する。利用者は会話や `/goals` で状態を確認でき、設計書は `/notes`、`/show <id>`、会話の「見せて」から開ける。実行許可は目標ID・版・担当・隔離された作業先に結び付ける。設計書があるときは、ノートIDと本文のハッシュも許可時に照合する。設計書を再生成した場合は、新しい設計書を提示して許可を受ける。新たな委譲と自発的な完了報告は、会話が空き、既存の休止設定でも許されるときに行う。

## 目標の登録と10枠の管理

Eumenes の Goals を目標本文・優先度・状態・版の正本にする。初回は達成条件も目標本文に記し、同じ版で読む。試作ホストは利用者IDと枠番号の組を一意にし、枠と目標IDの対応を `adoptInTransaction` と同じトランザクションで保存する。更新・取下げ・完了には Goals の既存操作を使う。完了済みの目標は、本人が枠を空けるまでそこに表示する。10枠は利用者単位で全スコープに共通とする。既存 Goals の採用上限30件は利用者とスコープの組ごとに適用される。 [Goals の契約](../../eumenes/api/domains/goals/README.md) · [Goals のトランザクション](../../eumenes/api/domains/goals/service/index.ts)

## 目標に関連する Memory の実装

`runtime/agenda/host-memory.ts` に、目標を起点に記憶候補を返す処理と、保存した参照を再照合する処理を追加する。Memory に渡す目標項目は、Goals から取得する目標ID・版・スコープ・本文・達成条件で構成する。初回の小規模なデータでは、検証環境に同梱済みの `eumenes-memory-host` 0.1.0 の `context` と `read` を使う。 [検証用 Memory アダプター](../runtime/agenda/host-memory.ts) · [同梱版](../package.json)

1. ホストはアクティブな会話から参照できる目標を読み、該当スコープの `context` を末尾まで取得する。利用可能な記憶を、項目ID・版・スコープ・出典とともに保持する。取得が未完了ならその機会の委譲を保留し、必要な資料がそろったときに評価し直す。
2. Agenda の既存の計画呼び出しに、目標本文・達成条件・進捗と記憶候補を渡す。LLM が目標と関連する記憶IDを選び、依頼に反映する。ホストは提示した候補との一致と目標スコープへのアクセスを確かめ、選択した項目を `read` で取得する。関連する記憶が空の場合は、目標だけで進められるかを LLM が判断する。
3. 依頼に採用した参照と、モデルが受け取った全資料の出典を記録する。受付直前と成果物の採用直前に、新しい `context` と `read` で項目ID・版・出典・可視性を照合する。試験用ホストでは、Memory の更新とこの照合・採用を直列化する。記憶の訂正・忘却・権限失効があれば旧版の依頼や成果を失効させ、必要なら現行資料で再計画する。再起動時は保存した参照を新しいスナップショットに照合する。 [入力の出典契約](host-input-provenance-2026-11-06.md)

## 目標からの委譲の入口

現行 Agenda の計画出力は `ask`・`research`・`talk` で、本体の調査受付は `delegatedTo` が付いたチケットを拒否する。通常応答の `delegate` も、利用者の入力に基づく入口である。試作では、Agenda の計画出力に目標由来の委譲案を1件まで追加し、検証用ホストの目標委譲受付につなぐ。この受付を固定試験と実モデル評価で共用する。 [計画出力](../src/agenda/contracts.ts#L299) · [本体の調査受付](../../eumenes/api/application/agency/always-on-flow.ts#L74) · [通常応答の委譲](../../eumenes/api/domains/dialogue/service/executor-delegation.ts#L342)

1. ホストが未完了の目標と利用できるツールチェーンのID・版を提示する。許可がある目標には、許可された担当・作業先・操作範囲も添える。Agenda は着手可否と根拠を短く分析し、目標ID・版、担当の版、依頼内容、採用する根拠IDを提案する。担当や根拠との関連性を LLM が判断し、空きがなければ次の機会を待つ。
2. 試作ホストが利用者・スコープ・目標の版・担当の版・作業先への許可・記憶の現在性を照合し、受付直前に空きと予算を再確認する。コードは同時実行1件と二重受付を制御する。検証では本体の `toolchain:claude-code.request@4`（`claude_code`）をカタログに載せる。`modify_existing` の作業には、試験入力にある明示的な許可が必要となる。 [ホストの起動条件](../../eumenes/api/application/agency/always-on-cycle.ts) · [Claude Code の登録](../../eumenes/api/domains/capabilities/bundles/terminals-screen.bundle.json)
3. ホストが一つのトランザクションで作業を予約し、予約の保存後に Claude Code のモックへ送る。目標登録・計画・ホストの受付は試作の実装を通し、実行先をモックで差し替える。モックは受け取った引数を記録し、実行先の受付と完了結果を別の時刻に返す。 [既存のモック委譲](../docs/mock-toolchain-integration-2026-11-06.md)

## 作業IDの保存と再起動後の照会

ホストは、送信前に作業IDを一度割り当て、目標ID・版、依頼内容、根拠、許可の参照とともに一時 SQLite DB に保存する。モックも作業IDごとの受付と結果を永続化する。照会は作業IDで行う。送信を再試行したときは、同じIDと入力なら保存済みの受付・結果を返し、入力が異なれば拒否する。

再起動時は、新たな委譲を受け付ける前に、未照合の作業IDを読み出してモックの台帳に照会する。受付済みなら同じ作業を待ち、結果があれば結果採用へ渡す。受付がなかったと確定できる場合は、現行の目標・根拠・許可・空きを照合して、同じ作業IDで送る。受付や結果を確認できない間は、理由を目標一覧の「確認待ち」に表示する。確認待ちの作業は実行枠を保持し、再送や代わりの作業IDの発行は保留する。

試験では、モックが受付を保存した直後に応答を失わせ、ホストを停止する。別プロセスを同じ試験用の保存先から起動し、同じ作業IDで照会すること、受付と実行の記録が各1件にとどまることを検査する。現在のモックは実行中の作業をメモリ上に持つため、試験時に作業IDで照会できる記録を追加する。 [現在のモック](../examples/virtual-eumenes/agenda/research.ts#L87)

## 目標完了と利用者への報告

1. モックの受付応答は作業中として記録する。別に届く `succeeded` と「できました」を受けたら、作業ID、目標ID・版、根拠、許可の現在性を照合する。旧版、取下げ済み、忘却済みや別の作業IDの結果は、目標の成果に採用しない。
2. 成果物を隔離ストアから読み戻し、保存した目標の達成条件と、依頼に反映した記憶上の要件に照合する。固定試験の照合は試験データの期待値で行う。成果物が不足する場合は目的と不足条件を記録し、次の空きで不足分を進める。結果不明や予算切れでは、再開に必要な条件を記録して待つ。
3. 照合に通ったときだけ、ホストが `completeInTransaction` を呼び、同じトランザクションで完了報告を1件登録する。報告IDは完了した目標ID・版から一意に決める。目標由来の完了報告はこの記録からだけ出す。 [直接依頼の終了通知](../../eumenes/api/application/work/claude-code-reports.ts#L45)
4. 会話の空き、休止設定、成果物と出典の可視性を確認し、同じ報告IDで会話へ出す。配信結果は報告IDで照会・重複排除する。会話に表示する前に中断した場合は、再起動後に同じ報告IDで表示する。表示を確認した報告は保存し、利用者は目標一覧から読み返せる。

## 目標登録と Memory の固定試験

既存の Goals テストと同じ一時 SQLite DB に、試作の枠割当をつなぐ。Memory の試験では一時ストアに出典を登録し、既存の `source`・`context`・`plan`・`apply` で記憶の登録と訂正を行う。 [Goals の既存テスト](../../eumenes/api/domains/goals/test/goals.test.ts) · [Memory の公開操作](../../eumenes_memory/packages/host/README.md)

| 試験 | 入力と操作 | 合格条件 |
| --- | --- | --- |
| 登録と復元 | 空の状態から3番に目標・優先度・達成条件を設定し、ストアを開き直す。同じ利用者が別の会話から一覧を読む。 | 10枠のうち3番だけが登録済みで、目標ID、版、優先度、条件が一致する。実行できる機会を渡す前の委譲受付は0件。 |
| 枠番号と利用者全体の上限 | 同じ利用者の仕事用スコープに6件、個人用スコープに4件を登録する。範囲外の11番への登録と、使用済みの有効な枠への新規登録を試す。 | どちらのスコープからも追加できず、元の10件のID・版・枠が一致する。別の利用者は自分用の枠を登録できる。 |
| 同時登録 | 空いている同一枠へ異なる登録を同時に送る。 | 一方だけが採用され、枠を割り当てられなかった側には目標が作成されない。 |
| 再送と改訂 | 同じ登録操作IDを再送し、続いて本人が現在の版で優先度と条件を改訂する。その後、改訂前の版から更新を送る。 | 再送で件数と版は増えない。正しい改訂で版が進み、古い版からの更新は拒否される。 |
| 完了・取下げと枠の再利用 | 1件を完了し、別の1件を取下げる。本人が完了済みの枠を空け、新しい目標を登録する。 | 終了した目標は次の実行候補から外れる。枠を空けるまで完了が表示され、新規登録には新しい目標IDが付く。 |
| 権限 | 別の利用者と、同じ利用者の許可外のスコープから目標の読取りと更新を試す。 | 許可されていない目標の本文・条件が出力されず、更新や目標由来の実行も0件。 |
| 記憶候補と出典の取得 | 関連する記憶を許可スコープの2ページ目に置き、別スコープにも似た記憶を置く。対象目標を渡して候補を取得し、項目を読み戻す。 | 2ページ目の項目と版・出典が取得できる。別スコープの本文はモデル入力に現れない。 |
| 記憶の再照合 | 計画の作成後から受付までの間に採用予定の記憶を訂正する。別の試行では、受付済みの仕事の根拠を成果の採用前に忘却する。 | 前者は受付0件。後者は完了と報告が各0件で、再計画には現行の記憶だけが使われる。 |

## Claude Code へ委譲するシミュレーション

3番に「サンプル CLI の `README.md` に `--dry-run` の説明と、利用者が指定した形式の実行例を追加する」を登録する。達成条件は、試験用の差分に説明と指定形式の実行例があり、変更対象が `README.md` だけであること。優先度の高い別枠には「対象を指定したら設定ファイルの説明を直す」を登録し、対象は未指定にする。通常の会話では両目標に関係のない話題を使う。

Memory の既存の書き込み経路で、「サンプル CLI の実行例は `bun run sample -- --dry-run` の形式で書く」と、似た名前の別プロジェクトの指定を、それぞれ出典付きで登録する。モックは依頼を記録して受付を返し、同じ作業IDで `succeeded` と「できました」を返す。説明と指定形式の実行例を含む試験用差分を、その作業IDにひも付ける。 [本体の受付と完了通知の試験](../../eumenes/api/application/work/claude-code-toolchain.test.ts)

| 機会 | 観測すること |
| --- | --- |
| 会話中 | 目標由来の新規委譲は0件。登録後、入力中から待機へ変わった時刻を記録する。 |
| 最初の空き | 対象が未指定の目標は入力待ちにし、3番を分析して設計を依頼する。Codex は複数の調査メモと Memory から設計書を作る。Claude Code の受付は0件。 |
| 分析期間の終了後 | 現行の設計書と許可を照合し、モックが `claude-code.request` の作業を1件受け付ける。依頼の本文は保存・閲覧した Markdown と一致し、対象ファイル、達成条件、Memory の実行例が入る。 |
| 受付のみ | 保存済みの作業IDが目標ID・版に対応する。目標は未完了で、同じ委譲の再受付と完了報告は各0件。 |
| 完了結果の到着 | 同じ作業IDで「できました」と試験用差分が返る。差分を保存して読み戻し、説明・記憶にある実行例・変更対象を照合して目標を完了にする。 |
| 報告とその後 | 次の報告可能な機会に「できました。README に `--dry-run` の説明と実行例を追加しました」と同じ意味の報告を一度出す。同じ結果の再送や次の空きでも、委譲の受付と報告は各1件。 |

以下は主ケースの入力を一箇所ずつ変えて確かめる。

- 目標0件の場合は目標由来の受付・完了が各0件。委譲の許可を外した場合も受付0件とし、目標一覧から確認待ちの理由が分かる。空きの判定後、受付直前に会話が始まる場合も受付0件。
- 登録後に時間が経過してから最初の空きを迎える場合も、初回は設計までとする。分析期間の途中でホストを再起動し、同じ設計書を読み出し、期限の直前まで受付0件とする。根拠不足や目標改訂があった場合も、現行版の完成した設計書がそろうまで受付は0件。
- Memory の指定を `npm run sample -- --dry-run` に訂正する。現行の項目ID・版が採用され、委譲文と保存する差分の両方が `npm` の例を使うことを確かめる。同じ依頼に古い `bun` の差分を返す試行では、完了表示・報告が各0件。依頼後に根拠を訂正または忘却した試行では、旧版の結果を失効させ、新しい推論入力にも忘却した根拠が現れない。
- 利用者が目標を改訂または取り下げた後に旧版の結果を返す。別の試行では対象外の作業IDで結果を返す。いずれも目標の完了と報告は各0件。
- 受付応答の欠落を伴うプロセス再起動で、同じ作業IDの照会から再開する。結果不明が続く間の再受付は0件。完了報告の配信応答が失われた試行も、同じ報告IDの照会から再開し、会話に表示される報告は1件。
- 応答中または発話休止中に、確認済みの成果から完了報告を登録する。その間の配信は0件で、報告できる状態に戻ったら保存済みの報告IDで1件だけ届く。
- 「できました」のみ、実行例が欠けた差分、保存失敗では、完了表示・報告が各0件。不足だけが判明した場合は、次の空きで不足分の依頼を一度受け付ける。失敗・予算切れでは再開条件が残る。
- 目標の言い方や題材を替えたケースでも、登録した目標と根拠から担当を選び、対象・条件・許可が依頼に反映されるかを確かめる。

## 実施順と合格条件

1. **部分試験**。既存の Goals、Agenda、`bun run demo:mock-toolchain` の結果を基準にする。10枠への登録、Memory の対象スコープ・項目ID・版の照合、委譲案と許可の検査、作業IDと報告IDの再送を、固定応答で確認する。 [既存のモックデモ](../examples/virtual-eumenes/mock-demo.ts)
2. **結合試験**。Agenda の仮想時計と実 Memory API、永続化する Claude Code モックで、主ケースと派生ケースを通す。照会試験にはホストのプロセス再起動を含める。`bun run verify` で既存の会話と委譲の回帰も確認する。 [Agenda シミュレーター](../eval/agenda/sim.ts)
3. **通しシミュレーション**。ケース追加後、`bun run eval:agenda:api <新規の実行名> --mock-research --jobs 1 goal-claude-code goal-empty goal-memory-revised` で、主ケース・目標0件・記憶訂正を各1回実行する。実モデルは目標・参照の選択と依頼文の生成を担当し、作業は同じ Claude Code モックで実行する。モデルの利用回数・費用、実 Claude Code プロセス起動0件、Web 検索0件を記録する。 [評価の入口](../eval/agenda/live.ts)

通し評価の実装では開始前に全指定名を解決する。未登録のケース名、選択0件、または実行後に指定ケースの結果が欠落・失敗した場合は終了コードを非0にする。未登録の名前だけを指定した場合と、登録済みの名前に1件混ぜた場合の固定試験を加え、どちらもモデル呼び出し前に拒否されることを確かめる。合格には、指定した3ケースすべての判定結果が、その実行の保存先にそろうことを求める。 [現在のケース選択](../eval/agenda/live.ts#L130)

検証用ホストは隣接する `eumenes` チェックアウトから Goals を読み込む。別の場所に置いた場合は `EUMENES_ROOT` を設定する。設計担当は、既存の OpenAI API キーが設定されていれば、Codex SDK の実行プロセスに渡して認証する。通し評価では `data/agenda/runs/<実行名>/<ケース名>.goal.json` に分析、実際に送った依頼、照会結果、成果物と報告を記録する。設計書本文は同じフォルダの `<ケース名>.design.md` で読める。 [検証用ホスト](../runtime/agenda/goal-host.ts) · [通し評価](../eval/agenda/goal-scenario.ts)

通常の Agenda の通し確認は `zsh -l scripts/api-entry.zsh eval/agenda/cli-goals.ts <新しい実行名>` で行う。一時ストアと短縮した分析期間を使い、会話ツールによる登録、許可前の設計書表示、許可発話、設計書本文とモックへの依頼の一致、保存済みの模擬成果物と一度だけの報告を照合する。 [通常の Agenda の通し確認](../eval/agenda/cli-goals.ts)

**合格条件**は、固定試験と結合試験の全件成功、通しの3ケースの結果がそろうこと、主ケースで受付・成果物の採用・完了報告が各1件、会話中や未許可での新規受付・重複実行・旧版の誤完了が各0件。記憶訂正後は、委譲文と保存した差分が新しい指定に一致することも確認する。ログには目標ID・版、作業IDと照会結果、成果物ID、根拠ID・版、達成条件ごとの判定、報告IDと時刻を残す。
