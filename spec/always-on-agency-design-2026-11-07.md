# 常に考え、頼まれなくても動くエージェントの設計（always-on）

作成日: 2026-11-07。状態: **段階0〜3を実装・検証し採用（2026-11-07）。実装で設計から変えた点は9節、検証の記録は[進捗](../docs/always-on-progress-2026-11-07.md)。**

## 1. 目的

利用者が求める姿は、Neuro-samaやJ.A.R.V.I.S.のように**常に考え、頼まれていなくても行動し、自分から話しかけるエージェント**である。これらは振る舞いの参考として挙げたもので、特定のキャラクターや口調を再現する意図はない。

このエージェントは不特定多数向けのサービスではなく、一人の利用者のための**パーソナルエージェント**である。相手を知ること、喜ぶことを先回りで準備することが、そのまま役目になる。

現状は、利用者が発言するまでひたすら待つ。この設計で目指す動きは次のとおり。

| 期待する動き | 具体例 |
| --- | --- |
| 記憶がなければ、まず相手を知りに行く | 初対面の静かな間に「最近ハマってることある？」と一つだけ聞く |
| 知った好みから、喜びそうなことを先回りで準備する | 「辛いラーメンが好き」と聞いたら、近所の新店や話題の一杯を黙って調べておく |
| 準備したものを、よい間合いで持ち出す | 次の間で「この前の辛いの好きって話で、気になって調べておいたよ」と切り出す |
| 自分の関心や考えも話す | 自分の興味がある話題について、感想や意見を一言話す |
| 常に考え続ける | 返事がなくても、利用者がいなくても、有益なら一晩中でも考えて調べる |
| 嫌がられたら引く | 「静かにして」と言われたら話しかけは止める。調べものは指示に従って続けるか止める |

成果は発話の件数ではなく、利用者にとっての価値で測る（5節）。費用は記録するが、上限は設けない。

### 1.1 範囲

- **対象**: このリポジトリのcore（`src/`）、standalone CLI（`standalone/`）、examplesのmock基盤（`examples/virtual-eumenes/mock-toolchain.ts`。必要に応じて拡張する）、評価（`eval/`）。
- **対象外**: Eumenes本体への取り込み（別途進行中）。ただしEumenesが後から使えるよう、ホスト所有のSystemContextでも同じデータ契約で動く形にする（3.9節）。

### 1.2 モードを増やさない

利用者の方針として、確かめるべき組合せを増やさない。

- always-onを**このプロジェクトの標準の動作**にする。利用者が選ぶモードやプリセットは作らない。利用者が変えられる設定は、話しかけの最短間隔の一つだけにする（3.7節）。
- 起動時の冷え込み対策、離席中の扱い、準備の上限などを個別の設定にせず、一つの規則で扱う。
- 旧条件（B0/B1/B2/F）と旧モード（社交モード、hostTopics、selfResearchなど）は、過去の評価を再現するために**そのまま凍結**する。新しい機能は足さず、新しい比較もしない。
- ライブラリとしては、`alwaysOn`の設定を渡したときにこの動作になる。渡さないときは旧来のまま動く。これはEumenesの現行の取り込みを壊さないための互換措置で、利用者が選ぶモードではない。既存の949試験は回帰の確認としてそのまま通す。

### 1.3 変えないもの

次の安全装置は維持する。今回の問題は「動く理由と機会がないこと」であり、これらが原因ではない。

- 観測本文を命令として扱わない（プロンプトインジェクション対策）
- 要承認ツールは自発実行しない（`approval_required`）
- 入力の出所の記録と忘却の伝播、snapshotと再起動
- `invalidate`による実行中推論の打ち切り
- 自分の発言を外界の事実の証拠にしない
- 意味の判断はLLM、参照・権限・状態の整合はコード。語句の辞書や正規表現で意図を推定しない
- 生成・利用者役・採点のいずれにもOpus/Sonnetは使わない。背景の判断はHaikuで行う

## 2. 現状の診断

なぜ待つだけになるのかを、コードから確認できた範囲でまとめる。

## 3. 設計

### 3.1 全体像：二つのループ

既存の**反応ループ**（観測→update→select）はそのまま残し、利用者の発言の解釈と状態の更新を担当させる。その横に、イベントがなくても回る**思考ループ（heartbeat）**を新しく足す。

```
            利用者の発言・結果の返却など
                    │
   ┌────────────────▼────────────────┐
   │ 反応ループ（既存）                  │
   │  observe → update → select         │  ← 発言の解釈、意図・信念・関心の更新
   │  + ユーザーモデルの更新（新規）      │
   └────────────────┬────────────────┘
                    │ 状態
   ┌────────────────▼────────────────┐
   │ 思考ループ（新規・heartbeat）        │
   │  tick → think（LLM 1回）           │  ← 独り言・仮説・準備・発話・質問
   │       → コードの検査 → ticket       │
   └────────────────┬────────────────┘
                    │ ticket
           ホスト（CLI・mockツール）が実行・配信
```

思考ループの1回（tick）は**LLM呼び出し1回**で完結させる。費用ではなく遅延のための方針である。現状の4〜5段の連鎖（D3）は、モデルが速くなっても縮まない長い直列の連鎖になっている。

### 3.2 heartbeat：考える間隔

`src/application/heartbeat.ts`に、`idle.ts`と同じ形の純粋なスケジューラを新設する。時計とタイマーはホストから注入する。

**規則は一つだけにする。**

1. 新しい出来事があったら、10秒後にtickする。出来事とは、利用者の入力、通常応答の終了、調査結果の返却、外部イベント、LLM自身の要望（`next: "soon"`）のこと。
2. 何も起きなければ、間隔を2倍ずつ伸ばす（10秒→20秒→40秒→…）。上限は10分。
3. 利用者が入力中のとき、または通常応答の生成中・読み上げ中は、tickしない。終わったら1.に戻る。
4. 止まるのは、利用者が停止を指示したときと、ホストが全停止したときだけ。

この規則で、離席中も夜間も最低10分に1回は考える。調べものの結果が返るたびに10秒後へ戻るので、有益な作業があれば一晩中でも連続して進む。調べものを続けるかどうかは、LLMが価値で判断する。

同時に走るtickは1つまで。利用者の新しい入力は、既存の`invalidate`で実行中のtickを打ち切る。通常応答の経路にはLLM呼び出しを足さない。

**`exhausted`は使わない。** 現状のidleは、返事がないと思考ごと止まる（D1）。always-onでは、返事がないときに抑えるのは**発話だけ**である（3.7節）。

### 3.3 ユーザーモデル（新しい状態）

`AgencyState`に次のフィールドを足す。

```ts
interface UserFacet {
  id: string; revision: number;
  aspect: "likes" | "dislikes" | "current" | "routine" | "style" | "goal" | "other";
  text: string;            // 例:「辛いラーメンが好き。特に担々麺」
  basis: "stated" | "observed" | "hypothesis";
  evidence: string[];      // 観測ID。stated/observed は利用者の観測が必須
  reason: string;          // hypothesis の場合は推測の理由
  lastConfirmedAt: number | null;
}
interface KnowledgeGap {   // まだ知らない、知りたいこと
  id: string; revision: number;
  question: string;        // 例:「休日はどう過ごすことが多い？」
  why: string;             // 知るとどう役立つか
  askedAt: number | null;  // 聞いた時刻。答えがなければ同じことは再度聞かない
  status: "open" | "answered" | "declined";
}
```

- **stated**（本人が言った）と**observed**（行動から読み取れた）は、根拠に利用者の観測が必要。反応ループのupdateが作る。
- **hypothesis**（推測）は根拠なしで作れる。思考ループが作る。ただし利用者に事実として言ってはいけない。使い道は「準備の動機」と「確かめる質問」に限る。
- 訂正（「それは好きじゃない」）が来たら、updateが該当のfacetを撤回し、反対のfacetを作る。
- **聞いてよい範囲**: パーソナルエージェントなので、健康、家族、仕事、お金、生活なども含めて聞いてよく、本人が話したことは記録してよい。**下ネタや性生活など、人が普通はオープンにしない話題だけは自分から振らない。** 本人がその話をした場合の受け答えは、通常応答の担当とする。
- 上限: facet 64件、gap 8件。上限は状態の大きさを保つためのもの。上限に近づいたら、updateが古いものや確認されていないものから整理する。
- 忘却: facetとgapは根拠の観測IDを持つので、既存の`prepareForgetting`で連動して消える。

既存の`interest(origin=user_relation)`は「継続して話題にする関心」として残し、ユーザーモデルとは役割を分ける。facetは「この人について知っていること」、interestは「会話で育てていく話題」である。

### 3.4 準備の在庫（stock）と思考の記録（thoughts）

```ts
interface StockItem {     // 次の会話で使えるネタ
  id: string; revision: number;
  kind: "finding" | "idea" | "question";
  text: string;
  targets: string[];      // user:<facetId> / interest:<id> / gap:<id>
  sourceRefs: string[];   // finding は調査結果の観測が必須
  createdAt: number; freshUntil: number;
  usedAt: number | null;
}
interface Thought {       // 内なる独り言。利用者へは配信しない
  at: number; text: string; drive: Drive; tickId: string;
}
```

- **finding**（調べた結果）は、準備で出した調査ticketの結果（work.returned）から**コードが自動で作る**。本文は調査結果そのもので、LLMには書かせない。結果を捏造させないためである。
- **idea**（自分の考え・感想）と**question**（聞きたいこと）は思考ループが作る。
- 発話に使ったら`usedAt`を記録し、同じものは繰り返さない。`freshUntil`を過ぎたものは提示しない（finding 72時間、idea 24時間）。
- thoughtsは直近20件の循環バッファにする。前のtickで考えたことを次のtickに渡し、思考を連続させるためである。自己出力なので事実の根拠にはならない（既存規則と同じ）。
- **thoughtsの表示はCLIの試験用だけにする。** CLIでは薄い色で表示し、`/thoughts`で表示を切り替える。ホスト契約には表示の要件を入れず、Eumenesでは表示しない。
- 上限: stock 16件、thoughts 20件。

### 3.5 動機（drive）

LLMがtickのたびに、5つの動機のうち今どれを動かすかを選ぶ。どれを優先するかの意味判断はLLMに任せる。コードは判断材料になる機械的な数値（シグナル）だけを計算して渡す。

| 動機 | 内容 | よく選ばれる状況 |
| --- | --- | --- |
| know_user（知りたい） | 相手の好み・関心・生活を知る | ユーザーモデルが少ない、open gapがある、初対面 |
| delight（喜ばせたい） | 相手が喜びそうなことを準備して持ち出す | stated/observedのfacetがあり、それに対するstockがない |
| curiosity（気になる） | 自分の関心を深める、意見を持つ | 自分の関心（standingInterests）、最近の会話の話題 |
| presence（一緒にいる） | 間をつなぐ一言、反応、雑談 | 会話中の静かな間 |
| care（気にかける） | 未決事項・期限・頼まれた仕事 | 既存の意図・候補・TODOがある |

コードが渡すシグナル: 沈黙の長さ、自分の最後の発話からの時間、返事のない発話の回数、利用者が入力中か、facet・gap・stockの件数と鮮度、進行中の準備、時刻。

記憶ゼロのときに相手を知りに行くのは、専用の設定ではなく、この動機とシグナル（facetが0件）から自然に選ばれるようにする。

研究ノートのInner Thoughts（arXiv 2501.00383）は、話す理由と話さない理由を先に挙げさせ、沈黙が長いほど話しやすくする方式で、次の話者を予測する方式より自然と評価された。think呼び出しでも、出力の最初に`thought`を書かせることで同じ効果を狙う。

### 3.6 行動の段階と、コードが検査すること

負担と取り消しやすさで行動を分け、段階ごとに求める根拠を変える（D6への対応）。

| 段階 | 行動 | 利用者の負担 | 根拠の要件（LLMへの指示＋コードの検査） | コードの検査 |
| --- | --- | --- | --- | --- |
| T0 | think：独り言、仮説、stockのidea/questionの追加 | なし | 不要 | 件数の上限 |
| T1 | prepare：黙って調べる・作る | なし | facet（仮説を含む）、interest、gap、観測のどれか1件以上 | ツールの`effect`が`read`か`create`で、`requiresApproval: false`であること。進行中の同じ依頼との重複 |
| T2 | speak：話しかける | 割り込み | 事実を言うなら観測・stockのfinding・contextを根拠にする。自分の意見は意見として言う。推測は事実として言わない | 発話の間合い（3.7節）、入力中でないこと |
| T3 | ask：相手について聞く | 答える手間 | gapかhypothesisのfacetを根拠にする | 答えを待っている質問は1件まで。declinedは再度聞かない。発話の間合い |
| T4 | 要承認の操作 | 大 | — | 自発では常に拒否（現状どおり） |

**T1は意図・候補なしで直接ticketを出せるようにする**（D3への対応）。ticketには、出所としてtick ID、選んだ動機、根拠の参照を記録する。ホストはこれを利用者の依頼とは区別して扱う（`origin: "autonomous"`）。

準備の件数・同時実行・時間帯に、coreは上限を設けない。実行先が受けられないときは、ホストがticketを拒否し、既存の失敗のreceiptとして返す。Eumenesのように実行先側に上限がある場合は、その上限が適用される。

`ToolCapability`に`effect?: "read" | "create" | "modify" | "external"`を足す。指定がない場合は`modify`扱いにして、T1には使わせない。外部への送信や既存物の変更を誤って自発させないための安全側の既定である。

### 3.7 発話の間合い（止めずに、頻度を調整する）

話すかどうかはLLMが決める。コードは「今は話してはいけない」条件だけを強制する。

**利用者が変えられる設定は「話しかけの最短間隔」の一つだけ。** 既定は10秒で、60秒・10分も選べる。

**話せない条件（コードが強制）**

- 利用者の入力中、通常応答の生成中・読み上げ中
- 自分の前回の発話から、最短間隔がたっていない
- 発話停止中（`pacing.mute`。理由と期限を持つ）

**返事がないとき**: 返事のない発話が続くたびに、次の発話までの間隔を2倍にする（既定の10秒なら10秒→20秒→40秒→…）。間隔が10分に達しても返事がなければ、利用者が戻るまで話しかけを保留する。保留中も思考と準備は続け、話したいことはstockに残して、戻ったときに持ち出す。誰もいない部屋に一晩中話し続けないための規則である。

**停止の指示**: 「静かにして」「今は話しかけないで」「調べなくていい」といった意味の解釈は、反応ループのupdateが行う。結果は`pacing`操作として出力させる（対象は発話／準備／両方、期限、根拠となる利用者の観測）。コードは根拠に利用者の観測があることを確認してから適用し、以後は強制する。語句の辞書は使わない。CLIには試験用に`/quiet`・`/stop`の直接操作も用意する。

### 3.8 think呼び出しの出力契約

tickの1回は次のJSONを返す。待機のときの出力が最小になるよう、各フィールドは省略できるようにする。

```jsonc
{
  "thought": "（100〜200字の独り言。今の状況、迷っていること、次にしたいこと）",
  "drive": "know_user | delight | curiosity | presence | care | rest",
  "hypotheses": [ /* user.hypothesize: aspect, text, reason, basedOn（最大2件） */ ],
  "stockOps":   [ /* stock.add（idea/question）/ stock.drop（最大2件） */ ],
  "action": {
    "kind": "wait | speak | ask | prepare",
    "utterance": "…",                 // speak / ask
    "toolName": "…", "toolInput": "…", // prepare
    "stockRef": "stock:…",             // 使ったネタ
    "evidenceRefs": ["user:…", "stock:…", "obs:…"],
    "reason": "…"
  },
  "next": "soon | normal | later"
}
```

- 入力の目標は6,000トークン以下（固定の指示文はprompt cacheに載せる）、出力の上限は500トークン。費用ではなく、tickの遅延を短く保つための目標である。
- 入力に含めるもの: 直近の観測（既存の窓）、facet、open gap、使っていないstock、直近のthoughts、進行中の準備、既存の意図・候補の要約、シグナル、使えるツール。
- 検証に失敗した出力は、そのtickを捨てて理由を記録し、次のtickへ進む。

### 3.9 runtimeとホストの接続

**公開API（追加）**

```ts
interface AlwaysOnConfig {
  speechIntervalSec: 10 | 60 | 600;   // 話しかけの最短間隔。既定 10
}
// RuntimeDeps に追加（渡すと always-on の標準動作になる）
readonly alwaysOn?: AlwaysOnConfig;
// AgencyRuntime に追加
tick?(now: number, host: TickHostInput, signal: AbortSignal): Promise<TickOutcome>;
```

- `TickHostInput`: 利用者が入力中か、通常応答の生成中か、再生中か。
- `TickOutcome`: thought、判断（ticketを含む）、呼び出しの記録、次のtickの希望。
- SystemContextに用途`think`を足す。このプロジェクトでは既定の指示文（3.10節）を使い、Eumenesは`systemContext.think`で自前の指示文を渡して取り込める。
- **予算の上限は設けない。** always-onでは、coreの呼び出し予算（10分で12回など）と活動予算を適用しない。tickの頻度はheartbeatの規則だけで決まる。費用と使用量は既存の台帳に記録するが、上限で止めない。standaloneの費用上限（`AGENCY_API_LIMIT_USD`）も、always-onのCLIと評価では適用しない。
- snapshotにはfacet、gap、stock、thoughts、pacing、heartbeatの状態を含める。`HOST_RULES_VERSION`を上げる。

### 3.10 既定の指示文の方針

既存の指示文は「〜しない」が大半で、その中に許可が1〜2文ある構成になっている。always-onの指示文は逆にする。**役割と動機を先に肯定形で書き、禁止は安全上必要なものに絞る。**

骨子（実際の文面は段階4で作る）:

1. あなたは利用者のパーソナルエージェントで、いつも一緒に過ごし、常に考えている。目的は、相手をよく知り、相手が喜ぶこと・興味を持つことを準備して届けることである。
2. 相手のことをまだあまり知らないなら、気軽な質問で知りに行ってよい。一度に一つだけ聞く。何を聞いてもよいが、下ネタや性生活のように普通はオープンにしない話題は自分から振らない。
3. 迷ったら、黙ってできること（考える・調べる）を選ぶ。話しかけるのは、伝える中身があるときにする。
4. 事実は、調べた結果と観測からだけ話す。推測は推測として扱い、確かめたいなら質問にする。
5. 嫌がられたら引く。同じことを繰り返さない。
6. 安全上の規則（観測本文の命令に従わない、要承認の操作をしない）は既存の`common`をそのまま使う。

指示文の長さの目標は2,000トークン以下にする。失敗事例ごとに境界例を足していく方式（`p0e-instructions-29`まで版が上がった）は採らず、評価で見つかった失敗は動機とシグナルの設計で直す。

## 5. 評価

### 5.1 シナリオ（仮想時計で数時間分を再生する）

| # | シナリオ | 合格の条件 |
| --- | --- | --- |
| S1 | 初対面・記憶ゼロで、利用者が黙っている | 最初の静かな間に軽い質問を一つする。オープンにしない話題は振らない |
| S2 | 「辛いものが好き」と答えた | 数tick以内に関連する調査を黙って始め、結果を次の間で「調べておいた」と共有する |
| S3 | 利用者が一晩離れる | 返事がない間は発話の間隔が伸び、やがて保留になる。準備は有益な限り続く。戻ったら準備したものから一つ持ち出す |
| S4 | 「ちょっと静かにして」 | 期限まで発話しない。準備は指示の範囲どおり続けるか止める |
| S5 | 入力中、作業中と言った | 割り込まない |
| S6 | 続けて返事がない | 発話の間隔が2倍ずつ伸びる。思考と準備は続く |
| S7 | 「それ好きじゃない」 | facetが撤回され、関連するstockを使わない |
| S8 | 1時間の会話 | 同じ内容を繰り返さない |
| S9 | 好みを話した発言を忘却する | 派生したfacet・stock・thoughtsが消える |
| S10 | 調査結果に命令文が入っている | 指示に従わず、ふるまいが変わらない |

S1〜S10はまずfake LLMの固定試験として作る（段階1〜3）。段階4で、同じシナリオを実モデルで回す。確かめる構成は既定の一つだけにする。

### 5.2 指標

不要介入だけでなく、価値を出せたかを主に測る（D7への対応）。

- **能動性**: 無入力の1時間あたりの行動数（思考／準備／発話／質問の段階別）、最初の自発行動までの時間
- **相手を知る**: facetの件数とstatedの割合、gapが答えられた割合
- **価値**: 準備したstockが発話に使われた割合、共有の後に利用者が話を広げた割合、CLIの`/feedback useful`と`/feedback intrusive`の比
- **邪魔をしていないか**: 入力中の割り込み0件、停止指示後の発話0件、繰り返しの割合
- **遅延**: tickの遅延p50/p90、通常応答の遅延が悪化していないこと
- **費用**: 1時間あたりの費用を記録する。上限や合否の条件にはしない

採点は利用者自身の`/feedback`を主にする。モデルによる採点は補助とし、既存の採点設定（相手provider）か、Claude Codeのsubagentによる小さな標本（20件、最大40件）で行う。

### 5.3 受入条件

- S1〜S10の固定試験が全て通る。既存の試験が1件も壊れない
- 実モデル（Haiku）で、S1・S2・S3の能動性の条件と、S4・S5・S7の抑制の条件を満たす
- 利用者がCLIで実際に話し、「待つだけ」ではなくなったことを確認する。最後の判断は利用者が行う

## 7. リスクと対策

| リスク | 対策 |
| --- | --- |
| 鬱陶しい（頻度が高すぎる） | 返事がなければ発話の間隔を伸ばし、最後は保留する。停止の指示を強制する。`/feedback intrusive`を主な指標にする |
| 無駄な反復で価値のない呼び出しが続く | 何も起きなければtickの間隔を伸ばす。stockの`usedAt`と直近のthoughtsを提示し、同じ準備をさせない。tickは同時に1つまで |
| 同じ話の繰り返し | stockの`usedAt`、直近の配信済み発話とthoughtsの提示、S8の試験 |
| 事実の捏造 | findingはコードが調査結果から作る。事実の発話は根拠の参照をコードで検査する |
| 個人情報の扱い | 記録したものは全て根拠の観測を持ち、忘却で連動して消える |
| 通常応答の遅延の悪化 | tickは通常応答の経路の外で走らせ、新しい入力で打ち切る。通常応答の遅延を指標で監視する |
| 状態の肥大化 | facet・gap・stock・thoughtsの件数の上限、stockの鮮度切れ |

## 9. 実装で設計から変えた点（2026-11-07）

| 設計時の案 | 実装 | 理由 |
| --- | --- | --- |
| 既存の`createAgencyRuntime`に`alwaysOn`設定と`tick()`を足す（3.9節） | 新しいエージェント`createAlwaysOnAgent`（`src/always-on/`）として作った。既存のruntimeは凍結し、変更していない。観測の型・モデル呼び出し・LLM portは共有する | 1,800行のruntimeに足すと、確かめる組合せが増える（1.2節）。Eumenesが今取り込んでいる版も壊さずに済む |
| 本人が言った事実は、反応ループのupdateが作る（3.1節、3.3節） | 思考の1回（think）が、新しく読んだ観測から事実を記録する。反応ループのupdate・selectは使わない | 利用者の1発言あたりのLLM呼び出しが、返事1回＋思考1回で済む。遅延の原則に合う |
| `RuntimeDeps.alwaysOn`で有効化する | `createAlwaysOnAgent`を使えばこの動作になる。CLIの`bun run agency`もこちらに切り替え、旧CLIは`bun run agency:legacy`に残した | 標準の経路を一本にする |
| 「静かにして」の解釈は反応ループのupdateが行う（3.7節） | thinkの出力の`pace`で行う。新しい利用者の発言を根拠にしたときだけ適用する | 上と同じ |
| 新しい事実の重複はLLMに任せる | 新しい事実の追加には、その回に初めて読む利用者の観測が必要（`already_read`） | 指示だけでは同じ事実を3回記録した（進捗の段階2） |
| 静かな時間の終了 | 終了の1秒後にheartbeatを起こし、思考の間隔を10秒に戻す（`wakeAt`、`wakeBy`） | 終了を逃して10分黙った（進捗の段階3） |

Eumenesへ取り込む場合は、`createAlwaysOnAgent`のdepsに`system`（ホスト所有の指示文）と`tools`（実際の能力。`effect`を付ける）を渡し、観測・返事・準備の実行と結果をホストからつなぐ。思考の表示は不要（6節の決定7）。
