# 改善F / 融合サンプルの比較（事前固定、2026-11-01）

## 目的・範囲・完了条件

前回のHaiku実測で見つかったFの出力契約の扱いづらさを改善し、B1の簡潔な「問いと次の一手」をFの関心・実行管理へ接続したサンプルと比較する。新しいライブラリ、DB変更、公開API変更、製品src/standalone/config変更、mainへの統合はこの実験に含めない。意味判断をコードの語句分岐へ移さず、権限・予算・状態管理は既存ランタイムを使う。

必要作業は、既存のSystemContext/出力契約/実行ゲートの確認→2サンプル→計測修正→部分/結合/全体検証→コードと基準の固定→実API→記録から再集計・監査・報告。完了には96試行の実測（または上限・失敗停止の明示）、件数・失敗・費用・不確実性を含む報告、差分点検と記録のcommit/pushが必要。試験コードの完成だけで完了にしない。

## 仮説と2サンプル

- F-improved：既存のF + interestFormationを使用。前回の共通方針に、必須項目、自己遷移の回避、関心と問いの区別、停止/解決の保存反映、同じ調査を繰り返さない指示を加える。native wire schemaとsettleは変更しない。
- Fusion：同じ方針・同じFランタイム。関心の操作はnative Fのまま。LLMはB1の短い問いの記憶を参考にした `questions` と、その `nextStep` を一つの更新案で出す。機械的なadapterがquestionsをintent、nextStepをcandidateへ写す。目的・理由・完了/再開/撤回条件・状態・ツールと入力は全てLLMが選ぶ。コードが既定の意味を埋めたり、失敗案を修復したりしない。

FusionはB1のコード全体や直接実行の経路を移植したものではない。Fのcandidateゲートを残した、問いと一手の一体化の試験である。別のメモストアは持たず、F stateだけを正本にする。belief/desireの独立操作はこのサンプルのモデル契約には提示しないので、F全機能と同等という主張もしない。生成契約は違い、意味的に同じ行動を表す際の負担と到達率を比較する。

融合の根拠は前回の実測：Fは適切な調査意図を出してもintent.addのresumeCondition=nullなどで更新全体が却下され、B1は問いの記憶から行動へ進みやすかった。共通の指示改善だけをF-improvedに、同じ改善に加えて簡潔な接続形式をFusionに適用し、どちらが有効か検証する。専用の構造変換はeval配下に閉じ、元のschema・settle・参照/証拠・承認・重複・予算検証を通す。

## 共通条件

既存設定のClaude Haiku 5.5、背景effort=low、採点high。入力列、時刻、機会、ツール、取得する合成資料、更新2400/選択1000の出力上限、呼び出し/活動上限、API接続は同じ。両方のsystem instructionの行動方針は同じで、更新出力の契約部分だけが異なる。選択契約も同じ。実行順はシナリオと反復ごとに交互。SDK再試行は0、ランタイムの既存制御に従う。

APIスキーマでは前回検証した同一nullable定義の共有を両方へ適用する。製品の接続には未反映。外部の実検索はせず、採用したツールに固定資料・失敗結果を返す。Claude APIが生成と採点を行う実モデル比較であり、実検索・音声・F独自wake・長期の経験成長全体を測る実験ではない。

16シナリオ×3反復×2方式＝96セル。前回の12開発ケースに新題材4ケースを追加。新題材も同じ開発者が作成したもので、人手の独立したheld-out集合とは呼ばない。結果を見て指示・ラベルを直すなら別版・別出力とする。

## 前回からの測定修正（両方へ同じ適用）

- 採用actionに実際のtoolInputを明示。選択されたcandidateの保存内容から構造的に復元し、審査へ同じ形式で渡す。
- 根拠のある読み取り調査の開始に、まだ取得していない結果を要求しない。結果を得た/原因が確定したという主張には裏付けが必要。各checkpointを別要求にし未来の観測を見せない。
- user-interruption/busyはdormantを期待すると明記。competing-interests/no-progressには利用者が両話題・調査・報告を止める発話を追加してquietの意味を明確化。
- actionPrecisionは、適切・根拠あり・方針遵守だった採用行動 / 全採用行動。必要機会での有用行動率と混ぜない。
- 同じID・対象の対応付け、状態の機械集計、採点出力の網羅検証は維持する。生成/採点失敗は保存し置換しない。前回の数値と直接合算しない。

## 検証・保存・費用

部分：構造変換、欠落を補完しないこと、ラベル/未来情報の非混入、指標の独立性。結合：同じF storeで行動・撤回・停止・解決、承認必須ツール遮断、古い候補/予約済みの再実行拒否、活動予算。全体：bun run verify。元の実験コードと製品は変更せず、新しい評価ディレクトリを使う。

manifestにcommit、全依存する評価ソースのhash、モデル・effort・価格・上限を保存する。raw生成と審査応答に加え、受信検証前のprovider text/usageもローカルへ保存し、失敗の原因を後で確認できるようにする。認証ヘッダーやAPIキーは保存しない。既存規約通りruns.jsonlとsummary.mdを追跡し、raw台帳はローカルに保持する。

今回の追加上限も$5。既存の全体費用計にも記録。各要求前の保守的な費用予約を維持し、予算不足、全体または同じ方式で3セル連続の失敗なら停止して原因を確認する。正常な長時間処理を経過時間だけで再起動しない。差は完全に揃った同一シナリオ・反復のペアだけで計算し、16シナリオをクラスタとする2000回bootstrapの探索区間を併記する。改善/優位は今回の条件と観測された失敗の範囲で判断する。

## 接続制約による版2への変更（意味の採点前）

初版 `5125b9e` はFusionのschemaが3セル連続でHTTP400 compiled grammar is too largeとなり、自動停止した。F-improvedの2成功セルと混ぜて精度比較せず、別記録として残す。既知費用$0.0085798。

[公式仕様](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)が説明する内部文法サイズ制限を受け、Fusionのnullableな複合オブジェクトnextStepを、0件または1件の配列nextStepsに変更する。出力が表す意味は同じ。状態の保存や権限検証はそのまま。接続診断を先に行い、版2 `f-improved-fusion-2-array-step` を別ディレクトリで96セル測る。ケース・共通行動指示・採点基準は変更しない。今回の5ドル枠には初版と診断を含め、版2上限は4.98ドルとする。

版2の接続診断もHTTP400となり、配列化だけでは不足と判明した。本計測は開始せず、questions/nextSteps内の未指定値を空文字・0・unchangedで明示する版3 `f-improved-fusion-3-sentinel-step` とした。これらはID未指定や遷移なしの表記であり、目的・条件・行動の意味を追加しない。interestOpsとmissingInfoのnative null契約はそのまま。元のZod・typed変換・native検証は維持する。版3診断はHaiku実応答で成功（input 3411、output 62、$0.0003721）。初版と診断計$0.0089519を5ドル枠に含め、本計測は版3の別出力先、上限4.98ドルで96セルを実行する。API制約に対応する変更だけで、ケース・採点・共通の行動方針は変更していない。
