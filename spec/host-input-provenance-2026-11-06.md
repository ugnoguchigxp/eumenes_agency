# ホスト入力の出典契約と本流互換の仮想結合計画

2026-11-06。Memory側の追加レビューを受けた改訂計画。**先にAgencyのホスト入力契約を直し、F条件で「忘却後も無関係な会話・発案を続けられる」ことを確認する。MemoryのAPI追加やプロンプトの再調整は先行させない。** 本書は実装順の正本とする。0.1.4で`WithInput<string>`とホスト資料の`input`、推論前検査を追加し、[mock導線の結合](../docs/mock-toolchain-integration-2026-11-06.md)まで確認した。未実装の段階は下記の計画として区別する。

利用者の範囲指定により、Agencyの主用途は会話・自動発話と、エージェント主導のツールチェーン利用の発案・依頼の受渡しまで。バンドル・サブエージェントの起動や実行管理はEumenes側に置く。今回の結合成功条件は、examplesのmock実行先まで正常に導線がつながること。実モデルの行動品質の採点を、この固定判断の成功で代用しない。

## 1. 今回見直す判断

前回の仮想ホストでは、Memory公開APIによる原文保管・archive・忘却連動を確認した。一方、実験用SystemContextを固定使用し、既定のB1と、試験側が指定する過去IDを主な比較に使っていた。本流のF・独自指示・話題・TODOに対する接続完了の証拠は揃っていない。

追加レビューのF再現結果は、実験用指示だけなら新しい発話の結果を受付、独自指示またはMemory由来の話題があると拒否、というもの。提供されたstdoutを確認し、現行コードでも以下の経路と整合することを確認した。レビュー記載のAgency35件・Memory15件の試験は提供情報であり、この計画更新では再実行していない。

- `runtime.ts`のupdate/selectが、独自SystemContextやホスト資料を含む入力へ一律に`unknownInput`を加える。
- 完全な出典を申告する入口がないため、忘却journalが1件でもあると、新しい独立した発話のattemptも不完全な依存になる。
- `recordResult`はattemptとreceiptの依存を合成するため、結果受付時だけ完全な出典を渡しても解消しない。
- 本流の`api/application/agency/runtime.ts`はF、`planOnOpportunity`、`repairUpdates`、`constrainToolNames`、`findings`、`interestFormation`、`hostTopics`、`hostTodos`と独自SystemContextを使う。人格設定も指示の構成に使われる。
- 本流の話題生成は現在`{id, text}`へ投影する。元のState itemの版・scope・出典をAgencyへ渡す形にはなっていない。既存のtopic cacheの破棄だけを、派生候補の再検証済みとは扱えない。

MemoryにはRecords、State、版、アクセス、外部依存、変更通知、forget/reconcile/receiptがある。現時点で必須APIの不足は確認していない。前回レビューのR01を「独自指示だけの修正」から、ホスト入力全体の出典契約へ広げて解決する。R02の根拠重複とR03の指示整合は残すが、有料の行動調整より先に本契約を通す。

## 2. 目的と責務

| 担当 | 受け持つもの |
| --- | --- |
| Agency | 提示した入力の依存を合成・伝播する。忘却・現在性・世代・権限の検査を通った状態からだけ外向ticketを作る。意味理解・再計画は既存LLM経路で行う |
| 仮想接続ホスト | 内容と出典を同じsnapshotで取得する。観測IDとMemoryのSourceRefまたはState itemの版、アクセス、ホスト設定・仕事の版を対応付ける。保存・通知・実行前確認・削除確認を接続する |
| Memory | 利用者の情報と原文、その版・状態・アクセス・変更・忘却を既存公開APIで提供する |
| 将来の本流接続 | 仮想ホストで合格した契約を採用する。今回は本流のコード・DBを変更せず、必要差分と受入条件を引き渡す |

Agencyのintent・candidate・belief・desireを利用者のMemory Stateへ移さない。Memoryの`subject:self`は利用者を指す。`standalone/checkpoint-store.ts`は試験用のままとし、本番用Memoryの拡張・代替には使わない。新しい検索・要約・意味分類・汎用イベント基盤も作らない。

## 3. 最優先の契約

### 内容と出典を一緒に確定する

既存の`InputContext { sources, complete }`、`ProvenanceTracker`、`mergeInputs`、`dependsOn`を使う。Memory型をAgency coreへ持ち込まず、出典IDはホストが解決する不透明なIDとする。

推奨する最小の受渡しは、**値とInputContextを持つ小さな組**である。新たな推論機構や保存領域を意味しない。

```ts
// 0.1.4で追加。SystemContextSourceがこの形式を受け付ける。
type WithInput<T> = {
  readonly value: T;
  readonly input: InputContext;
};
```

- **SystemContext:** 既存の静的文字列・構成関数に、本文と追加依存を同時に返す形式を追加する。構成関数へ渡したModelDataの依存はAgencyが既に追跡し、ホストはそれ以外に使った人格設定・設定資産・Memory等の依存を申告する。本文を作った後、別時点のcallbackで出典だけを推測しない。
- **話題・TODO等:** 実際に表示した項目ごとに同じ出典情報を持てるようにする。既存型への任意metadata追加などで互換性を保ち、ModelDataを組み立てる際にmetadataを分離する。全リストを一括して完全扱いにしない。
- **入力棚卸し:** ambient、standing interests、persona、ツール説明、設定から差し込む本文も確認する。同じ契約で処理し、Memory由来の値をツール説明や設定へ移すことで依存を失わせない。APIを用途ごとに乱立させない。
- **追加依存がない静的規則:** ホストが実際に追加資料を使っていない場合だけ`{sources: [], complete: true}`を明示できる。文字列が静的という理由で、埋め込まれた利用者名・人格・資料まで出典なしと推定しない。内容を読むLLMや語句の分岐で安全判定もしない。
- **未申告:** 既存の文字列・項目は受付形式を維持しつつ、追加依存は不明のまま扱う。既存保存の不明な依存を、新しい宣言だけで完全へ格上げしない。忘却後は必要情報の不足を明示して止める。

ホストの申告は信頼境界である。Agencyは型・完全性・既知の失効・上限を検証し、Memoryへの実読出し・版・アクセスの検証はホストが行う。callbackが隠れて読んだ変数をコードから推定できるとは約束しない。

### モデルに渡した範囲だけを追跡する

1. ホスト資料とSystemContextを取得し、本文とmetadataをcloneして固定する。
2. 既存の可視性・件数・提示窓を適用する。隠されたintentや表示しない話題を混ぜない。
3. その論理呼び出しに本当に渡す観測、状態、SystemContext、話題・TODO等の全入力から依存を合成する。未使用のカタログ全体へ依存させない。
4. 忘却履歴がある場合や出典の失効が判明している場合は、依存不明も含めてLLM呼び出しと外向ticketより前に検査する。却下した呼び出しはモデル呼出数・課金を0にする。receipt時にも実際の書き直し・ツール入力を合成して再検査する。忘却履歴も既知の失効もない旧callerの受付は従来どおり維持し、そこで作った不明な依存は不明のまま保持する。新ホストは最初から完全な宣言を使う。
5. 成功した更新、candidate、attempt、receipt、履歴、archiveへ既存の追跡機構で伝播する。

通信の再試行は本文とmetadataを再取得せず、同じ固定入力を使う。修正推論は別の予算付き試行として扱い、変更されたホスト資料を旧宣言で包まない。ホストの設定・Memory状態・アクセス世代が途中で変わった場合は既存のepoch検査で結果を失効させる。

依存管理用metadataはSystemContextやモデルの資料本文へ自動挿入しない。LLMの再評価に必要な訂正・現在の状態・有効期間は、それとは区別して型付きの資料・変更観測として明示する。出典申告だけで引用可能ID、独立した証拠、実行権限を増やさない。LLMが引用した根拠だけへ依存を縮める処理は追加しない。

## 4. 「無関係な仕事を続ける」の合格条件

忘却対象Aと、別の仕事Bを用意する。少なくとも次を分けて確認する。

| 条件 | 必要な動作 |
| --- | --- |
| Aだけに依存する状態・候補・実行票 | 消去・失効。遅着結果を新しい観測・発話へ戻さない |
| Aがモデル入力に含まれたが引用されなかった結果 | Aへ依存する結果として処理する。引用なしを無関係の証明にしない |
| Bの状態・入力が完全に追跡され、Aに依存しない | Bの状態と処理位置を維持する |
| Aの忘却後、Aを除いた指示・話題・TODOでBを実行 | 更新、選択、保存、発話結果受付、再起動後の続行まで成功する |
| Bに不明な旧依存が残る | 無関係と推測して通さず、保守的に停止・除去し、必要情報を明示する |

最初から仕事単位の複雑な取消機構を作らない。既存の全体epochで一時的に推論を止めてもよいが、独立したBの状態を消さず、新しい有効な入力でBを再開できることを要求する。忘却履歴があるという理由だけで、以後すべての仕事を恒久的に拒否してはならない。

「receiptが受理される」だけでも不足する。未確定ticketを公開しない、保存済みの状態・履歴・原文にAが残らない、Bの進捗を巻き戻さない、遅着結果・古い保存・再投入でAが復活しない、までが一組の完了条件となる。

## 5. ホストの出典対応と永続化

既存仮想adapterの観測ID→Memory Record対応を拡張する。すべてを新しいRecordへコピーして一種類に揃えることはしない。

| 入力の種類 | ホストが保持・検査する対応 |
| --- | --- |
| Agency観測 | 元の観測ID・順序と、原文のMemory record/SourceRef・固定revision |
| Memoryの原文 | SourceRef、revision/digest、principal、scope、アクセス方針の版 |
| MemoryのState話題 | itemId、revision、状態・有効期間、principal/scope、必要な出典。外部依存は`state_item`へ正しく登録する |
| TODO・仕事の結果 | 既存仕事台帳のID・版・scopeと、その生成で使った全入力。Memoryへ無理に移管しない |
| 指示資産・人格・関心等 | ホスト設定/資産のIDと版、実際に参照した設定値の出典とアクセス |

同じitemIdでも版やscopeが違えば区別できる出典IDにする。IDの構造の解釈はホスト内に閉じ、Agencyは不透明な文字列として扱う。忘却通知は版をまたぐため、通知対象から過去に提示した該当版すべてへ到達できる対応を残す。最新の1版への対応だけで上書きしない。

外部依存登録は、引用でなく提示した全入力を基にする。Memoryの登録が成功しただけで本文の可用性・現在性・アクセスが確認できたとは扱わない。実読出しと権限の確認は別に行う。登録拒否、上限、mapping欠損、scope不整合を成功扱いにしない。

checkpoint、履歴、出典対応、外部依存、処理位置は整合した保存単位にする。古いrevision本文が保存に残る場合は、その依存も削除できるよう版ごとの外部IDを使う。同じexternalIdへの登録が置換であることに注意する。本文のない構成・版metadataは、忘却後の再投入や復元の検査に必要な範囲だけ保持する。

## 6. 忘却と、それ以外の変更を分ける

### 忘却

既存のjournal先行、Memoryの公開forget/reconcile、Agencyの`prepareForgetting`、revisionのredaction、epochを再利用する。ホストは次の順を守る。

1. 外向配信・実行を止め、実行中・予約済み・遅着結果をfenceする。
2. MemoryのjournalをDB外へ先行保存する。
3. 原文、Agencyの派生状態、保存履歴、archive、checkpoint、話題等のcacheを削除・失効する。派生した原文がMemoryにある場合も公開APIを使う。
4. 保存成功と削除を確認してから、当該外部依存の削除完了を返す。他のproviderや確認できない外部保持まで完了にしない。
5. 起動時・古いDB復元時はworkerより先にjournalを再適用し、変更feedを必要に応じて全再同期する。古いcursorや失われたmappingを完全な状態とみなさない。

遅れて到着した課金使用量は共通台帳へ計上する。失効した結果の本文を再投入することとは分ける。利用料を見えなくするために古い呼び出しを無視しない。媒体・provider・別の会話ログの物理削除は、この仮想結合の保証へ含めない。

### 訂正・停止・期限切れ・権限変更

これらを忘却として本文削除する方法は採らない。Memoryの変更feedと既存の現在時刻・アクセス確認から、影響するcache・状態・候補・ticketを使用保留にし、新しい資料でLLMに再評価させる。期限切れは新しい変更通知がなくても起こるため、機会・実行直前にも確認する。

重要なのは、**忘却に使う全入力依存と、行動に使ってよい現在性を混同しないこと**。訂正後も「過去の推論に旧版を使った」という依存は残す。一方、再評価された新しい候補まで旧版の履歴を理由に永久停止させない。既存revision・epoch・候補の保留を使い、必要な「要再検証」の最小metadataと解除条件を固定試験で決める。

`source.changed`を観測しただけ、cacheを消しただけ、LLMがno_changeを返しただけでは、古い候補の再検証完了にしない。旧ticketは復活させず、現在の許可された資料で検証された新しい候補/版から発行する。履歴として読める旧版を、現行の事実としてそのまま再採用しない。

この非破壊の失効処理は、最優先の忘却後継続を通した次の段階で実装する。契約の初版から違いを明記し、後からforget APIへ押し込む手戻りを避ける。

## 8. 検証の順序と停止条件

### 部分試験・API不要

- 純粋な静的指示、追加の人格設定、動的指示、話題、ambient、TODO、関心等の宣言を個別に検査する。
- 呼び出しに使った値とmetadataの同一snapshot、再試行時の一致、callerによる後続変更からの隔離を確認する。
- 未提示・非表示・提示窓外の資料を依存へ混ぜず、提示したが未引用の資料は依存へ含める。
- 忘却後の未申告・不完全、忘却済み・権限外・mapping欠損はLLM/ticket前に止まる。静的追加依存なしを明示した場合は通る。忘却前の旧callerの不明状態を、移行で完全へ格上げしない。
- 宣言を根拠IDや実行許可へ流用しない。旧snapshotの不明な依存を完全へ変えない。

### 仮想結合・API不要

本流互換の主試験はF、独自SystemContext、`hostTopics`、`hostTodos`で行う。`planOnOpportunity`、`repairUpdates`、`constrainToolNames`、findings、関心形成、出力上限（現行本流はupdate 2,400 / select 1,000 token）など本流の設定を固定し、任意の感情設定も対照で確認する。B1・実験用指示だけの試験は診断用に残す。

独自指示の資産と実際の資料の形を、版/hashを記録したfixtureへ固定する。人格・利用者情報は合成値とし、本流サーバーへ接続しない。単なる短い代替指示だけを通して「本流互換」と呼ばない。正常・不明・忘却済みの各出典条件で、指示のみ、話題のみ、TODOのみ、併用の組を確認する。

忘却Aと独立B、未引用A、実行中と遅着、receipt書き直し、履歴・archive、削除途中の異常、再投入、古いDB、通知の重複・欠番・再同期、訂正・停止・期限切れ・アクセス変更を確認する。保護を別コピーで外した反証も含める。実際のMemory配布物・一時DB・公開APIを使い、模擬Memoryだけの成功で終えない。

### 通し・実API

部分→仮想結合→ローカルverify/配布物の消費側→有料の行動評価の順とする。CIは追加・実行しない。コード変更がない今回の計画更新では、リンクと差分だけを確認し、以前の909成功等を今回の再実行結果としない。

無料結合が未合格の段階で、大量のプロンプト変更や有料評価を行わない。必要なら最初に少数のF対照で入力・結果の健全性を測り、その後に正式集合へ進む。Fを本流互換の主条件に据え、以前のB1評点との単純差分を改善量としない。高い方式だけを混ぜず、同じ固定条件で比較する。

3ラウンドの仮説・実施・確認後、または新しい根拠のない同一失敗で、原因・減った残作業・次の判断を見直す。検証中の版を固定し、正常な長時間処理を時間だけで止めない。続行の根拠がなければ同じ操作を反復せず、未解決事項と続行条件を記録する。

## 9. 費用と80点の扱い

今回の計画再検討では有料APIを呼ばない。現時点の累計既知は3.33176422 USD、以前の未確定5予約は3.7464 USD、保守的上限は7.07816422 USD（切り上げ7.08 USD）。同じ台帳と9 USDの実行policyを維持する。10 USDまでの差額をそのまま新たな実行枠とは扱わず、モデルごとの最大呼び出し予約も含めて判定する。

単体完成度の技術50%・行動30%・忘却/圧縮20%、合計80点超え・各区分75点以上という基準を維持する。両providerの必要成功80%以上・不要介入5%以下、必要/不要各20機会以上、未完了・通信障害・安全違反なしという条件も維持する。元46ケースと未使用48ケースは元のラベル・内容judge条件で評価し、小さいoracle-ID probeで代用しない。

設計が揃ったこと、固定試験が増えたこと、Memoryとの接続で原文が読めたことだけでは加点しない。現在の技術68.8点、前回版の単体71.7点はそれぞれ当時の観測値として保ち、この計画の期待点を作らない。本流の実会話・実運用の検証は、仮想ホストの合格後も別に必要である。

## 10. 採らない案とMemoryへの依頼条件

- ホスト全体へ一括で`complete:true`を付け、不明検査を迂回する。
- `recordResult`だけを緩める、journalを消す、独自指示をexperimental扱いにする。
- 引用だけから全入力依存を推測する、未使用資料まで全仕事の依存へ入れる。
- MemoryのAPI追加・独自Memoryの改造・検索の再発明を先に進める。
- 訂正や一時停止をforgetで処理する、旧版の履歴依存を消して新しい候補を通す。
- 今回の本流互換fixtureと、本流へ実際に組み込んだ実会話検証を同一視する。

公開APIでは満たせない具体的な問題をMemory側で単独再現できた場合だけ、固定版/hash、期待/実際、影響、Agencyを外した再現、受入試験を持つ改修依頼を作る。現時点ではその依頼を必要とする根拠はない。別チャットへの送信や本流変更は、この計画更新では行わない。

## 実装の現在地

値と出典を同時に固定する基本契約、表示した資料の追跡とmetadata分離、忘却後の不明依存の早期拒否を実装した。Eumenesの指示資産を使ったFのmockで、会話→発案→ホスト→mockツールチェーン/バンドル/サブエージェント→結果→発話を確認した。取消、遅着、失敗、能力拒否、独立した会話の継続も結合試験を通した。

実Memory State itemや本流仕事台帳までの完全な出典対応、訂正・停止・期限切れの非破壊失効は未完了。R02と実モデルでのR03・会話品質評価も残す。本流取り込み、実サブエージェント実行、独自Memoryの拡張は行っていない。
