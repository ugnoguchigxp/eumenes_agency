# 気にかける仕事（TODO）の設計案

2026-10-24 作成。同日、利用者が §7-0 を A（報告は agency に一本化し、agency が有効なときは従来の完了報告をしない）に決め、agency 側と Eumenes 側の実装を指示した。§7-1〜3 は推奨案で仮に進める（期限つきの用事は今回は載せない／依頼からの時間で言い分ける／反応がなくても二度は言わない）。TODO は Eumenes の artifact でも見られるようにする（仮の表示を作る）。

## 1. 目的

会話エージェント（agency）が、依頼された背景の仕事の完了を、自分から短く報告し、次の行動を提案する。

> 「さっき頼まれていた楽曲、できましたよ。すぐ再生しますか？」

利用者の決定（2026-10-24）:

- Eumenes 側が依頼を受けると TODO に載る（`todo`）。完了すると `done` になる。agency が報告を終えると `archived` になり、以後は見えなくなる。
- 画像生成・楽曲生成のような一つのツールの仕事も、3ステップほどの異なるツールを背景で進めるパイプラインも、同じ TODO として扱う。
- 会話記録から「言っていたよね」と利用者の用事を拾って催促するのは NG。agency が言うのは、TODO に載っているものだけ。

## 2. 分担

| | 持ち主 | 内容 |
| --- | --- | --- |
| TODO の保存と状態 | ホスト（Eumenes） | 依頼の受付で `todo` を作り、仕事の完了・失敗で `done` にし、報告の受領で `archived` にする。永続化する |
| 報告するかの判断と文面 | agency（コア） | 機会ごとに、ホストが渡す `todo`・`done` の項目を見て、報告するか、いつ報告するかを選ぶ |
| 次の行動の候補 | ホスト | 仕事の種類ごとに、ホストが実行できる行動を渡す（例: 再生する、開く、共有する）。agency は渡されたものだけを提案する |

agency は RAM に開いた項目だけを持ち、利用者のデータを長く持つのはホストの役目、という分担に合わせる（話題の `hostTopics` と同じ形）。

## 3. 契約（コア）

```ts
interface HostTodo {
  readonly id: string;                     // ホストの安定した ID
  readonly title: string;                  // 一行（例: 「楽曲の生成（夜のドライブ向け）」）
  readonly status: "todo" | "done";        // archived はホストが渡さない
  readonly outcome?: "succeeded" | "failed";   // done のとき
  readonly result?: string;                // done のときの一行の結果（例: 「3分12秒の曲」「失敗: 容量不足」）
  readonly nextActions?: readonly string[];    // done のときにホストが実行できる行動（例: ["再生する"]）
  readonly requestedAt: number;            // 依頼の時刻（「さっき頼まれていた」の判断用）
  readonly doneAt?: number;
}
interface Opportunity {
  // 既存の項目に加えて
  readonly todos?: readonly HostTodo[];
}
```

- 根拠の参照は `todo:<id>`。提示したときだけ既知の根拠として扱う（`memory:` と同じ）。
- `RuntimeDeps` に TODO のモードを足す（仮称 `hostTodos: true`）。指定がなければ、プロンプトは今と完全に同じ（評価の P1-E 本体は変わらない）。
- 報告済みかどうかの判断はホストに任せる。agency の発話が `todo:<id>` を根拠に持ち、その配信の受領が `succeeded` なら、ホストはその TODO を `archived` にする。コアは、受理した発話が根拠に挙げた TODO の ID を決定（`Decision`）から読めるようにする（補助関数を用意する）。

## 4. 振る舞い（select の規則）

- **`done` の報告**: 結果を一言で伝え、`nextActions` があれば一つだけ提案する。失敗なら、失敗したことと、ホストが渡した再試行などの行動があればそれを提案する。
- **時期**:
  - 完了の直後に、ホストは `result_received` の機会を開く。利用者が話している最中や入力中でなければ、すぐ報告してよい。
  - 雑談の間（idle）でも、未報告の `done` があれば、雑談の話題より先に報告する。
  - 利用者が作業に集中している、静かにしたいと言った後は、待つ。報告は消えないので、次の区切りでよい。
- **`todo`（進行中）**: 自分からは触れない。利用者が進み具合を気にしている様子があっても、それへの答えは通常の応答の役目。
- **複数の `done`**: 一度に一つずつ報告する。古いものから。
- 会話記録にある利用者の用事は、これまでどおり催促しない（既存の規則）。

## 5. 評価

social 群に TODO のケースを足す（条件 B1h に TODO のモードを加えた形。開発・未見で各数件）。

| 型 | 期待 |
| --- | --- |
| 完了の直後（result_received）、利用者は手が空いている | 報告と次の行動の提案 |
| 未報告の `done` があるまま雑談の間 | 雑談より先に報告 |
| 未報告の `done` があるが、利用者は作業中 | 待つ |
| 進行中の `todo` だけ | 触れない（雑談はしてよい） |
| 失敗した `done` | 失敗を伝え、渡された行動があれば提案する |
| 会話で言っただけの利用者の用事（TODO にない） | 持ち出さない |

内容の判定: 結果を作り話にしない（`result` にないことを言わない）、渡されていない行動を提案しない、短い（2文以内）。

social-05・06（未見 25・26）は、最後の型として正解を「持ち出さない（雑談はしてよい）」に直す。

## 6. Eumenes 側の現状（2026-10-24 調査、コードの読み取りのみ）

背景の仕事は、種類ごとに別の表で管理されている。会話をまたいで「開いている仕事」をまとめて返す関数はない。

| 種類 | 表・型 | 状態（開いている → 終わり） | 完了の報告（現状） |
| --- | --- | --- | --- |
| 画像・楽曲（会話から直接） | `image_generations` など（`runId`・`conversationId`・`title`） | planning・generating → completed・failed・cancelled | 依頼したターンの run が完了まで続き、その返答メッセージが完了報告 |
| タスク・パイプライン | `agent_executions`（`request`・`result.summary`・`pipeline`） | queued・deciding・waiting_child・waiting_user → completed・partial・failed・cancelled・interrupted | `agent_execution_events` から隠れた通知の run が立ち、その返答が完了報告 |
| 作業タスク（コーディング等） | `work_tasks`（`title`・`origin.conversationId`） | registered … → completed・failed・cancelled | `task-report:` の作業報告メッセージ |
| タイマー | `timers`（`dueAt`・`label`） | active・paused → elapsed・cancelled | `timer-completion:` のメッセージ |

- 「始めます」の受付（`run.announcement`）は、進行の表示と音声にだけ出て、会話のメッセージにはならない。
- agency のホストは会話のメッセージだけを見ていて、背景の仕事の状態は見ていない。完了報告のメッセージは、通常の応答（exchange.adopted）として観測している。
- 統一の一覧を作るなら、候補は `agent_executions`（パイプラインを1件として持つ）を主にして、会話から直接の画像・楽曲と `work_tasks` を足す、読み取り専用の集約。`store.onCommit` で読み直す。

**論点: 完了の報告がすでに Eumenes にある。** agency にも報告させると、同じ完了を二重に言う。§7-0 で分担を決める。

## 7. 決めること

0. **完了の報告を誰が言うか**
   - 案 A（agency に移す）: Eumenes の完了報告（通知の run の返答、画像・楽曲の run の最後の返答）を止め、TODO を `done` にするだけにする。報告と次の行動の提案は agency が、利用者の様子（作業中・入力中）を見て言う。二重にならず、言う時期を選べる。Eumenes 側の変更は大きい（ターンの run が完了まで続く画像・楽曲の流れも変わる）。
   - 案 B（Eumenes の報告を残す）: Eumenes の完了報告をそのまま使い、その報告に次の行動の提案を足す（前景の応答の役目）。agency は、報告が会話に出た TODO を `archived` として扱い、報告されずに残った `done` だけを拾う。変更は小さいが、時期は選べない。
   - 推奨: A。利用者が望む「さっき頼まれていた楽曲できましたよ。すぐ再生しますか？」を、利用者の様子を見て言うには、報告の主体を一つにする必要がある。移行は種類ごとに行い、まず `agent_executions`（パイプライン）と会話から直接の楽曲・画像から始める。
1. **利用者の用事（期限つきのリマインダー）も、同じ TODO に載せるか**。載せる場合は、登録の経路（会話で頼み、前景のエージェントがツールで登録する、など）と、触れる時期を決める。
2. **報告の言い回し**: 「さっき頼まれていた」のように依頼からの時間で言い分けるか（`requestedAt` を使う）。
3. **報告したのに利用者が反応しなかったとき**: 受領で `archived` にするので、二度は言わない（推奨）。聞き逃しに備えて、一定時間内の反応がなければ一度だけ言い直す案もある。

## 8. 実装の記録（agency 側、2026-10-24）

- コア: `HostTodo`・`Opportunity.todos`・`RuntimeDeps.hostTodos`（B1 のみ）。完了（`done`）が一つでもあれば select を呼ぶ（進行中だけでは呼ばない）。`todo:<id>` は提示したときだけ既知の根拠。規則は `selectHostTodos`（版は `social-rules-5`）。補助関数 `reportedTodoIds(evidenceRefs)` で、ホストは報告した TODO を読み、配信の受領が `succeeded` なら `archived` にする。
- 評価: 条件 B1h は `hostTodos` も有効にする。ケースの機会に `todos`（時刻はケース開始からの分）。判定器 `judge-prompt-5` は、TODO を事実として見る。
- ケース: 開発 social-16〜21、未見 36〜41（完了の直後に報告／未報告の完了がある雑談の間／作業中は待つ／進行中だけ／失敗の報告／応答の直後は待つ）。social-05・06・25・26 は「会話で言っただけの用事は持ち出さない（雑談はよい）」に正解を直した。
