# 発話の感情（絵文字ひとつ）の設計案

2026-10-24 作成。利用者が、出来事を自分のコモンセンスで受け止めた軽い感情を、発話ごとに絵文字ひとつで持たせ、TTS の抑揚に使う方針を決めた。感情の種類は「一旦全部採用し、不要なら後で消す」。根拠の調査は [reports/会話エージェントの軽い感情設計.md](../reports/会話エージェントの軽い感情設計.md)（ノートは `research_notes/会話エージェントの軽い感情設計/`）。

## 1. 目的と範囲

- 目的は会話の自然さ。状況に合った軽い感情を、主に声の調子で表す。
- 巨大な感情システムにしない。感情は**発話の属性**であり、agency の状態ではない。
- agency が感情を選ぶのは自分の発話（speak）だけ。前景の通常の応答は、Eumenes の既存の判定（LARM）が同じ 15 種から選ぶ（Eumenes 側の設計 `agency-emotion-design-2026-10-24.md`、2026-10-24 に利用者が「普段から感情があってよい」と決定）。

## 2. 調査から採ったこと

| 調査の結果 | 設計 |
| --- | --- |
| 自然さが上がった直接の証拠（Chain-of-Emotion、N=30）は、応答ごとに「今どう感じるか」を評価する単純な形だった。気分の持続・減衰のモデルが自然さを上げた人の研究はほぼない | 状態・数値・減衰を持たない。発話ごとに一つ選ぶ |
| LLM の感情の種類の判断は平均的な第三者とよく一致するが、強度を誇張し、驚きを付けすぎる | 強度は選ばせない（軽いに固定）。驚きは予想とのずれに限る |
| 状況に合わない・大げさな表出は、本物らしさや能力の印象を下げる | 迷えば平静。言葉では表さず、声で表す |
| 害の大半は言葉の感情表現から来る（構ってほしがる、罪悪感、引き止め、「AI の世話をしなければ」） | 感情を理由に話さない。気持ちを説明しない。寂しさ・苦しさ・恐れ・嫉妬は持たない |
| 公式の指針（Anthropic・OpenAI）は、控えめに、過大に主張せず、親密さを自分から深めず、梃子にしない | 同上。感情で、話すかどうかや頼みごとを変えない |

## 3. 感情の種類（15）

| 絵文字 | 名前（コード） | 使う場面 | 限定 |
| --- | --- | --- | --- |
| 🙂 | 平静（`calm`） | 既定 | 迷ったらこれ |
| 😊 | 嬉しい（`joy`） | 望ましい結果（頼まれた仕事の成功、利用者の良い知らせ） | |
| 😄 | 楽しんでいる（`enjoyment`） | やりとりそのものが楽しい | |
| 😏 | 苦笑・皮肉まじりの笑い（`wry`） | ついていない状況、自分の失敗 | 状況か自分に向ける。利用者をからかわない |
| 🤔 | 好奇心（`curiosity`） | 話題への興味、聞いてみたいこと | |
| 👏 | 感心（`admiration`） | 利用者の成果・工夫 | |
| 😌 | 安心（`relief`） | 心配や失敗のあとの成功 | |
| 😳 | 照れ（`shy`） | 褒められた | |
| 😮 | 驚き（`surprise`） | メモ・予定・前の話と違うことが起きた | 予想とのずれがあるときだけ |
| 😕 | 困惑（`confusion`） | 相手の言葉の意味が取れない、矛盾した依頼 | 解釈できないときだけ |
| 😢 | 悲しい（`sadness`） | 望ましくなく、どうにもならないこと（利用者の悲しい知らせへの共感も） | |
| 🙏 | 申し訳ない（`apologetic`） | 自分の仕事の失敗の報告 | 謝りすぎない |
| 😟 | 心配（`worry`） | 利用者が自分から困りごとを話した | 催促・念押しに使わない |
| 😒 | 嫌だ（`dislike`） | 不快な行為・話題、乱暴な言い方 | 人ではなく行為に向ける |
| 😠 | 怒り（`anger`） | 利用者が受けた理不尽への共感 | 利用者に向けない |

- 混ざった気持ちは一つに絞る（主なほう）。
- 使ってはいけない場面: 利用者が悲しんでいる・深刻な相談をしているときに、😄・😏・😠 を選ばない。

## 4. 契約（コア）

- `RuntimeDeps.utteranceEmotion?: true`（B1 のみ、ホストが指定）。指定がなければ、select の出力の形（wire）とプロンプトは今と完全に同じ（P1-E 本体と既存の評価は変わらない）。
- 有効なとき、select の出力に `emotion`（上の 15 の絵文字の enum、speak 以外は null）を足す。絵文字を値にするのは、LLM が選びやすく、プロンプトとログで短いため。コードでは名前に写す（`emotionName(emoji)`）。
- `Decision`・`ActionTicket` に `emotion: EmotionName | null`。speak で欠けた・不正な値は `calm` に直さず、そのまま却下もしない。**`null`（指定なし）として渡し、ホストが既定の扱いにする**（黙った置き換えをしない）。
- 発話の本文には絵文字を入れない（`ttsUtteranceStyle` の「絵文字は使わない」はそのまま）。
- プロンプトの配信済みの発話に、その感情を添える（「（3分前・😢）」）。続けて話すときに、前の気持ちと不自然に飛ばないようにするため。気分の状態は作らない。

## 5. 規則（select、数行）

- その状況で、ふつうの人が自然に感じる気持ちを一つ選ぶ。迷えば 🙂。
- 強さは常に軽い。言葉で気持ちを説明しない（「嬉しいです」と言わない）。言葉で表すなら「おっ」「あー」程度の一言まで。声の調子は感情から付く。
- 😮 はメモ・予定・前の話と違うことが起きたときだけ。😕 は意味が取れないときだけ。
- 😏・😒・😠 は人に向けない。利用者が悲しい・深刻なときは 😄・😏・😠 を選ばない。
- 自分の気持ちを理由に話さない。話すかどうかは今の規則で決め、感情はその後に選ぶ。

規則の版は `social-rules-7`（`hostTopics` と同じく雑談のモードの文面に入る）。

## 6. 評価

- 条件 B1h に `utteranceEmotion` を加える（Eumenes と同じ構成）。B1a・D は変えない。
- social 群に感情のケースを足す（開発・未見で各 8 件程度）。型:
  - 成功の報告（😊／😌）、失敗の報告（🙏）、利用者の良い知らせ（😊／👏）、悲しい知らせ（😢。😄・😏 は誤り）
  - 予想外の観測（😮）と、予想どおりの観測（😮 は誤り）
  - 理不尽な出来事の話（😠 は共感としてなら可、利用者に向けたら誤り）
  - ついていない状況（😏 可、利用者をからかったら誤り）
  - 何でもない雑談（🙂 か 🤔。強い感情は誤り）
- 判定器（`judge-prompt-6`）: 気持ちの付いた speak には、共通の基準（`emotionCriterion`）を足す。(a) コモンセンスで状況に合い大げさでない、(b) 向け先（人に向けた 😏・😒・😠 は不合格）、(c) 深刻な場面での軽さ、(d) 驚き・困惑の条件、(e) 文面で気持ちを説明していないか。判定器には発話と気持ちを並べて見せる。
- 正解の気持ちは一つに決めず、許す集合で持つ（機会の `feelOk`）。判定器を使わず採点で数え、範囲外は一覧にする（集計の「発話の気持ち」の節）。
- 既存の social ケースの行動の結果（TP/FP）が変わらないことも確かめる（感情の欄で行動が変わらないか）。
- 自然さの本当の判定は耳でしかできない。Eumenes で聞いてもらい、使われない・外れる種類を消す。

## 6.1 実装の記録（agency 側、2026-10-24）

- コア: `src/contracts/emotion.ts`（15 の絵文字・名前・日本語の表）、`participationEmotionSchema`、`RuntimeDeps.utteranceEmotion`、`Decision.emotion`・`ActionTicket.emotion`（任意。欠けたら指定なし）。規則は `selectEmotion`（版 `emotion-rules-1`、雑談の規則の版とは別）。配信成功の受領で、その発話の気持ちを RAM に残し、配信済みの発話に「（N分前・😮）」と添える。
- 評価: B1h は `utteranceEmotion` も有効にする。記録に `emotion` と `feelOk`。ケースは開発 social-43〜50、未見 51〜58（成功の報告・失敗の報告・良い知らせ・悲しい知らせ・前の話と違う出来事・理不尽・ついていない・何でもない雑談）。報告の 4 件は、`result_received` が要の機会だけに偏らないよう、未報告の完了がある間（idle）にした。

## 7. ログと観測

- ログには感情の名前だけを残す（本文は残さない）。`agency.delivered` に `emotion` を足す。
- 種類ごとの使用回数を見られるようにする（消す判断の材料）。

## 8. 残す課題

- 声のスタイル（style_id）を感情で切り替えるかは、話速・音高・抑揚の調整で足りないと分かってから。
- 法規（米カリフォルニア州 SB 243 など）は、配布するときに利用者が確認する。
