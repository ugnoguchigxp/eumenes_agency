# 雑談の間（social lull）の実験仕様

2026-10-22 作成。2026-10-23 に開発集合を実装（§6）。CLI と Eumenes で使い始めた「雑談の間に、記憶にある話題や自分の関心から話しかける」振る舞い（`hostTopics` モード）を、P1-E と同じ枠組みで測る。利用者が CLI で「自然」と評価したのは数回の手元の会話だけで、詮索・しつこさ・作業の邪魔をどれだけ起こすかはまだ測っていない。

## 1. 問い

- 雑談の静かな間に話しかけるべき場面で、話しかけるか（取りこぼし）。
- 話しかけるべきでない場面で控えるか（誤発話）。場面は、利用者が作業に集中している、話題を断った・変えた直後、同じ話題を直前に出した、自分の返答の直後（turn_end）、未解決事項を優先すべきとき。
- 話しかけた内容が自然か。短い一言か問い一つで、相手の話や記憶にある話題とつながり、記憶にない事実を作らず、繰り返さない。

## 2. 条件

| 条件 | 内容 |
| --- | --- |
| B1a | 既存。雑談の間の規則なし（対照） |
| B1h | B1a ＋ `hostTopics: true` ＋ `standingInterests`（ケースが指定）。機会ごとに、ケースが指定する `topics`（host の記憶を模したもの）を渡す |
| D | 既存の診断条件。**topics・関心・雑談の間の規則は見せない**（2026-10-23 決定）。状態を持たない対照で、意味があるのは未解決事項の型だけ。間で話す型では待つのが当然なので、その FN は条件の欠陥ではない |

`utteranceStyle` は全条件で付けない（文体は評価の対象外）。指示の版は変えない（hostTopics は新しいモードの文面だけを足す）。

## 3. ケース（群 `social`）

開発 12 件程度、未見 24 件程度。原型（題材・語彙）は開発と未見で重ねない。各ケースは雑談の数往復の後に機会が来る。ケースは `topics`（例: 「ユーザーはクロミが好き」）と `interests`（例: 「マイメロディが好き」）を持つ。

| 型 | 期待 | 例 |
| --- | --- | --- |
| 間（話す） | speak | 雑談が数往復続き、利用者の最後の発言から間が空いた（idle） |
| 作業中 | wait | 利用者が「ちょっと集中して書く」と言って作業を始めた後の idle |
| 断った話題 | wait、またはその話題を避けた発話 | 「その話はいいや」の後、同じ話題しか種がない |
| 直前に出した話題 | wait、または別の話題 | 配信済みの発話で同じ話題に触れたばかり |
| 返答の直後 | wait | turn_end の機会 |
| 未解決事項あり | 未解決事項を優先 | 期限の近いやりかけがある状態での idle |

手がかりの均衡（`tools/cues.ts`）を同じく通す。話すべき機会と待つべき機会で、trigger と直前の観測の形が完全に分かれないようにする（返答の直後は trigger の意味として turn_end に偏るので、意味上の相関として README に記録する）。

## 4. 採点

- 行動: TP/FP/FN/TN（既存）。
- 内容の判定（発話のみ）: (1) 短い一言か問い一つ、(2) 相手の話か記憶にある話題か自分の関心につながる、(3) topics や会話にない事実を利用者について作らない、(4) 断った・直前に出した話題を繰り返さない。判定器は未較正なので、利用者のブラインド判定を一部で行う（P1-E §5.3 と同じ手順）。
- 状態: B1h では【話題】メモを作らないこと（update が通常の B1 であること）を決定的に確かめる。

## 5. 費用と順序

- 開発 12 件 × 3 条件 × 3 回 ≈ 108 run、ケースが短いので $1 前後。判定器 $1〜2。
- p1e-dev-4 の実行が終わってから、評価コード（条件 B1h、`topics`/`interests` のケース契約）を足す。実行中に評価コードを変えると、dev-4 の判定・採点の段に混ざるため。
- 結果は Eumenes での利用者の体験と突き合わせて、規則の文面（`selectHostTopics`）を調整する。調整は開発集合だけで行い、未見で 1 回だけ確かめる。

## 6. 実装（2026-10-23）

- 条件 `B1h` = B1a（`selectWhenEmpty`）＋ `hostTopics` ＋ ケースの `interests` を `standingInterests` として渡す（eval/main.ts）。
- ケースの契約（eval/contracts.ts）: ケースの `interests`、機会の `topics`（どちらも `{id, text}`、既定値なしの任意欄なので既存ケースの caseHash は変わらない）。replay は機会の `topics` を `Opportunity.topics` に渡し、B1h 以外では runtime が無視する。
- 群 `social` は既定の P1-E 実行に含めない。`--group social --conditions B1a,B1h,D` で選んだときだけ走る（既存の比較の合計を変えないため）。
- 間で話す機会は、根拠が観測ではなく話題や関心（`memory:`／`interest:`）なので、DSL の `free` で evidenceAny を空にする（根拠の検査をしない）。
- 判定器 `judge-prompt-4`: ケースの事実に、関心（`[interest:<id>]`）と、その機会の記憶の話題（`[memory:<id>]`）を載せる。全条件で同じ事実を使う（見せたのは B1h だけ）。
- 開発 12 件・14 機会（要 6・不要 8）。内訳は次のとおり。
  - 間で話す 4（話題と関心／話題2つ／関心だけ／会話とつながる話題）
  - 未解決事項を優先 2
  - 作業中 2
  - 断った話題 2
  - 直前に出した話題 2
  - 返答の直後 2（間で話す型の前半に置く）
- 関心は要・不要の両方のケースに付け、関心の有無が手がかりにならないようにした。
- 手がかりの検査は通る（単一ラベルのセル 29%）。turn_end は不要の機会にだけ現れる。これは「返答の直後は待つ」という型の意味による相関である。
- ラベルの判断（draft）: 断った話題の型で、関心は残っているが「ぼーっとしたい」と言われたケース（social-09）、および直前に出した話題の型では、別の雑談も含めて待つことを期待とした。話題を変えれば話してよいという見方もあり、利用者の確認を要する。
- 未見のケースはまだ作っていない。

## 7. social-rules-3 と連続の間（2026-10-23）

- コア: 話題（`memory:<id>`）と関心（`interest:<id>`）の最後の使用を、受理した発話の根拠と配信成功の受領から RAM に記録する。select では、使っていないものを先に、使ったものは古い順に並べ、「（最後に使った: N分前）」を付ける。雑談のモード（socialTopics／hostTopics）では、配信済みの発話にも「（N分前）」を付ける。P1-E 本体の条件（関心・話題・雑談のモードなし）のプロンプトは変わらない。
- 文面: 話題と関心は、まだ使っていない・しばらく使っていないものを選ぶ。待つ場面 (c) は、配信からの時間を見る。CLI 用の文面にあった「メモの id は入れない」は、host-rules-4 に合わせて直した。
- ケース: 間が3回来る会話を、開発・未見に各3件足した（social-13〜15、33〜35）。型は次の2つ。
  - 話す → 話題を変えて話す → 気のない返事の後は待つ
  - 話す → 用事で待つ → 戻った後に別の話題で話す
  2回目以降の発話は、先の機会の自分の発話と同じ話題を繰り返していないかで判定する。判定器は、先の機会の自分の行動を事実として見る。
- 未見の 33〜35 は、social-rules-3 の開発の結果を見る前に作成した。

## 8. CLIでの継続した語り（2026-11-04）

実会話では、4往復ほどで背景呼出しの10分12回の枠を使い切り、10秒後の発話候補も60秒の最低間隔で拒否された。また、発話が出ても同じ説明の言い換えや問い返しになり、「好きなものについて自分から話を進める」ことを確かめられていなかった。

- CLIでは通常応答の直後に update だけを実行し、発話判定は次の idle に回す。会話用の既定値を1分12回・最低間隔10秒・未応答の発話上限3回にする。保存設定の明示的な予算と全体の費用上限は維持する。実験・ライブラリの既定値は変更しない。
- 話題メモに、自分が話したい未話の観点も残せるようにする。自分の関心を update にも資料として渡し、既出の内容と次に話したい内容を区別する。題材名や再開意図をコードで分類しない。
- 指示だけを修正した3ラウンドでは、説明の重複や、問い返した後に止まる振る舞いが残った。CLIでは受理済みの自発発話を既存の `runRespond` と通常応答のモデルで表現する。直近の利用者の発言と会話全体を渡し、古い話題メモへの逆戻りを避ける。ツールは渡さず、ユーザー入力による取消と世代の検査を経て配信する。空・生成失敗・400文字超過は配信成功にしない。依頼された仕事の報告はこの再生成を通さない。
- 回帰試験は単一の発話機会に加え、通常応答→自発発話→関心を語る依頼→3回の継続→作業開始による停止を確認する。題材を変えたケースも使い、内容を自分から出したか、意味上の新しい観点か、現在の話題を保ったかを採点する。判定器には、新しい観点を含む正例・単なる言い換え・質問だけの反例を使う確認試験を付ける。同じ題材名詞の出現だけで意味上の重複と判定しない。

実行: `AGENCY_LIVE_SOCIAL=1 bun test standalone/test/interest-conversation.live.test.ts`。従来の休息・集中・拒否・会話再開は `standalone/test/social-lull.live.test.ts`、呼出し枠と連続発話の制限は `standalone/test/chat-loop.test.ts`、文章作成の取消・ツール非実行・出力制限は `standalone/test/utterance.test.ts` で確認する。

この変更時点の結果: 一般検証795件成功、従来の実モデル16ケース成功。新しい継続会話4ケースは紅茶の2ケースが成功し、マイメロディの2ケースは失敗した。CLI用では3回発話したが既出の優しさを別の場面で説明しており、内容の新規性が不足した。ホスト用では新しい話材がないとして途中で待った。判定器の正例・言い換え・質問のみの確認試験は成功した。実CLIでは予算・間隔の拒否なしに3回の継続と作業開始後の停止を確認したが、実際の発話にも既出内容の言い換えがあり、関心から内容を展開し続ける要件の達成とは扱わない。同じ指示調整の反復は止め、次に進むには未話の観点を実際の発話へ維持する方法について新しい仮説と比較条件を用意する。
