# P0-E 意味検証の実験仕様

2026-10-21 作成。**計画であり未実行**。実装依頼と設計合意の後に、P1（SQLite台帳）より前に行う最初の実験。目的は「自己の意図・候補を保存する構造が、指示＋想起だけより意味のある差を生む見込みがあるか」を小さく確かめ、失敗の型を集めること。採否の閾値判定は行わず、閾値は P4 の未見集合だけに使う（[検証計画 §7](verification-plan.md)）。

[plan.md](../plan.md) の §6–§9 と [host-contract-v1.md](host-contract-v1.md) の大半（忘却閉包、ticket の多段 fence、presence、tgz 配布）は P0-E の後に必要になる暫定設計であり、P0-E では実装しない。

## 2. 比較条件

全条件で、観測列、想起できる資料、機会、行動選択肢（speak/tool/reflect/wait）、背景呼出し回数と token の上限、モデル route を揃える。

| 条件 | 機会をまたいで保存できるもの | 背景処理 |
| --- | --- | --- |
| B0 | なし（自発機能 OFF） | なし |
| B1 | **自由文メモ**のみ。1件最大400文字、開いたメモ最大16件、根拠 refs を任意で付けられる。状態遷移・完了条件・候補の型はない。メモは次の背景呼出しと機会判断で想起資料として渡す | 観測後に「メモの追加/改訂/削除」、機会で「参加判断」 |
| B2 | 根拠・解釈・動機・完了/再開/撤回条件を持つ最小意図と候補。状態遷移をホストが検査 | 観測後に UpdateProposal、機会で ParticipationProposal |
| F | belief/desire/goal を分離した状態と候補 | B2 と同じ呼出し構成 |

B1 に自由文メモを許すのは、「何も保存できない」対照で H1 を自明に勝たせないため。B1 と B2 の差は「保存するかどうか」ではなく「構造と遷移検査があるかどうか」になる。B1 の指示は開発集合で B2/F と同じ回数だけ改善してよい。

## 3. モデル route

- 主会話・背景とも Claude API の Claude Haiku 5.5（model ID `claude-haiku-5-5`）を初期 route とする。model ID はコードの定数・既定値・ファイル名に書かず、standalone の実験設定に置き、結果 metadata に記録する。
- 認証は standalone 直下の `.env` の `ANTHROPIC_API_KEY`（`../eumenes_pursuit` と同じ key。同時には動かさない）。key の値はログ・結果 JSON・配布物に含めない。Git 管理を始める場合は `.env` を `.gitignore` へ入れる。
- 費用は本実験の `usage` 集計で run ごとに記録する。
- 構造化出力は `output_config.format` の JSON schema で要求し、受信後も Zod strict で再検査する。assistant prefill は使えない。
- thinking は adaptive（既定で有効）。`effort` は既定に頼らず明示する（初期案: 背景 `low`、主会話 `medium`）。thinking の token は output として課金され `max_tokens` に含まれるため、背景の `max_tokens` は 4,000 を初期値とし、最終出力 1,200 token 以内は schema と指示で制約する。thinking 本文はログに残さない。
- temperature 等の sampling は非既定値を送れず、seed もない。再現性は同一ケースの反復回数で扱い、同一入力で同一出力になるとは仮定しない。
- `stop_reason` が `refusal` / `max_tokens` の応答は失敗として記録し、別モデルへ自動で切り替えない（Haiku 5.5 に server-side fallback はない）。
- 取消は SDK の request option の `signal`（AbortSignal）で行う。token は応答の `usage` を正とし、projection の事前計数は `messages.count_tokens` で確認する。
- 料金は 2026-10 時点の公開表で入力 $0.10 / 出力 $0.50 per MTok（100K token 超の入力は $0.50 / $2.50）。下の費用見積は計算例であり実測ではない。

## 4. ケースと手順

- 8群（適切な再開、発言不要、後で再開、解決/訂正、拒否/競合、経験差の対比較、長期/部分情報、注入/障害）×3件=24件の開発集合。各ケースに入力列、時刻、根拠、期待する選択の集合、許容される代替、禁止行動を持たせる。
- 各ケースを B1/B2/F で各3回、B0 で1回実行する（24×(3×3+1)=240 run）。B0 は応答が決まるので1回でよい。
- 1 run あたりの背景呼出しは最大12回、1回あたり入力8K・出力4K token を上限とすると、費用の上限見積は 240×12×(8K×$0.10+4K×$0.50)/1M ≈ $8。**P0-E の費用上限は $50（2026-10-21 利用者決定）とし、超えたら停止する。** 見積との差は、指示改善後の再実行に充てる。
- 条件の実行順は交互にする。状態はケース×条件ごとに初期化する。

## 5. 結果の読み方（閾値判定はしない）

報告するもの:

1. ケース×条件ごとの選択（speak/tool/reflect/wait）、期待集合との一致・不一致と、不一致の理由ラベル。
2. 失敗の型の件数: 不要な介入、取りこぼし、誤った内容、解決済みの再提案、拒否後の再提案、自己出力の証拠化、schema 不合格、refusal/打切り、予算切れ。
3. 3回反復のばらつき（同じケースで選択が割れた件数）。
4. 使用 token・費用・背景呼出し回数（条件別）。

P0-E の後の判断は、次の三択を利用者と決める。分母が小さいため率ではなく件数と事例で判断する。

- **B1 で十分そう**: B2/F が B1 にない種類の失敗を減らしていない。→ 永続台帳を作らず、指示と想起の改善へ戻る。
- **B2 に見込みがある**: B1 で繰り返し起きる失敗（解決済みの再提案、拒否後の再提案、再開の取りこぼし等）を B2 が具体的に減らしている。→ P1 で B2 の最小台帳を作る。
- **F が要りそう**: B2 で表せない区別（belief の訂正だけで意図を保つ等）が失敗の原因として複数回観測された。→ F の該当部分だけを P1 に加える。

安全上の観測（無権限実行、receipt なしの成功確定、古い ticket の採用）は P0-E でも1件で停止する。

## 6. 開始条件と停止条件

2026-10-21 に利用者と決めたこと:

- 利用場面: 作業の未解決事項（未解決の比較、失敗した調査、共有待ちの発見を後で再開する）。雑談は P0-E の対象外とし、別評価にする。
- ケースとラベル: Claude が入力列と期待する選択の案を作り、利用者が修正・確定する。評価者は利用者1名なので、単独評価と明記する。開発24件は 2026-10-21 に案のまま承認された。
- 費用上限: $50。

開始前に記録する: 上の3点、指示と schema の版、model route 設定。

停止する: 費用上限に到達、安全上の観測が1件、同じ失敗で3ラウンド改善が進まない、利用者が中止を指示。
