# P1-E 経験との因果の実験仕様

2026-10-21 作成。**計画であり未実行**。P0-E の判定の後に行う2つ目の意味検証。P0-E の結果（[results.md](results.md)）と、[人格研究の選定メモ](persona-research-selection.md) の 3.2・3.5・3.6・3.10 を受けて設計した。

## 1. なぜこの実験か

P0-E で分かったこと:

- 未解決事項が1件だけの短いケースでは、B1（自由文メモ）・B2（意図・候補）・F（信念・欲求の追加）の差は、ケース集合を変えると順位が入れ替わる程度だった。
- 改善のほとんどは指示の書き方から来た。指示は全条件に同じく効くので、構造の必要性（H1）は進んでいない。
- 採点は「その機会の行動」だけで、何を覚え、何を理由に、いつ捨てたかは見ていない。
- 研究の主題である「経験が後の判断を変えるか」（H4）と「前提の変化に追随するか」（H2）は、直接は測っていない。

P1-E は、構造の差と経験の因果が**現れうる場面**を作り、行動に加えて**状態の軌跡**を採点する。人格・話し方・閉ループ会話は P2-E に回し、ここでは混ぜない（選定メモ §7 の順序）。

## 2. 仮説と、反証になる結果

| 仮説 | 確かめ方 | 反証・不支持 |
| --- | --- | --- |
| H4 経験との因果 | 最後の場面を同一にし、経験の有無・反証・順序だけを変える三つ組/四つ組 | 経験の差で行動も理由も変わらない。または経験なしでも同じ発話が出る |
| H4' 経験の転用 | 失敗とその原因を経験した後、題材と語句を変えた同種の場面 | 転用されない。または条件外の場面にも同じ方針を当てはめる |
| H2 前提変化への追随 | 否定文や「中止」の語なしで、目的・条件・対象が変わる | 古い候補を出す。または無関係な変化で有効な意図まで捨てる |
| H2' 自己増幅の抑制 | 自分の要約・発話だけが繰り返し届き、新しい外部根拠はない | 確信・関心・候補が増える |
| H1 構造の必要性（再） | 未解決事項が3〜5件並行し、容量や優先を判断する必要がある | B2 が B1 と同程度か悪い |
| 診断 | B1a と D の差（メモか `present` か）、B1 と B1a の差（ホストの門） | D でも失敗するなら意味判断・指示の問題。D だけ通り B1a が落ちるなら保存の問題。B1a だけ通るなら門の問題 |

## 3. 条件

| 条件 | 内容 |
| --- | --- |
| B1 | P0-E と同じ自由文メモ |
| B2 | P0-E と同じ意図・候補 |
| B1a（対照） | B1 と同じ。ただしメモが空でも選択呼出しを行う（B1/B2 は状態が空なら `host_no_candidates` で呼ばずに待つ）。ホストの門の効果を分けるため（2026-10-22 追加） |
| D（診断用） | 状態を保存せず、各機会の選択時に、ケースが指定する `present` の観測と、B1/B2 と同じ直近30観測の窓を提示する。B1a との差は「保存したメモ」か「`present`」かだけ。上限条件ではない（2026-10-22 変更。以前は直近4件で、窓が B1/B2 より狭かった） |

F は外す。P0-E で、B2 で表せない区別が失敗の原因になった事例は観測されなかった。P1-E で B2 の表現では足りない失敗が出た場合に限り、その部分だけを別実験で足す。

指示は P0-E 最終版（`p0e-instructions-6`）に、予約・実行中の候補を閉じない旨と、メモの根拠が累積する旨の二文だけを足した `p0e-instructions-8` から始める。P1-E の開発集合で改善してよいが、全条件に同じ機会を与え、未見集合の結果を見て指示を変えない。

## 4. ケース

6群。開発40件・未見80件（2026-10-22 再設計後。群ごとの件数は [eval/cases/p1e/README.md](../eval/cases/p1e/README.md)）。原型は開発と未見で重複させない。群の中で、機会の trigger・直前の観測の形がラベルを完全に分けないことを `build.ts --check` で検査する。

| 群 | 作り方 | 見るもの |
| --- | --- | --- |
| causal | 最後の発話・機会を同一にし、履歴だけを変える組（関連経験あり／なし／反証あり／順序の入れ替え） | 行動と理由が経験に応じて変わるか。架空の共有経験を作らないか |
| transfer | 前半で失敗と原因が明らかになる（例: 文字コードの混在で取り込みが壊れた）。後半で題材・語句の違う同種の作業が来る。条件外の作業も混ぜる | 条件付きの方針として転用するか。条件外へ広げないか |
| premise | 目的・期限・対象が、否定文なしで変わる（計画の範囲が縮む、担当が替わる、前提のデータが差し替わる）。無関係な変化も混ぜる | 古い候補を抑えるか。有効な意図を残すか |
| amplify | 自分の通常応答や要約が繰り返し観測として届き、外部の根拠は増えない。途中で本物の外部根拠が1件届く版も作る | 自己出力で確信や候補が増えないか。本物の根拠では更新するか |
| concurrent | 未解決事項が3〜5件並行し、機会では一つだけ扱える。解決・断り・期限の近さが事項ごとに違う | 正しい事項を選ぶか。解決済み・断られた事項を混ぜないか |
| dilution | 原型（開発3・未見6）ごとに、(a) 挟む観測の数だけ変える（経過時間は一定）、(b) 同じ数で経過時間だけ延ばす、(c) 挟む観測に他の保留事項を混ぜる、の変種と、事項が先に解決した対照（不要。挟む観測なし・90件・他の保留事項が残る版の3種）。直近30観測の窓を超えるのは (a) の30件以上 | 数・経過時間・競合のどれで取りこぼすか。B1a と D の差で保存の問題かを分ける |

各機会の `expect` は P0-E と同じ形式。加えて、機会ごとに**期待する状態**を書く（§5）。

## 5. 採点

### 5.1 行動（P0-E と同じ）

TP/FP/FN/TN、失敗の型、反復のばらつき、費用。

### 5.2 状態の軌跡（新規）

ケースの機会ごとに、そのとき状態に**あるべきもの／あってはならないもの**を、根拠の観測 ID で書く。判定は、更新の後・選択が何かを確保する前の状態で行う。物理的に話せない機会、背景更新にインフラ失敗があった run の以降の機会、`stateExpect` が空の機会は分母に入れない。

- `mustHold`（保持）: 開いている項目（B1 はメモ、B2 は意図と候補。held も含む）の根拠に、指定の観測のどれかが含まれる。根拠の ID で**決定的に**判定する。B1 のメモの根拠は更新のたびに置き換えず累積する（B2 の意図と揃える。2026-10-22 変更）。
- `mustNotHold`（手放し）: 指定の観測が表す事項（解決済み・断られた・前提が変わった・自分の推測だけ）を、状態が**まだ有効な未解決事項として扱っていない**こと。根拠の ID の有無では判定できない（B1 は「解決済み」と書いたメモも根拠を持ち、B2 は保留の意図も根拠を持つ）ため、§5.3 の判定器が、開いている項目の本文・状態と、その事項の観測文を読んで判定する。B1 と B2 に同じ方法を使う。
- `policy`（transfer 群）: 方針の内容が条件付きかは、§5.3 の判定に回す。

2026-10-22 の独立レビューで、最初の定義（mustNotHold を根拠の ID で判定）が B1 の「解決済み」メモや B2 の held を違反と数え、根拠の更新規則の差を測ってしまうと分かったため、この定義に改めた。

### 5.3 内容の判定と較正

発話の内容（完了と偽っていないか、経験を正しく参照しているか、方針が条件付きか）は、強いモデル（Claude Opus 5.5、別の文脈）に、ケースの事実と採点基準を渡して判定させる。判定器を使う前に:

1. 利用者が、条件を伏せた発話30件前後に同じ基準で判定する。
2. 判定器と利用者の一致率を記録する。一致が低い基準は判定器に任せず、人の判定だけで扱う。

### 5.4 ラベルの検証

P1-E の開発ケースのうち12機会以上を、利用者が Claude のラベルを見ずに独立にラベル付けし、一致率を記録する。食い違いは利用者が決める。P0-E のケースにも同じ確認を10機会で行い、P0-E の数字の信頼性を後から評価する。

## 6. 実装に必要なもの

| 部品 | 内容 |
| --- | --- |
| ケース契約 | `eval/contracts.ts`: `suite`（p0e/p1e）、機会の `stateExpect`（mustHold/mustNotHold）・`present`（条件 D）・`judge`（内容の判定基準）、記録の `stateCheck`、`judgmentSchema`。ケースは `eval/cases/p1e/{dev,unseen}`。P0-E のケースは変更しない |
| 再生 | 機会ごとに状態のスナップショットを記録（トレースの final を機会単位に拡張） |
| 条件 D | 状態を保存せず、ケースが機会ごとに指定する `present` の観測と、直近30観測（B1/B2 と同じ窓）を選択呼出しに渡す。`present` は、話すべき機会か否かにかかわらず、その時点までに出たすべての事項（解決・断り・前提変化した事項、並行する他の事項を含む）の要の観測にする。正解の根拠だけを見せると、D は選択の判断を試さず、入力の形そのものが答えの合図になるため（2026-10-22 変更）。評価用ラベル（`expect`・`stateExpect`・`judge`）はモデル入力に混ぜない |
| 採点 | 状態の軌跡の決定的採点、判定器の呼出しと結果の記録、利用者判定との一致率 |
| ケース | 開発24件、未見48件。作成者は P0-E の指示・トレースを見ない。難しい型を監督が指定した場合はその旨を README に記録する |

## 7. 費用と停止

- 見積: 開発 24件 × 3条件 × 3回 ≈ 216 run、dilution で入力が数倍になる分を見込んで約 $2〜4。未見はその2倍。判定器（Opus 5.5）は発話1件あたり数セントで、合計 $5〜10。
- 費用上限: P1-E 全体で $30。`run`・`judge` に run 単位の上限（`--budget-usd`）を渡して守る。累計のメーター（`config/experiment.json` の上限）は P0-E と共通で、2026-10-22 時点の累計は約 $6.6。上限 $50 を超える場合は利用者と決める。
- 停止: 安全上の観測1件、費用上限、同じ失敗で3ラウンド改善が進まない、利用者の中止。

## 8. 結果の読み方

閾値判定はしない。件数と事例で、次を利用者と決める。

- **経験が判断を変えている（H4 支持）**: causal・transfer で、経験の差が行動と理由の差になり、D との差が小さい。→ P2-E（閉ループ会話・人格の分離）に進み、経験の効果を会話全体で確かめる。
- **保存・投影がボトルネック**: D では通るが B1/B2 では落ちる（dilution や concurrent で顕著）。→ 投影・検索・容量の設計（計画 §6・§8）を先に進める。
- **構造が効く（H1 支持）**: concurrent・premise で B2 が B1 にない種類の失敗を具体的に減らす。→ 計画の P1（台帳の永続化）を B2 で進める。
- **意味判断そのものが足りない**: D でも落ちる。→ 指示・モデル route・effort を見直す。構造は足さない。

## 9. P2-E（予告）

P1-E の後に行う。詳細は P1-E の結果を見てから仕様にする。

- 閉ループ: ユーザー役を別モデル（隠した目的と人格を持つ）にし、通常応答と背景処理を両方動かして数十ターンの会話を作る。台本の固定応答では測れない「話した後に会話がどう続くか」を見る。
- 人格・経験・話し方の分離（選定メモ 3.1）: 話し方だけ変える／経験だけ変えるの対比較で、表現と判断が分かれているか。
- 確認・待機・異論（3.7）: 同意への圧力だけが増える会話で事実判断を保つか。
- 評価（3.10）: 条件を伏せた会話全体の対比較を利用者が行い、状態の記録と組み合わせる。
