# agenda エージェントの評価（2026-11-10 夜、独立レビュー）

対象はコミット 2921cb7（2026-11-10 23:24）の `bun run agenda` と `src/agenda/`、`eval/agenda/` である。問いは2つ。(1) 個々の場面を直すために足した規則が、その場面だけに寄りすぎていないか。(2) 能動的に話しかける会話エージェントの実装として妥当か。この評価ではコードを変更していない。[今朝の評価](agenda-review-2026-11-10.md)と[進捗](agenda-progress-2026-11-08.md)が前提である。

## 1. 結論

**(1) 特定の要件に寄りすぎていないか: 仕組みの層は寄っていない。言葉の層は寄っている。**

- コードで決めた仕組み（静かな時間の長さはコードが決める、約束した調べものは黙って消さない、話しかけの停止は利用者の発言で終わる、項目は根拠の id を持つ）は、場面を選ばない規則になっている。
- 言葉の表面を読む正規表現は、別の言い回しで外れる。実際に確かめた誤判定がある。「ご出身はどちらですか？」は二択として、「そのあと、どうなりましたか？」は二つ目の質問として書き直しになる。断りの判定は「不要です」「見なくていいです」を読めない。
- プロンプトの規則は、ログの文をそのまま写したものが増えている（「そうかあれ〜か」「決めつけていました」）。返事の指示は約4,600字、38項目ある。規則を足した後の CLI（21:24 の回）でも、メモの id を口に出す、正しかった前の発言を「誤りでした」と取り消す、頼んだことを2回言う、が出ている。
- 「同じテーマは調べない」に時間の考えがない。天気・ニュース・上映時間のように日で変わるものが、古いメモを理由に断られる（文字の重なり 0.69〜0.78、しきい値 0.6）。
- 「今の話題」を、5分という時間と、モデルが自分で挙げた根拠の id で代用している。利用者が話題を替えても、5分以内の前の話題の質問が出る（亡くなった猫の話の20秒後に暖房の質問）。
- 部品の試験は、直した場面そのものを測っている。言い換えや別の話題での確かめがない。ただし、部品で効いても実モデルで効かない変更を3件不採用にしており、この歯止めは働いている。

**(2) 会話エージェントの実装として妥当か: 骨組みは妥当。速さと話題の扱いが弱い。**

- 「いつ・どれを話すかはコード、中身はモデル」の分担、純粋な規則（`pacing.ts`）、時計の注入、利用者の発言で古い仕事を捨てる仕組み（epoch）、約束の引き継ぎは、この種のエージェントとして筋がよい。固定試験は 1136 件すべて通る。
- 設定の10秒は実際の間隔になっていない。夜の CLI では自発の間隔の中央値が47秒、利用者の発言から最初の自発まで18秒で、今朝（20.7秒）からほぼ変わらない。計画・チェック・話す文が直列で、進行中の呼び出しを取り消せない。
- 自発1回あたり、背景のモデル呼び出しが4回以上かかっている（15分・自発21回に対し、計画41回、話す文28回、調べものチェック15回。質問の確認の回数はログにない）。
- 状態のうち、聞いた質問・断られたこと・会話は再起動で消える。メモは91件に増え、見る範囲が部品ごとに違う（計画12件、返事6+8件、重複の判定は全件）。
- 返事と自発の発話が別々のモデル呼び出しで、同じ受け答えを2回する場面がある。

## 3. 特定の要件に寄りすぎている箇所

### 3.1 言葉の表面を読む正規表現

ログにない言い回しを与えた結果:

| 規則 | 場所 | 入力 | 結果 | 正しいか |
| --- | --- | --- | --- | --- |
| 二択の質問を断る | `src/agenda/compose.ts:139` | 「ご出身はどちらですか？」 | either_or で書き直し | 誤り（「どこ」の丁寧語） |
| 同上 | 同上 | 「週末はどちらへ出かけることが多いですか？」 | either_or | 誤り |
| 二つ聞く質問を断る | `src/agenda/compose.ts:135` | 「そのあと、どうなりましたか？」 | too_many_questions | 誤り（「あと、」が「そのあと、」に当たる） |
| 同上 | 同上 | 「お仕事のあと、よく寄るお店はありますか？」 | too_many_questions | 誤り |
| 断りの判定 | `src/agenda/text.ts:91-117` | 「不要です」「見なくていいです」「表示しなくていいよ」「その話はもういいって」「今じゃなくていい」 | どれも false | 取りこぼし |
| 質問で終わるか | `src/agenda/text.ts:75` | 「…大丈夫ですか？ 風が直接当たると、温度が安定しにくいこともあるそうです。」（12:23 の回の 689 秒の返事） | false | 取りこぼし（質問のあとに一文ある） |
| 同上 | 同上 | 「どんな子だったのか、よければ聞かせてください。」 | false | 取りこぼし（依頼の形の質問） |

- 書き直しは2回で項目を外す（`src/agenda/compose.ts:156`）。「どちら」で場所を聞く質問は、モデルが同じ語をもう一度使うと消える。
- `endsWithQuestion` は3つの判断に使われている。答え待ち（`src/agenda/agent.ts:258-260`、`:576-580`）、返事に渡した質問を聞いたかどうか（`:252`）、2回に1回の質問（`src/agenda/pacing.ts:113-119`）。質問のあとに一文が続くと、どれも外れる。689 秒の返事はその例で、返事が自分で足した質問は「聞いた」に数えられていない。
- 断りの判定は、計画に「断られた」と伝えるだけである（`src/agenda/agent.ts:227-239`）。計画は会話そのものも読むので、害は小さい。逆に言えば、この正規表現はなくても同じ情報が計画に届いている。

一般化するなら: 文の形の判断は、その文を書いたモデルの出力に持たせる。話す文の出力に「質問の数」「選ばせる質問か」を足し、コードはその値を確かめる。返事については、返事のあとに小さい分類の呼び出しを1回足すか、計画が会話から読む。正規表現を残すなら、上の表を固定試験に入れて誤判定を止める。

### 3.4 「同じテーマ」に時間がない

`src/agenda/plan.ts:232-243` は、新しい調べものを、これまでの調べもの全部とメモ全部の題・要約と比べ、文字の重なりが 0.6 以上なら断る。メモの古さは見ない。調べる前の確認（`src/agenda/check.ts`、`src/agenda/prompt.ts:80-91`）にも、メモがいつのものかは渡していない（`src/agenda/prompt.ts:143-152`）。

| --- | --- | ---: | --- |
| 明日の鎌倉の天気を調べる | 鎌倉の天気（11/10）… | 0.78 | 断る |
| 最近のAIニュースを調べ、重要なものをまとめる | 最近のAIニュース（11/3時点）… | 0.69 | 断る |

（メモの文は私が作った例。数字は `themeOverlap` の実際の出力）

- 利用者が頼んだ調べものは、この判定を通らない（`src/agenda/agent.ts:584-619`、`src/agenda/check.ts:53-56`）。断られるのは、エージェントが自分から先回りする分である。来週の「最近のAIニュース」や明日の天気は、頼まれない限り調べ直さないことになる。
- 返事にも「notes にあるテーマは調べ直さず、read_note で読んで答えます」とある（`standalone/agenda-reply.ts:353`）。古い天気のメモで答えるおそれがある（推測。ログでは確かめていない）。
- もとの要望は「同じ結果を何度も受け取らない」（11-08）で、掘り下げが同じ主題を回る問題への対処だった。その場面には効いている。日で変わる情報という別の場面を考えていない。

一般化するなら: メモに「いつの情報か」を持たせ、確認の呼び出しにメモの古さと依頼の中の日付を渡す。コードの文字の重なりで断るのは、実行中・待ちの調べものと、新しいメモ（たとえば24時間以内）に限る。

### 3.5 「今の話題」を時間と自己申告で代用している

- `holdsElsewhere`（`src/agenda/pacing.ts:151-152`）は、利用者が5分以内に話したかだけを見る。`tiesIn`（`:73-87`）は、項目の根拠が5分以内の言葉（利用者・返事・自発のどれでも）に当たるかを見る。
- 根拠の id はモデルが自分で挙げる。コードは id があることは確かめるが、中身がつながっているかは確かめない（`src/agenda/plan.ts:166`、`:188-195`）。
- 計画の指示は「共通点がある記憶なら、会話の言葉の id と記憶の id の両方を入れて足します」と教えている（`src/agenda/prompt.ts:39`）。会話の id を1つ添えれば通る。

12:23 の回で起きたこと:

| 秒 | 起きたこと |
| ---: | --- |
| 714 | 利用者「これから冬だから温度管理が難しいかもね」 |
| 806 | 利用者「前にもう一匹三毛猫がいたのですが…一昨年あたりに死んじゃいました」 |
| 854 | 利用者「エリと、あみちゃんは同時に飼ってたときも…」 |
| 874 | 自発の質問「そういえば、印刷する部屋の暖房はどんなものを使っていますか？」 |

暖房の質問は、5分以内の言葉（714 秒）につながるので「会話中の話題」として通る。利用者は話題を替えていて、しかも重い話だった。同じ回で、会話につながらない案は18件断っている。断る仕組みは働いているが、モデルは断られる案を出し続けており、そのたびに計画の呼び出し（約6.6秒）を使う。

この規則のもと（「フォーカスから外れている事をいきなり振ると違和感」）は一般的な要求で、方針として正しい。実装の「フォーカス」の定義が粗い。

一般化するなら: 「今の話題」を、利用者の直近の1〜2発言とそれにつながる項目、と定義する。計画の出力で各項目に話題の名前を付け、利用者の最新の発言の話題と違う項目は、会話中は後回しにする。5分の時計は、会話が終わったかの判定だけに使う。

### 3.6 約束を守る規則の条件

`src/agenda/plan.ts:117-127` は、頼まれた・引き受けた項目を、利用者が次に話すまで計画が外せないようにした。もとの場面（引き受けの7秒後に外した）には効く。ただし条件は「利用者が何か話したか」で、取り消したかどうかではない。利用者が「うん」と言えば、その後は外せる。12:23 の回の利用者は平均40秒ごとに話しており、調べものは数分かかる。守られる時間は短い。

一般化するなら: 頼まれた・引き受けた項目を外せるのは、利用者の取り消しがあるときだけにする。計画の drop に理由の種類（`user_cancelled`）と、取り消した発言の id を付けさせ、コードがその発言が項目より後かを確かめる。

## 4. 会話エージェントの実装としての妥当性

### 4.1 良い点

- **分担がコードに表れている。** 時刻と順序の規則は `src/agenda/pacing.ts` の純粋な関数で、モデルを呼ばない。計画・確認・話す文は、それぞれ出力の形が決まっていて、コードが受け入れを判定する（`src/agenda/plan.ts:150-243`）。モデルの出力を信用しすぎない作りである。
- **試験がしやすい。** 時計とタイマーは注入で（`standalone/agenda-session.ts:96-98`）、中核はホストに依らない（`bun scripts/check-boundaries.ts` で検査）。agenda の試験は 4,109 行ある。
- **割り込みの扱いが一通りある。** 入力中と返事中は話さない（`standalone/agenda-session.ts:126`、`:261-269`）。書いている間に利用者が話せば捨てる。返事は記憶の書き込みを待たない（`:332-362`）。
- **失敗の道がある。** 計画の失敗は次の情報まで待つ（`src/agenda/plan.ts:83-91`）。確認の失敗は60秒後にやり直す（`src/agenda/check.ts:86-102`）。step の例外は60秒あける（`standalone/agenda-session.ts:222-225`）。4本のログで例外は0件だった。
- **資料と命令を分けている。** メモ・記憶・会話は資料として渡し、`<` `>` を逃がす（`src/agenda/prompt.ts:181-185`）。忘却は、根拠をたどって連鎖する（`src/agenda/agent.ts:665-696`）。
- **約束を保つ。** 再起動で、開いている約束と静かな時間を引き継ぐ（`src/agenda/agent.ts:707-738`）。

### 4.3 方針との関係

- 「10秒に1度」は、今の作りでは届かない。待ちの規則を外しただけでは足りず、A〜C を直す必要がある。方針に無理があるのではなく、実装が追いついていない。
- 「発話を減らす規則は入れない」と「フォーカスの外をいきなり振らない」は、受け身の利用者の場面でぶつかる（ag50・ag54 の不採用）。両方を満たすには、つながる材料を増やすしかない。3.4 の「同じテーマ」の扱いは、その材料を減らしている。
- 「モードを作らず、場面ごとの規則を持つ」は、規則をコードの仕組みに置く限り保てる。プロンプトの文として足し続けると、3.2 のように干渉が増え、場面ごとの試験が要る。これは方針そのものの費用で、規則をまとめ直す作業を定期的に入れる必要がある。

## 5. 評価の仕組みの妥当性
