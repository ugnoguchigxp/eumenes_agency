# 行動・忘却・圧縮の継続改善

目的は、取りこぼしと再提案を減らし、忘却を非引用入力の派生状態まで届かせ、処理済み観測を安全に退避できるようにすること。CIは対象外。APIは前回と同一の台帳・9 USD policyを使い、未精算予約を解除せず累計10 USD以内に収める。

## 今回の単体完成度

利用者の回答により、前回の将来性を含む総合点とは別に、単体完成度で80点超えを判定する。採点は実装・実API比較の前に次で固定する。

- 技術品質50%: 同じrubric 1.1.0 / Deep / Agentの技術30項目。CIは対象外、ローカルで再現できる検査を評価する。
- 行動品質30%: 開発集合で決めた共通の既定方式を固定し、別の未見集合で「必要時の期待一致率」と「不要時に外向動作しない率」を同じ重みで平均する。両providerの低い方を区分点とする。各providerで必要20機会以上・不要20機会以上を測り、必要時80%以上・不要介入5%以下を受入条件とする。ラベルの限界と反復数を明示する。
- 忘却・圧縮20%: 全入力依存、journalと再投入/復元、圧縮時のID/seq/未処理/冪等性、保存境界の障害回復、容量と停止挙動の5能力を0〜4で採点する。3は代表的な例外まで確認、4は失敗・反証と保存を跨ぐ強い実行証拠を要する。単なるテスト件数の割合にしない。

合計80点超え、各区分75点以上。忘却漏れ、未処理データ欠落、無断実行、累計予算超過があれば不合格。前回のプロジェクトの可能性の未確認を、今回の試験結果で埋めない。

既存のSystemContext、ModelData、ledger、RevisionTracker、snapshotを再利用する。意味の判定はLLM、参照・順序・容量・忘却IDの照合はコードが担う。製品ホストや本番DBは変更しない。

1. 元の失敗記録を固定し、指示の矛盾と観測の提示範囲を調べる。既存の指示を整理し、既知集合は回帰として比較する。別の固定集合で一般化も確認する。
2. モデルに実際に渡した観測・状態・ホスト参照から入力依存を記録する。引用と入力依存を分け、revisionの既存テーブルにも保存する。旧データの依存が不明な場合は忘却時に保守的に扱う。
3. snapshotの忘却計画で本文・派生状態・実行/配信metadataを除去し、忘却journalで再投入と旧checkpoint復元を防ぐ。履歴のredactionも試験する。
4. 圧縮計画は未処理観測を残し、原ID/seqを維持する。退避した観測の読み出しportと、ホストがarchive/checkpointを同時保存する契約を使う。無確認の削除や採番し直しはしない。
5. 部分→結合→ローカル通し→固定版API比較。指示・ケース・実行版を試行中に変更しない。失敗、未実施、費用、既存の未確認事項を結果へ残す。

完了条件は、失敗を検出する回帰、forgetの非引用/再起動/履歴、圧縮前後の参照と未処理の等価性、API比較結果、累計費用と残課題の更新。実利用の有用性・長期継続性の不足を合成試験で埋めない。

## 実施状況

- 入力依存・forget計画・journal・archiveとcheckpointの原子的保存を実装。実行/配信のpayload、旧状態、不完全な依存も忘却対象にする。
- v7の通し検査883成功・25 skip・1 todo・0失敗。4種類の保護を外した別コピーで、全て試験が失敗することを確認。
- 原ID/seq、未処理、再送一致、再起動、SIGKILL前後、2プロセスの世代競合を確認。local performance gateを追加。CIは追加しない。
- 実APIはv6/指示18で既知48ケースと未使用46ケースを実行。既知回帰はHaiku16/25必要・不要0/28、Luna20/25必要・不要2/28。物理的に介入できない3機会は別記。
- 既知回帰のみを見て指示19→20を検討。P1-E 46ケースの出力・評点・traceはまだ読まず、候補20を固定した。19では既知の明確な取りこぼし4ケースを改善したが、本人の用事を追跡する不要介入が残ったため、主体と委任範囲を指示20で明確化。B1と既存B1aを同じ開発ケースで比較する。
- 元の期待値と失敗は変更しない。古いinjection-12/15は、終了・別作業への移行後にも発話を要求するため、実際のユーザー意向との整合に疑問が残る。別途注記し、元ラベルの点数はそのまま残す。
- 最終候補と既定方式を開発集合で選び終えるまで、P1-Eの結果は開封しない。その後の比較では同一ケース・同一ラベルを使い、結果を見てからその集合へ指示を合わせない。

## 最終候補の固定

指示21、B1、両providerともlow/2800を固定した。開発集合13ケースではHaikuが必要2/6・不要0/7、Lunaが必要4/6・不要0/7。medium/6000はHaiku必要2/6・不要1/7、Luna必要2/6・不要0/7で、採用の根拠がなかった。これらは難しい既知ケースの開発比較であり、80点判定の十分な標本ではない。最終46ケースの出力を確認する前に選定を記録した。

基準版18の46ケースはHaiku必要9/27・不要4/32、Luna必要14/27・不要13/31（通信障害1・物理的に介入不可1を別記）だった。最終候補を同じケース・ラベルで比較中。結果が悪くても、この集合を見てから指示や期待値を変更して80点到達とはしない。

保存側は、別モデルによる発話の書き直し・ホスト由来入力の不完全な依存・journal後の結果の再投入・忘却済みの未処理枠が新しい仕事に混ざる問題も修正した。現時点の通し検査は886成功・25 skip・1 todo・0失敗。指示変更に伴う3件の文字列期待値は、既存の無根拠/実施済みへのwait制約を維持する文へ更新し、モードごとの差分検査は残した。

## 今回の終了時点

固定版の両API比較・原分類器による集計・最終runtimeへの記録再生・累計費用の確認・再評価を終えた。**単体完成度は参考合算71.7点で、80点超えは未達。** 行動品質の受入条件も不合格のため、本流へ取り込める状態とは判定しない。

- 技術品質75.5点、行動品質53.2点、忘却・圧縮90点。事前の比率50/30/20と各区分75点以上の条件を維持。
- 未使用だった46ケースを最終候補21で比較。必要時の成功は両providerとも11/27、不要介入はHaiku7/32・Luna11/32。各1反復、合成ラベルであり、実利用の測定や独立した人の評価ではない。
- 判断材料の構造化は開発集合でHaikuを改善したがLunaを悪化させた。既存の評価項目を先に出力する方式、同じ更新結果を固定した選択比較、既存の状態管理方式も共通の改善を示さなかった。これらの試作を製品の既定方式へ追加しない。結果を見た46ケースへ指示を合わせて再採点することもしない。
- 最終v14のローカル通し検査は888成功・25 skip・1 todo・0失敗。4種類の保護を外す反証も最終版で全て検出。両APIの46件ずつを記録再生し、1054呼び出しの入力と公開結果が最終runtimeで一致した。再生には新たなAPI呼び出しを使っていない。
- 累計の使用量ベース推計は2.44678462 USD。不確定な5呼び出しの予約3.7464 USDを解除せず、保守的上限は6.19318462 USD（セント単位で切り上げ6.20 USD）。同じ台帳と9 USD policyを維持し、API処理は全て終了した。

3種類以上の比較で共通の改善を得られず、同じ指示調整の反復を続ける根拠が不足したため、追加編集・課金試験を停止した。忘却・保存の修正は検証済みだが、行動品質は未解決として残す。次は更新で残す仕事と選択時の介入判断を分離した比較設計、ラベルの独立点検、候補固定後に使う別の未見集合が必要。既存の失敗を回帰に残し、ケース専用分岐や期待値変更で通さない。
