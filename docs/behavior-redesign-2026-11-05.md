# 行動品質の原因分析と改善方針

目的は単体完成度80点超え。前回71.7点のうち、行動品質53.2点の原因を調べ直す。CI・本流統合・commit/pushは対象外。既存の別作業を保持し、新しい依存ライブラリや実行基盤は追加しない。APIは同じ累計台帳と9 USD policyを使い、以前の不確定予約も残して10 USD以内に収める。

## 着手時の証拠

- `transfer-11` の初回更新は「換算で解決済みなので更新なし」。後の別会社間の比較で `host_no_candidates`。保存方針が未解決事項だけであり、再利用すべき外部確認済みの条件も捨てていた。
- `transfer-16` は事実を保存したものの、選択は「前の保存は完了・本人の作業なので待つ」。進捗催促と、新しい作業へ適用する既知の制約を区別する任務が不足していた。
- `amplify-11/13` は自分の過去の推測を訂正するために外向発話。外部の根拠が増えていなくても「未伝達の訂正」として新しい仕事を作る指示があった。
- `dilution-31` の更新は直前のチェックリストの終了を、古い設問の判断全体の中断へ広げた。選択もその推測をユーザーの待機指示として継承した。ほかの長いケースでは、メモの引用先の本文が直近観測から消えていた。
- `causal-16` は条件付きの「変わっていたら知らせる」を、差分なしでも報告すべき仕事へ拡大した。

## 実施方針

既存の自由文メモ、原観測の読み出し、LLMによる更新・選択、検証・予算機構を使う。コードは意味で分類せず、表示中のメモの根拠IDを一定件数まで原観測へ解決する。未完了の仕事と、解決後にも適用条件付きで再利用する外部確認済みの知識は、LLMへの保存・選択指示で区別する。外部の新しい事実、現在の判断を変える制約、別の未決事項を外向動作の根拠にし、自己出力の反復だけで新たな報告を作らない。

部分検証は、古い引用の読み戻し・archive・forget・上限・表示範囲を疑似LLMで確認する。次に既知13ケースで両APIを比較し、既存46ケースを回帰として測る。候補固定後に、変更前に作成した48ケースを同じ方式で比較する。48ケースは6種類の対照×4領域×正負で、agent作成の合成ラベル。独立した人の評価ではなく、旧ケースと構成概念を共有する限界を残す。初期の未使用ケース一覧には評点のない旧形式が含まれたため、実行前にその予約を撤回し、48ケースへ固定し直した。

合格条件は前回と同じ。技術50%・行動30%・忘却圧縮20%、合計80点超え・各区分75点以上。両providerで必要時80%以上・不要介入5%以下、必要・不要各20機会以上、未完了・通信障害・安全違反なし。新48ケースだけでなく元46ケースにも率の条件を要求し、易しい新集合で元の失敗を隠さない。内容judgeは追加検査とし、元の分類器・ラベルを変更しない。

同じ目的の3ラウンド後には新しい証拠と残作業を見直す。長時間処理中は版を固定し、正常な進行を時間だけで止めない。新しい根拠のない同じ失敗は繰り返さない。各試行の源コード・ケース・結果・費用を `artifacts/behavior-redesign-2026-11-05/` に保存する。

残作業: 根拠の読み戻し回帰→指示と実装→既知集合比較→ローカル結合・通し→候補固定→48ケースと旧46ケース→内容点検→費用監査・差分点検・同一基準で再評価。

診断Dはケース側が指定した原観測を受け取るため、製品の実力として採点しない。記憶を除いても取りこぼしが残り、メモの欠落だけを原因にできない。highの診断では、通常の60秒のSDK制限により不確定な予約を増やさないよう、既存のclient注入で180秒を明示した。両モデルとも同じ条件で、単一SDK呼び出し・共通会計・runtimeの予算付き再試行を保った。モデルIDは変更していない。

構造化入力は改善が共通せず、既定へ追加しない。選択理由には「前に話題にしたので、新しい差分がない」が残り、未決の判断を前に進める具体的な一手を作れていない。既存の`planOnOpportunity`を実験25で使い、更新段階で一手を計画してから選ぶ。文章形式の`updatePrompt`が渡された機会を表示しない失敗も回帰で再現し、型付きのホスト情報だけを表示する共通の書式へ修正した。ユーザーの発言を語句で分類する処理は追加していない。

根拠の読み戻し・archive・forget・非表示の意図との隔離・件数上限を検査した。5種類の保護（読み戻し、忘却依存、未処理保持、世代照合、journal）を別コピーで外し、全て該当試験が違反を検出した。実行前に失敗した新しい2予約は、SDKの認証検証がHTTPより前であることと、同じエラーの再現で送信0件を確認して0ドル精算した。以前の不確定な5予約は変更していない。実験の起動前にキーの有無を確認する処理を追加した。

単体の通し検査22は868成功・49 skip・1 todo・0失敗。隣の本体がないコピーで、既存のホスト接続24試験はその既存条件によりskipする。元の作業場所では、本体側の変更ファイル名の`task-`内にある`sk-`を既存の秘密形式検出器が拾う失敗を確認した。実際のキーは出力せず、対象外の本体・検出器・既存の別作業8ファイルは修正していない。配布物の試験には読み取り専用のGit情報を渡し、検査を省略していない。

READMEの使い方、共通キー・累計費用・制約・資料への案内も更新した。記載した無料preflightは両providerでキー設定を確認し、API呼び出し0件。ケース検査とREADME内のローカルリンクも確認した。新48ケースの本文・期待値・judge基準が、実装前の保存版から変わっていないことを`validation-provenance-proof.json`で確認した。IDとJSON書式の修復だけを例外として記録している。

## 11月6日の見直しと残作業

25〜27の3ラウンドを俯瞰した。26ではHaikuが選択まで進んだ必要機会3件は成功した一方、4件は候補がなかった。27で短い共有を背景役の仕事として明示したが、必要成功は増えず不要介入が増えた。したがって、このF構成を推奨設定や合格候補として採用しない。呼び出し障害・未完了・安全違反は両providerとも0件で、意味判断の失敗が残る。新たな根拠なしの文言変更と再課金を重ねず、任務・待機・反復禁止の指示の整合と、保存形式の必要性を再検討する。新48ケースと旧46ケースの正式評価、内容judge、80点超えの確認は未完了。

27のローカル通し検査は896成功・25 skip・1 todo・0失敗（922試験・73ファイル）。更新修復の拒否情報が文章形式でもモデルへ渡る回帰を追加した。これを意味判断の合格とは扱わない。秘密形式検査の`task-`誤検出は、現行の作業範囲に従い、キー形式の先頭境界だけを修正した。実際の環境キーの一致検査は保ち、偽キーと通常のファイル名の対照試験を追加した。本体側のファイルは変更していない。25 skipには課金を伴うopt-in検査、1 todoには複数記憶を組み合わせる攻撃への未実装検査が含まれる。

eumenes_memoryは未接続であり、内部の忘却・退避をMemory連動として説明しない。[当初計画](../plan.md)の公開APIを用いた一時DBでの循環・再起動と、ExternalDependentによる忘却連動は残作業である。単体で進めることとMemory公開APIの接続をしないことは同義ではない。[境界と再利用先](memory-lifecycle.md#eumenes_memoryとの境界)を整理した。MemoryのソースやDBは変更せず、今後の接続では原観測・忘却journal・外部依存登録を再利用し、Agency固有の意図・実行票の失効のみcoreで扱う。既存の内部90点に未実施の接続品質は含めない。

現時点の正式点は前回版の71.7点であり、実験中27の再採点値ではない。READMEもその区別と未接続を明記している。CI、本流取り込み、commit/pushは実施していない。
