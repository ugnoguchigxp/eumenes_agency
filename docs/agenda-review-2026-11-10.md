# agenda エージェントの評価と改善点（2026-11-10）

対象はコミット b23e49a（2026-11-09 23:44）の `bun run agenda`（`standalone/agenda.ts`）と `src/agenda/` である。問いは「積極的に発話し、行動できているか」。期待値は[設計書](../spec/always-on-agenda-design-2026-11-08.md)2節と、2026-11-09 の利用者の決定（自分からの発話は10秒に1度くらい、やや喧しいくらい。静かにするのは利用者が頼んだ時間だけ）とした。この評価ではコードを変更していない。それまでの経過は[進捗](agenda-progress-2026-11-08.md)にある。

## 結論

- エンジニアリングの質は高い。ローカル検査はすべて通り、「いつ・どれを話すかはコード、中身はモデル」という分担も守られている。
- 「積極的に発話する」は、利用者がよく返事をする場面では達成した。評価では自発の発話が基準の約7倍（0.10 → 0.75回/分）になり、間隔の中央値は200秒から22秒になった。
- 実モデルの評価は、18件中6件が例外で止まった（`src/agenda/check.ts:117`）。調べものの重複チェックの不具合で、最初に直す必要がある。
- 利用者が受け身の場面と、実機（CLI）では達成していない。話す量を決めているのは10秒の間隔ではなく、次の3つである。
  1. LLMの待ち時間。実機では、利用者の発言から最初の自発発話まで中央値20.7秒かかる。
  2. 話す材料の供給。相づちしか返さない利用者には、60分で3回しか話していない。
  3. モデルと返事が自分で黙る判断。利用者役が「ちょっと待って」「今はのんびりしたい」と言うと、返事が120〜720分の静かな時間を設定する。
- 「行動する」は、調べものについては達成した。話しかけを止めている間も掘り下げを続ける。ただし、できたメモの4割は話題にならず、調べるテーマは利用者の言葉から離れていく。
- 発話が増えた分、利用者役の違和感は 22% から 55% に上がった。感想は「しつこい」が最多である。対策は話す中身で行う（頻度は下げない）。
- このコミットは、実モデルで測られないまま採用されていた。また、今の評価の物差しは発話量を測らず、静かな方を高く採点する。先に物差しを直さないと、次の調整の効果を判定できない。

## 評価

### 良い点

- 分担がはっきりしている。いつ計画し、いつ調べ、いつどれを話すかはコード（`src/agenda/pacing.ts`）が決め、モデルは中身を書く。
- 固定試験が厚い（agenda だけで77件）。忘却の連鎖、メモに紛れた指示、停止中の動きを確かめている。
- 11-09 の調整は、ねらいどおり効いている。待ちの規則を外したことで間隔は200秒から22秒になり、話の流れからの掘り下げで調べものも増えた（先回り 2.78 → 3.08）。
- 意味での聞き直しチェック、メモができた時刻を返事に渡す仕組み、調べものの重複チェックは、記録の上でも働いている。

### 届いていない点

- 実機では、発話までの道のりが長い。返事のあと、記憶と予定メモの書き込み、計画、質問チェック、調べものチェック、話す文が順に走り、その間に利用者が次を打ち始める。書いた話す文の36%が破棄されている。
- 受け身の利用者には話す材料が尽きる。材料があっても、モデルの判断と返事の約束で止まる。
- 発話の種類が質問と豆知識の2つしかなく、10秒おきに同じ話題を質問で掘るので「しつこい」になる。
- 物差しが目標を測っていない。発話量の指標がなく、判定役とシナリオの期待値は静かな方を高く採点する。

## 改善点（優先順）

進め方は今までと同じにする。1つずつ実装し、4回測り、基準をはっきり超えたものだけ採用する。最初に `src/agenda/check.ts:117` の例外を直す（今は評価の3分の1が止まる）。次に1を済ませ、今のコミットを新しい物差しで4回測って基準にする。

### 1. 物差しを目標に合わせる（最優先）

| 何が起きているか | 直し方 |
| --- | --- |
| 発話量の指標がない。`compare.ts` が出すのは違和感・判定役・守る条件だけである | 自発の回/分、間隔の中央値、最長の沈黙、メモが話題になった割合、計画した項目が発話になった割合を足す |
| シナリオの期待値が古い。`eval/agenda/scenarios.ts:39` の「返事がなければ間隔を空け」、`:52` の「騒がしくしない」は、11-09 の決定と合わない | 期待値を「利用者が頼んだ静かな時間だけ控える」に書き直す |
| 判定役の加減（`eval/agenda/judge.ts:38`）が、話しかけの多さを減点する。話しかけを止めている間の調べものも「約束と合わない」と減点する | 加減の基準を、頼まれた静かな時間を守ったか、に絞る。静かな時間にも仕事は続けてよいことを伝える |
| 仮想の時計がLLMの呼び出し中に止まり、入力中も再現しない（`eval/agenda/sim.ts:262` で busy が常に false） | 呼び出しにかかった時間だけ時計を進める。利用者役の返事に入力の時間を持たせる |
| 利用者役が、すべての自発の発話に別々に、遅れて答える。10秒間隔では、古い発話への答えが後から届いて話が絡まる | 新しい発話が出たら、前の発話への答えは取り消す |
| 質問チェックで外した質問が、評価の記録に出ない | `step` の `repeats` を記録する |

### 2. 実機で話すまでの時間を縮める

| 何が起きているか | 直し方 |
| --- | --- |
| 返事のあと、記憶と予定メモの書き込みが終わるまで、話しかけも計画もできない（`standalone/agenda-session.ts:275-344`。`replying` が書き込みの終わりまで true） | 書き込みは裏で走らせる。計画は書き込みのあとに呼ぶが、すでにある項目の話しかけは待たせない |
| `step` の中で、計画・質問チェック・調べものチェック・話す文が直列に走る（`src/agenda/agent.ts:274-355`） | 話す系（話す文）と計画系（計画・チェック・調べもの）を分けて並行にする |
| 話してよい時刻になってから話す文を書き始める | 次に話す1件の文を先に書いておき、時刻が来たら出す（利用者が話したら捨てる） |
| 会話中の自発の話題は、返事と入力に挟まれて出にくい | `askIfFits` と同じ形で、つながる話題を1つ返事に渡す。ag39 の案2と違い、自発の話題は減らさない |

確かめる数字は、利用者の発言から最初の自発までの秒数（今は20.7秒）と、破棄した話す文の割合（今は36%）である。

### 3. 黙る場面を潰す

| 何が起きているか | 直し方 |
| --- | --- |
| 返事が、やわらかい言葉から長い静かな時間を設定する（12件中4件、120〜720分） | `set_quiet` の使いどころを絞る（`standalone/agenda-reply.ts:118`）。勧めを断られたことや、話題への引きは、話しかけ全体を止める意味にしない。長さが言われていないときは短くする（今の既定は60分、`DEFAULT_QUIET_MIN`）。どこまでを依頼と読むかは利用者が決める |
| 返事が「話しかけずにおきます」と約束し、あとの話す文がそれを理由に見送る | 返事に、黙る約束をさせない。話す文には、自分の前の約束を見送りの理由にさせない |
| 計画の drop（`src/agenda/prompt.ts:67`「もう意味のない項目」）と話す文の見送りで、新しい話題が消える | drop と見送りの理由を、答えが出た・期限が過ぎた・利用者がその話題を断った、に限る。理由を選択肢にして、コードで確かめる |
| できたメモのうち、話題になるのは60%である（55件中33件）。静かな時間中のメモには、話題の項目ができないものがある | できたメモは、コードが話題の候補にする。利用者が戻ったら、留守の間にできたものから話す |
| 相づち（「うん」）でも5分間「会話中」になり、つながらない話題が止まる（`src/agenda/pacing.ts:135`） | 話の流れからの掘り下げが何も足さなかったら、つながらない話題を出してよいことにする |
| 掘り下げが何も足さないと、次の新しい情報か1時間後まで何もしない（`src/agenda/pacing.ts:160-167`） | 使っていないメモや項目があれば、それを話す。なければ時間をおいて掘り下げ直す |
| 話題の締めの「表示しましょうか？」が質問として数えられ、利用者が話すまで次の質問を止める（`src/agenda/agent.ts:525-527`） | メモ表示の申し出は、答えを待つ質問に数えない |
| 質問チェックが、好きなもの・苦手なもの・予定・困りごとを同じ種類の質問として1回にまとめる（`src/agenda/prompt.ts:98`）。完了分では、聞いた質問112件に対し、外した質問も112件あった（計画の drop、このチェック、話が終わった質問を合わせた数。内訳は記録に出ない） | 同じ中身の質問だけを聞き直しとする。先に、外した理由を記録に出して内訳を確かめる |
| メモ1件につき話題は1回だけである（`src/agenda/plan.ts:176-185`） | メモの要点ごとに話題にできるようにする |

確かめる数字は、hour と lull の回/分、最長の沈黙、メモが話題になった割合である。

### 4. 多く話しても「しつこい」にならない中身

| 何が起きているか | 直し方 |
| --- | --- |
| 発話の種類が質問と豆知識の2つだけである。correction では、同じ話題に90秒で質問を5回した | 種類を足す（相手の話への感想だけの一言、いま調べていることの実況、前の話の続き）。同じ話題で質問が続かないよう、コードが種類を回す。頻度は変えない |
| 「今日はこのへんで」「その話はあまりしたくない」のあとも、同じ話題の質問が出る。断りの判定（`declinesOffer`）は決まった言い方しか読まない | 話題への引きを計画に伝え、その話題の項目を外して別の話題に切り替える。黙るのではなく、話題を替える |
| 調べものが連鎖して、利用者の言葉から離れる。hour では「家でのんびりしてる」の一言から、入浴・照明・夕食・ストレッチ・飲み物・昼寝の7件を調べた | メモを根拠にした調べものは、元になった利用者の言葉を引き継ぐ。利用者が反応した枝を先に伸ばす |

## 見つけた不具合

- **`src/agenda/check.ts:117`**: 重複チェックが `covered` を `coveredBy: null` で返すと、`coveredBy!.slice(5)` で例外になる。頼まれても約束してもいない調べもので起きる。プロンプトは「前の依頼と同じなら null でよい」としている。scripted LLM で再現した。
  - 今回の計測では、18件中6件がこの例外で止まった（prepare・direct・intro の各1回目、hour の2回目、returning の2回）。止まった時刻は240〜1810秒である。
