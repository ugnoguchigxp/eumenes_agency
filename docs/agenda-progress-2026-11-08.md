# agenda（always-on 改訂）の実装と検証の記録

2026-11-08。[設計](../spec/always-on-agenda-design-2026-11-08.md)を agency の中だけで実装し、Eumenes の構造を mock で再現して検証した記録。Eumenes のコードは変更していない。前の方式（tickごとにLLMが判断する always-on）の記録は[always-on の進捗](always-on-progress-2026-11-07.md)にある。

## 作ったもの

| 場所 | 中身 |
| --- | --- |
| `src/agenda/` | コア。やることの一覧（ask・research・talk）をコードが持ち、いつ計画するか・いつ調べものを頼むか・いつどれを話すかをコードが決める。LLMを呼ぶのは、計画（新しい情報があったとき）、調べものの重複チェック（頼む直前）、話す文（話すと決めたとき）の3つだけ |
| `examples/virtual-eumenes/agenda/` | Eumenes の mock。eumenes_memory と steward（往復ごとに利用者の事実を記録）、Docling の Markdown 文書（調べた担当のメモ、ファイル保存も可）、一度に1件だけ受ける web_research |
| `standalone/agenda-reply.ts` | 通常応答。記憶とメモを参照し、ツールは `start_preparation`（調べものを頼む。利用者が頼んだかどうかを区別）、`show_note`（メモを表示）、`set_quiet`（話しかけだけ止める／すべて一時停止） |
| `standalone/agenda-session.ts`・`standalone/agenda.ts` | CLI（`bun run agenda`）。記憶とメモは `data/agenda/` に残り、agent の作業メモは残らない |
| `standalone/agenda-research.ts` | 実際の Web 検索で調べてメモを書く担当（CLI の既定。評価は `--web` のとき） |
| `eval/agenda/` | 仮想時計の再生（16シナリオ）、実モデルの評価（`bun run eval:agenda:api <run>`）、計測 |
| `test/agenda/` | scripted LLM の固定試験 |

前の方式の `src/always-on/` は、別の作業が同時に変更していたため触っていない。

## 計測の項目

- 質問の数と答えてもらえた数、話題（メモをもとにした話しかけ）の数、調べもの・メモ・記憶の数
- 計画・重複チェック・話す文の呼び出しと、そのうち中身がなかったもの（何も変えなかった計画、見送った話す文）の時間の割合（「無駄」）
- 重ねた質問（答えを待っている質問があるのに次を聞いた）、二択の質問、繰り返し
- シナリオごとの守る条件
- 遅延と費用（記録のみ）

## 1回目（ag1、修正前、Haiku low、mock の調べもの）

- 中身のなかった呼び出しの時間は 16%（前の方式は「待つ」で終わった時間が 57〜60%）。費用は16シナリオで $0.076（前の方式は $0.14〜$0.36）。
- 見つかった問題:
  - 返事が、ツールを呼ぶ前と後で同じことを2回言った。
  - 朝なのに、前の晩に作った「明日の京都」の質問をそのまま言った。
  - 二択の質問（「ピリッと系と激辛系のどちらが」）。
  - 返事が自分で始めた調べものも「頼まれた」扱いになり、「頼まれていた調べものができました」と言った。
  - 利用者が言っていない話題（エージェント自身の好きなマイメロディ）を調べた。自分の好みと利用者の好みを混同して質問した。
  - 同じテーマの調べものを繰り返した（箱根の宿選びを前日と翌日に、12月の箱根のイベントを2回）。

## 直したこと

- 返事: ツールを先に呼び、結果を見てから一度だけ書く。
- 話す文: 項目を作ってからの時間を渡し、「明日」などの言い方を今の時刻に合わせる。計画は、時刻が進んで合わなくなった項目を外す。
- 二択の質問をしない（計画と話す文の両方）。
- `start_preparation` に「利用者が頼んだか」を足した。頼まれたものだけ、できたことを知らせる。
- 調べものの根拠は、利用者の言葉・記憶・それを元にしたメモだけ。自分の発言だけでは調べない。エージェント自身の好きなもの（`interests`）は仕組みごとなくした（利用者の判断）。
- 同じテーマの調べものを繰り返さない（利用者の指摘）。
  1. 計画の段階で、これまでの調べものとメモ（前のセッションの分も）と文字の重なりで比べ、明らかに同じテーマなら入れない。
  2. 頼む直前に、短いLLM呼び出しでメモの一覧と照らし合わせ、もう分かっていれば外し、一部だけ新しければ新しい点に絞って頼む。
- 「重ねた質問」の数え方を、答えを待っている質問があるのに次を聞いた回数に直した（前の数え方は、返事のあとの質問まで数えていた）。

## 3回目に向けて直したこと

- 話す文に、静かな時間が終わったことを渡す。
- 質問を1件見送ったら、ほかの質問もまとめて10分後に回す。
- 話題の一言が「？」で終わったら、答えを待っている質問として扱い、答えがあるまで次の質問をしない。
- quiet・overnight の守る条件から「静かな時間中も調べる」を外した（話しかけを止めても調べものが止まらないことは固定試験で保証する。調べるテーマが一つなら、同じテーマを繰り返さないのが正しい）。二択の計測から「どちらも」を外した。

## 3回目（ag3）と4回目（ag4）

ag3 で新たに見つかった問題:

- overnight: 朝の返事が、夜に実際に頼んでメモになっていた調べものを「実は頼めていませんでした。すみません」と言った。返事には、前の返事でツールを呼んだ記録が見えていなかった。
- mock の steward が「明日京都へ」を「明日」のまま記録し、返事の謝罪を「利用者は京都の調べものを頼みたくない」と利用者の考えとして記録した。
- anticipate: 返事はメモの題と要約しか見えず、本文にあるエリアの情報を使えなかった。呼んでいないのに「調べもの担当に頼みました」と言った。
- intro: 返事が質問で終わり、答えがないまま60秒後に次の質問をした。

ag4 に向けて直したこと:

- 返事の状態に、このセッションの調べものの記録（何を頼み、メモになったか）を入れた。呼んでいないのに「頼みました」と言わない、記録にある調べものを「頼めていなかった」と言わない、と指示した。
- 返事にメモの本文を読むツール `read_note` を足した（結果は資料として印を付けて渡す）。
- 返事が質問で終わったときも、答えがあるまで次の質問をしない。
- mock の steward に現在の日付を渡し、相対的な日付を日付に直す。エージェントの発言を利用者の考えとして記録しない。
- 質問に「それと」などで二つ目を足したら断る。

ag4 の様子:

- overnight: 夜に返事が頼んだ調べものは、記録どおり実際に頼まれていた。記憶は「11/8（日）に京都へ日帰り」と日付で残った。朝の返事はメモの中身で答えた。夜の間も、頼む直前の確認で観点を絞りながら、帰りの時間や当日の催しを調べた。ただし朝の「おはよう！」で話しかけの停止を解除せず、朝の話題を振れなかった（前の2回は解除していた）。
- anticipate: 返事が `read_note` でメモを読み、エリアの情報がないと正直に言ってから一般的な知識で答え、エリア比較を頼んだ。2分後にその結果で話題を振った。
- news: 話題の一言の最後に、5分前にした質問と同じ文を付けた（文全体の一致しか見ていなかった）。

ag5 に向けて直したこと:

- 返事: 静かな時間の途中で話しかけられ、その理由が終わったと分かるとき（おはよう、ただいま、作業終わった）は `set_quiet` で解除する。
- 繰り返しを一文ずつ比べる。話題の一言は「表示しましょうか？」で締め、前にした質問を足さない。

## 5回目以降（ag5〜ag12）と独立レビュー

ag5〜ag10 で見つかって直したこと:

- 朝の返事が、夜に実際に頼んでメモになった調べものを「頼めていなかった」「正確ではなかった」と訂正する誤りが、状態に調べものの記録を入れても続いた。前の返事でのツール呼び出しと結果を、次の返事の会話履歴に本物の呼び出しとしてそのまま入れた（ツール呼び出しの id は英数字・`_`・`-` だけにする。`.` を含めると API が 400 を返した）。利用者の前の発言から30分以上たっていれば、状態の先頭に「留守の間」の要約（何時間たったか、その間に完成したメモ、調べ中ではないこと）を置いた。
- 返事が「調べておきます」と頼んだ調べものは約束として扱う。重複チェックはかけるが、もうメモで分かっていれば頼み直さず、そのメモの話題で約束を果たす。チェックを飛ばすのは利用者がはっきり頼んだものだけ。できたら「調べておくと言っていた」と知らせる（「頼まれていた」とは言わない）。
- 返事が読んだ・表示したメモ、返事の文が題・要約と大きく重なったメモは、話題にしない（返事の直後に同じ内容を繰り返していた）。
- 返事の二重化（ツールの前と後で同じことを言う）は指示だけでは止まらず、同じ文の2回目をコードで除いた。
- 二択の質問（「どちら」「どっち」）は、指示があっても出たのでコードで断る。
- 最近見送った項目と理由を計画に渡す（相づちしか返らない場面で、質問を足しては見送ることを繰り返していた）。
- 返事はメモの id を言わない。ツールの操作を説明しない。時刻の文字列に年を入れた（夜の調べものの依頼が年を取り違えた）。

## 利用者役と判定役を入れた評価（ag16〜ag18）

台本の利用者は答えないため、会話が続いたときの振る舞いが見えなかった。そこで評価に2つを足した。

- **利用者役**（`eval/agenda/user.ts`）: シナリオの人物として、エージェントの話しかけに答えるかどうかを決める。答えるなら何秒後に何と言うかも決め、そのときの気持ちを一言残す。
- **判定役**（`eval/agenda/judge.ts`）: 会話全体を読み、流れ・質問・先回り・加減・正直さを1〜5で採点する。いちばん直すべき点を一文で書く。

判定役も利用者役も Haiku なので、回ごとのぶれは大きい。点数は傾向として見て、個々の指摘は記録で確かめる。

### ag16 で見えた問題と直したこと

- **質問攻め**: 利用者が答えるたびに、返事の15秒後に次の質問が来た（cold で5回続き、利用者役は「しつこい」）。
  - 原因1: 短い答えでも、返事のない発話の数が0に戻るため、間隔が伸びなかった。
  - 原因2: 返事には質問で終えないよう指示し、代わりに自分から質問していた。
  - 直したこと: 会話中（利用者が3分以内に話した）は、自分から質問しない。聞きたいことは、コードが選んだ1件を返事に渡し、返事の最後に添える。添えるのは、返事2回に1回まで。
- **断ったあとの話題**: 「今はいいかな」のあとに、別のメモを勧めた。
  - 直したこと: 断りの言葉を見たら、質問と話題を10分止める。計画にも、断られたことを伝える。
- **判定役の読み違い**: 一時停止が明けたあとの動きを「停止を守っていない」と減点していた。停止の行に終わりの時刻を書くようにした。

### ag17 で見えた問題と直したこと

- 返事が「〜ありますか。」と「。」で質問を終えると、質問と数えなかった。丁寧な問いかけの形も数えるようにした。
- 返事は渡された質問をほとんど添えず（3回）、残った質問を10分近く後に自分から聞いた（「モンハンの話に戻りますね」）。
  - 返事には、急いでいるとき以外は聞くよう指示した。
  - 会話の言葉にひもづく質問は、5分過ぎたら外すようにした。
- 断りの判定は、独立レビューで誤検出の指摘を受けた（「それはいいですね」「それは結構好き」も断りと判定していた）。句全体が断りの言い方のときだけ、断りとみなすようにした。約束した調べものの報告は止めない。

- **質問攻めはなくなった。** 違和感の割合は 66% → 48% に下がった。
- **集めた事実は減った。** 記憶は 65 → 41 件。会話中の質問が「返事2回に1回」になった分である。「多少うるさいくらいに集める」との兼ね合いは、利用者の試用で決める。
- **ag18 の判定役の指摘の多くは、mock の調べものに由来する。** mock のメモは実在の情報を持たないため、「まとまりました」と言いながら中身が「確かめ方」だけ、という指摘になる。残りは次のとおり。
  - 会話の2分ほどあとに、その話題のメモを勧める（inject・dislike・restrain）。設計どおりの先回りだが、利用者役は「しつこい」と感じることがある。
  - 出発前の朝、会話が途切れた3分後に、自分から質問した（overnight、利用者役は「慌ただしい」）。

## 本物の memory に替えた（2026-11-09）

Eumenes が導入している eumenes-memory 0.0.4 と Memory host 0.1.0 の配布物を、Eumenes の `vendor/` から `examples/virtual-eumenes/vendor/` に取り込んだ（SHA-256 は Eumenes の manifest と一致）。CLI（`bun run agency`）と実モデルの評価は、mock の記憶の代わりにこれを使う。

- 書き手: 利用者の新しい発言を出典（source）として登録し、memory 自身の計画の指示と schema で Haiku（low）が記録・訂正・忘却を決める。host が引用を出典の byte 範囲で確かめてから適用する。エージェントの発言は出典にしない（直前の発言は資料として計画に渡す）。
- 置き場所: CLI は `data/agenda/memory-host/`（SQLite、journal、socket）。前の mock の `data/agenda/memory.json` は読まない（消してはいない）。評価はシナリオごとに一時フォルダ。

- 費用と時間: 1発言あたり約 $0.001、5〜8秒（返事のあと裏で動く）。

### 試して分かったこと

- 訂正はうまく扱う。「来週の土曜は京都」は日付に直して記録し、「再来週だった」で同じ項目を 11/21 に更新した。
- **意図や未確定の予定は記録しない。** 「来月、箱根に一泊で温泉旅行に行こうと思ってるんだ」「一泊だけ考えてます」は、low でも medium でも記録されなかった（memory の指示の「確定していない可能性は記録しない」に当たる）。medium では「来週の土曜は京都に行きます」も記録しなかった。anticipate シナリオでは前日の会話から記憶が1件も残らず、翌日に使えたのは調べもののメモだけだった。先回りに要る「予定・関心」の置き場所は、memory とは別に決める必要がある。
- `recall` は質問に記憶で答えるための想起で、関係する記憶を選ぶ検索ではない。「推論の速度を上げる方法を知りたい」に対して、「AI MAX 395 で Qwen3.8 27B を動かしている」を返さなかった。
- 3シナリオ（intro・recall・anticipate、ag19-mem）は1回ずつで、判定はぶれの範囲。比較はまだしていない。

### レビューで直したこと

- memory が書き込みのまとまりの一部だけを適用したとき（確認待ち・途中で失敗）、エージェント側の記憶が古いままになっていた。apply の結果をまとまりごとに見て報告し、apply を試みたら必ず読み直す。

## 予定と関心のメモ（2026-11-09）

本物の memory は意図や未確定の予定を記録しないので、それを置く場所として「利用者の予定と関心」の Markdown メモを足した（利用者の選択 (b)）。

- 中身: 見出し「予定」「関心」の下の箇条書き。予定は未定のものも含め、日付に直して書く。関心は、いま気にしていること、考え中のこと、memory に入らなかった習慣や好み。
- 書き手: core の `updateProfile`（src/agenda/profile.ts）。会話のあと、memory の書き手の次に Haiku（low）を1回呼ぶ。根拠は利用者の新しい発言だけで、エージェントの発言は根拠にならない。足す・直す・消すは名指しした行だけを変えるので、利用者が書いた行や言い回しは残る。関心を消すには利用者の言葉が要る（過ぎた予定だけは根拠なしで消せる）。
- 使い道: 計画・話す文・返事に `plans`・`interests` として渡す。計画は `profile:<id>` を調べものの根拠にできる（利用者の言葉と同じ扱い）。このメモを根拠にした質問は、会話の言葉にひもづく質問と違って5分で外れない。
- 置き場所: CLI は `data/agenda/profile.md`（実行中にエディタで直してよい。`/profile` で表示）。評価はシナリオごとに持ち、前日と翌日の会話で共有する。
- 固定試験 5件（memory に入らない予定が入る、エージェントの発言は根拠にならない、利用者の行が残る、関心は勝手に消えない、計画がメモを根拠に調べものと質問を足し、その質問が話される）。

### 実モデルで確かめたこと（各1回）

- anticipate（ag20-profile）: 前日の「来月、箱根に一泊で温泉旅行に行こうと思ってる」が「12月に箱根へ一泊の温泉旅行を考えている。宿と同行者は未定」として残った。翌日の返事は予定を知っている前提で答え、「同行者は未定」から「どなたかと一緒に行かれる予定ですか？」と聞き、答えでメモを「ひとり旅」に直した。先回りの判定は 3 → 4。memory は前回と同じく0件。

## 調べたことを雑談に使う：試したが採用しなかった（2026-11-09）

調べものは会話エージェントの責務ではなく、Eumenes の web_research と pursuit の責務である（利用者の判断）。このプロジェクトでは Haiku のサブエージェントが代わりに調べ、メモだけを返す。agency が良くできるのは、届いたメモをどう話題にするかの部分になる。段階ごとに実装・検証・採用する方針で、悪影響のあるものは入れない。

### 話題の試験台（eval/agenda/talk-bench.ts）

8つの場面（`eval/agenda/talk-situations.ts`）で、計画が話題を1件足したところから、エージェントが自分の話す文の処理で話題を振る。メモは実際の Web 検索で一度だけ作って固定し（トークン代 $0.027、検索16回）、どの版も同じ場面と同じメモで比べる。利用者役が反応し、確認係（Haiku）が次の3つを判定する。

- 話題への反応（乗った・相づち・断った）
- メモ表示の申し出への反応（見たい・今はいい）
- メモにない断定

```
zsh -l scripts/api-entry.zsh eval/agenda/talk-bench.ts notes
zsh -l scripts/api-entry.zsh eval/agenda/talk-bench.ts run <name> [--repeat 5] [situation...]
bun eval/agenda/talk-bench.ts compare <name>... [--detail]
```

- 話題そのものにはほぼ乗る。
- メモ表示の申し出は、20回中17回が「今はいい」だった。
- 違和感の多くは「メモを勝手にまとめてあった」「表示の提案が押しつけがましい」だった。

### 判断

- 基準は2回とも同じ水準で、十分である。それを超えない変更は、ぶれと悪影響を増やすだけとみて、どれも採用しない（利用者の判断）。
  - 2a・2b・話題のあとも返事を待つ修正・第3段階は、すべて元に戻した。
  - 試験台と、頼んでいない結果を受け取る試験は残す。
- 1回の発話だけを見る試験台で良くなっても、会話全体では良くならないことがある。採用は会話全体のシミュレーションで決める。
- 記録しておく既知の問題: 朝のあいさつを繰り返すと、その話題ごと捨てられる（京都の場面）。直すなら、基準の上でこの修正だけを、会話全体で確かめてからにする。
